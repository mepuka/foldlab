## The header discipline, as applied

Both emitters already carry the house header pattern: a prose block, then
`Gate.Emitted.headerLines` (schemaVersion, emitter, module, toolchain — four
fields, no timestamp, no path). The refactor in each emitter is the same shape:

```
moduleWith (header : List String) : Module   -- shared imports + decls
```

so the two copies of a module cannot differ in a declaration, only in the prose
that says which file the reader is standing in. Verified mechanically:

```
diff <(sed -n '/^ \*\//,$p' library/effects/src/cas/generated/WordLogSchema.ts) \
     <(sed -n '/^ \*\//,$p' experiments/workbench/src/generated/WordLogSchema.ts)   → identical
diff <(sed -n '/^ \*\//,$p' library/effects/src/cas/generated/grammar/kindTags.ts) \
     <(sed -n '/^ \*\//,$p' experiments/workbench/src/generated/kindTags.ts)        → identical
cmp  library/effects/src/cas/generated/grammar/names.json \
     experiments/workbench/src/generated/grammar/names.json                          → byte-identical
```

**The header does not embed the output path.** `Gate.Emitted` is deliberately
four constants of the build so a regeneration that changes nothing changes no
byte; adding a path field would make the header a function of where the file
went. So the two TypeScript mirrors differ only in the hand-written prose block,
and `names.json` — a JSON document, whose `emitted` header is four fields with
nowhere to put a sentence — is byte-identical. That is the strongest form the
mirror claim takes anywhere here, and it is the one to quote.

The workbench headers quote the README's law verbatim:

> «any surface the store language already describes must be generated, never
> typed by hand» — `experiments/workbench/README.md`

placed in the file a person tempted to hand-edit will actually be standing in.

## Judgment calls, flagged for the grill

### 1. No `gen:workbench-*` tasks. The brief asked for them; I did not add them.

The brief allowed "one `gen:workbench` if the house pattern prefers — read how
`gen:backend-*` tasks are structured". Having read them, the house pattern is
**one task per `lake exe`, listing every fixture that executable writes**
(`gen:grammar-manifest` already lists five outputs; `gen:meta` lists eight). One
run of `lake exe emitword` now writes both packages' copies, so the workbench
mirrors are outputs of `gen:backend-word` and `gen:grammar-manifest` and are
listed there. Three reasons a second task is worse, not better:

1. It would re-run the same executable — the same work and the same bytes twice
   per `gen`, and twice again per `gen:ci`.
2. `tools/EnvLedger.lean` joins each `[[lean_exe]]` to the task that runs it bare
   (`drives`) and to the `--check` that gates it (`gates`), taking the FIRST
   match. Two tasks running `lake exe emitword` would make `declaredOutputs`
   depend on the order of `mise.toml` — precisely the drift the ledger exists to
   report.
3. The zero-duplication spellings are unavailable by design: the ledger's TOML
   door reads `description`, `dir`, `run`, `sources`, `outputs` and REFUSES any
   other task key, so `depends` or an alias would red the environment gate rather
   than wire anything.

The alternative I considered and rejected: drive the second copies by
`mainAt`'s positional override (`lake exe emitgrammar <workbench path>`) from
separate tasks. That is a real house mechanism, but re-pointing `emitgrammar`
moves four fixtures, not two — the workbench would acquire `manifest.json` and
`refMarkers.ts` nobody asked for — and it would run both emitters twice.

**Consequence to weigh:** there is no task whose name contains "workbench" that
regenerates these files. `mise run gen:backend-word` and
`mise run gen:grammar-manifest` do. The mise comment block now says so at the
place the README's promise ("its TypeScript comes from a `mise run gen:` task")
sends a reader. If the grill wants the promise honoured literally by name, the
cheap fix is renaming the two existing tasks, not adding two more — and a rename
touches the ledger's residence rows, so it is a ruling, not a wiring change.

### 2. Layout: `kindTags.ts` at the generated root, `names.json` one level down

I followed the brief's paths literally — `src/generated/kindTags.ts` and
`src/generated/grammar/names.json`. Note this is NOT the effects layout, where
both sit under `generated/grammar/`. The asymmetry looked deliberate (the brief
spelled one name with a `grammar/` prefix and the other without, in the same
sentence), so I did not "fix" it. If parity with the effects tree is wanted so
Lane C's two import paths differ only in the package root, it is a one-line
change to `EmitGrammar.workbenchTagsTarget` plus the matching `outputs` line.

### 3. Fixed targets, not derived ones

The workbench targets are fixed constants, deliberately NOT derived from the
positional override the way `tagsTargetFor` / `namesTargetFor` derive from the
JSON target. Those three are siblings in ONE generated directory; these are
mirrors in a DIFFERENT package, and a re-pointed effects artifact must not drag
the front end's copies after it. `EmitGrammar.registryTarget` is the standing
precedent for a fixture the override does not move.

### 4. Only two of the five grammar projections

The workbench gets `kindTags.ts` (the door's refusal set) and `names.json` (the
derived-name inventory) — the two a surface over this store needs to name a node
and to refuse an unregistered plane. Not `manifest.json` (the whole interchange
document; nothing in the workbench reads it yet) and not `refMarkers.ts` (the
payload-key law of a codec the front end does not run). Each is one line the day
something needs it. This follows the brief; recorded so the omission is visible
rather than looking like a miss.
