## Part 2 — Foldkit API deep dive (factual)

Source of truth for this section: `/Users/pooks/Dev/foldlab/experiments/workbench/node_modules/foldkit/` at version **0.154.0**, peer-pinned to `effect@4.0.0-rc.112`. Quotes are from the shipped `.d.ts` and `.js` files.

### 2.1 The canvas module, in full

Four files, ~120 lines of real logic:
`dist/canvas/shape.d.ts`, `dist/canvas/view.d.ts`, `dist/canvas/paint.d.ts`, and the barrel `dist/canvas/public.d.ts`.

The public surface is exactly:

```
export { BezierTo, Circle, Close, Group, LineCap, LineJoin, LineTo, MoveTo, Path,
         PathInstruction, Point, QuadTo, Rect, Text, TextAlign, TextBaseline, view }
export type { Shape, ViewConfig }
```

**The shape union is five constructors.**

```ts
export type Shape = typeof Rect.Type | typeof Circle.Type | typeof Path.Type | typeof Text.Type | Group
```

- `Rect` — `x, y, width, height`, optional `fill`, `stroke`, `lineWidth`.
- `Circle` — `x, y, radius`, same optional paint fields.
- `Path` — `instructions: ReadonlyArray<PathInstruction>` plus `fill`, `stroke`, `lineWidth`, `lineCap`, `lineJoin`. `PathInstruction` is a five-way union: `MoveTo`, `LineTo`, `QuadTo`, `BezierTo`, `Close`.
- `Text` — `x, y, content`, optional `font` (a raw CSS font string), `fill`, `stroke`, `lineWidth`, `align`, `baseline`. One line of text per node.
- `Group` — `shapes: ReadonlyArray<Shape>`, optional `translate: Point`, `rotate: number`, `scale: Point`, `opacity: number`. Recursive; the schema side uses `S.suspend`, the type side an `interface` so TypeScript's lazy interface evaluation resolves the cycle.

Every constructor is a `taggedStruct` — an Effect `Schema` that is also callable. **The scene is schema-described data, not opaque draw calls.** That is the single most consequential fact about this module: a `ReadonlyArray<Shape>` can be decoded, encoded, diffed, hashed, stored, and sent over a wire with the framework's own codec machinery, because `Group` is built from `S.Array(S.suspend(() => S.Union([Rect, Circle, Path, Text, Group])))`.

**What the shape union cannot express, as shipped.** There is no node for: images or `ImageBitmap` (no `drawImage`), gradients or patterns (fills are `S.String` only, so any CSS colour string works but a `CanvasGradient` object cannot be attached), shadows, clipping regions, line dashes, `globalCompositeOperation`, multi-line or wrapped text, `roundRect`, ellipse/arc-as-a-shape (only via `Path` beziers — there is no `ArcTo`), or any handle on `measureText`. There is no z-index; paint order is array order, depth-first.

**Group transform order is fixed** (`paint.js`, `paintGroup`): `globalAlpha *= opacity`, then `translate`, then `rotate`, then `scale`. A caller who needs scale-then-translate must nest two `Group`s.

**The repaint model is: clear everything, repaint everything, every render.**

```ts
export const paintScene = (ctx, width, height, shapes) => {
    ctx.clearRect(0, 0, width, height);
    Array.forEach(shapes, paintShape(ctx));
};
```

`paintShape` brackets **every single shape** in `ctx.save()` / `ctx.restore()` — including leaves, not just `Group`s — so per-shape state cannot leak to siblings. That is a correctness guarantee bought with two context-state operations per node.

There is **no dirty-rectangle tracking, no damage region, no scene diffing, no retained bitmap, no layer separation, no culling, and no partial repaint of any kind.** The `.d.ts` states the contract plainly: "The canvas is a pure function of `shapes`. Same shapes produce the same pixels."

**When the repaint fires.** `view.js` attaches three snabbdom hooks to the `<canvas>` vnode:

- `insert` — `canvas.getContext('2d')`, store it in a module-level `WeakMap` keyed by the element, then `paintScene`.
- `postpatch` — look the context up in the `WeakMap`, then `paintScene` again.
- `destroy` — delete the `WeakMap` entry.

`postpatch` runs on **every patch of that vnode**, unconditionally. It does not compare old and new `shapes`. So the canvas fully repaints whenever the surrounding view is patched, whether or not any shape changed — unless the caller interposes memoization above it (see 2.7, seams).

**DPR handling: absent.** `view.js` sets `props: { width, height }` — the canvas *attribute* size, i.e. the backing store — from the same two numbers the caller passes. Nothing reads `window.devicePixelRatio`; nothing calls `ctx.scale`. There is no CSS-size-versus-backing-store separation in the module at all. On a 2× display, a canvas sized `{ width: 400, height: 300 }` and laid out at 400×300 CSS pixels renders at 1× and is upscaled by the compositor — visibly soft. The caller can compensate only by passing `width: cssWidth * dpr` and scaling every coordinate, or by wrapping the whole scene in a `Group({ scale: { x: dpr, y: dpr } })` and sizing the element via `className` CSS.

**Event mapping is three pointer events and a point.**

```ts
onPointerDown?: ((point: Point) => Message) | undefined
onPointerMove?: ((point: Point) => Message) | undefined
onPointerUp?:   ((point: Point) => Message) | undefined
```

`toCanvasPoint` is the whole coordinate contract:

```ts
const toCanvasPoint = (canvas, event) => {
    const rect = canvas.getBoundingClientRect();
    const scaleX = rect.width === 0 ? 1 : canvas.width / rect.width;
    const scaleY = rect.height === 0 ? 1 : canvas.height / rect.height;
    return { x: (event.clientX - rect.left) * scaleX,
             y: (event.clientY - rect.top) * scaleY };
};
```

It maps client coordinates into the canvas's *internal* coordinate space, correcting for any CSS scaling — the guard against a zero-width rect is there. Note what it does **not** do: it does not invert any `Group` transform. If the scene is drawn inside a pan/zoom `Group`, the point arrives in unpanned, unzoomed canvas space and the application must invert the transform itself.

What the module gives you, per event, is **a `Point` and nothing else**. No `pointerId`, no `buttons`, no modifier keys, no `pressure`, no `pointerType`, no coalesced events. And there is no `wheel`, no `pointercancel`, no `pointerenter`/`leave`, no `contextmenu`, no `dblclick`, no keyboard, no pointer capture, no `ResizeObserver`. Dispatch is synchronous: the listener calls `__requireDispatch()`'s `dispatchSync` at fire time.

**Hit testing: none.** There is no `isPointInPath`, no spatial index, no picking. The application receives a point and owns the entire question of what is under it.

### 2.2 The render loop — what actually schedules a repaint

This is the fact that determines the canvas module's real performance envelope, and it lives in `dist/runtime/runtime.js`, not in the canvas module.

**Renders are coalesced into one `requestAnimationFrame` callback.**

```js
const scheduleRenderFrame = () => {
    if (isRenderFrameScheduled) { return; }
    isRenderFrameScheduled = true;
    commitNotifier.markCommitPending();
    requestAnimationFrame(renderFramePlain);
};
```

The source comment states the guarantee: render frames run as plain JavaScript inside the rAF callback; Messages arriving between frames mark at most one pending frame, and the callback renders once with the latest model. So a burst of one thousand Messages in one task produces **one** view build, **one** snabbdom patch, and therefore **one** canvas repaint. The framework already owns the frame-coalescing discipline that hand-written canvas code usually has to invent.

**Message drain has a yield budget.** The runtime accumulates synchronous processing time across drains and, once over budget, defers to a `MessageChannel` tick to start a new task so a pending frame can paint. The comment is explicit about why not `setTimeout`: browsers clamp it to 4ms+, while MessageChannel delivers in roughly 0.5ms. Dispatch itself routes through `queueMicrotask` rather than the Effect scheduler, for the same sub-millisecond reason.

**Each frame rebuilds the whole view and patches it.** `renderSyncPlain` calls `view(model, htmlBuilder)` to produce a fresh `Document`, then `__patchVNode(maybeCurrentVNode, nextDocument.body, container, ...)`. The canvas vnode is patched as part of that, firing `postpatch`, firing `paintScene`.

**Four phases are individually budgeted and measurable.** `SlowPhase` is `Schema.Literals(['Update', 'View', 'Patch', 'SubscriptionDependencies'])`, and `SlowConfig` lets you set `thresholdOverrides` per phase and supply `onSlow(context)`. Each context carries `durationMs` and `thresholdMs`; the update context carries `previousModel`, `nextModel`, `message`. This is a shipped, first-class frame-budget instrument — on in development by default, and settable to `show: 'Always'`.

**View Transitions are a per-render decision.** `ViewTransitionConfig` is a predicate over `{ previousModel, model, message }` returning `false`, `true`, or `{ types }`. Returning true wraps that render in `document.startViewTransition`. The doc notes the runtime coalesces a burst into one frame, so the predicate sees the last dirtying Message before the frame.

### 2.3 How long-running and streaming inputs enter the loop

Foldkit has four distinct doors, and they are not interchangeable.

**Subscriptions — the blessed door for anything whose lifetime is derived from the Model.** `Subscription.make<Model, Message>()(entry => ({ ... }))`. Each entry declares:

- `dependenciesSchema` — must be a `Schema.Struct`, so every dependency is explicitly named at the schema level.
- `modelToDependencies: (model) => Dependencies`
- `dependenciesToStream: (dependencies) => Stream.Stream<Message, never, Services>`

The lifecycle rule is stated in the type docs: without `keepAliveEquivalence`, every Model change recomputes the dependencies; equivalent dependencies leave the Stream alone, and **any change tears it down and restarts it**. Equivalence is derived automatically via `Schema.toEquivalence(dependenciesSchema)` unless you supply your own. This is the load-bearing hazard for a streaming canvas: a subscription whose dependencies include anything that changes per frame restarts its stream every frame.

`keepAliveEquivalence` is the documented escape hatch — Model changes the equivalence calls equal leave the Stream running, and the running Stream reads the latest dependencies through a second `readDependencies` thunk argument. The `.d.ts` names the canonical case: Foldkit UI's `DragAndDrop.autoScroll` reading the latest pointer `clientY` each rAF tick.

- `Subscription.persistent(stream)` — a Stream whose lifecycle is independent of the Model, running for the lifetime of the Subscriptions record. This is the door for a connection that must not be torn down by unrelated Model churn.
- `Subscription.aggregate` combines records and throws on duplicate keys at startup.
- `Subscription.lift` translates a child Submodel's record into a parent context, with an optional `when` gate — one predicate for the whole record, or an `EntryGates` map naming entries individually. A closed gate is documented as a real teardown, not a paused stream.
- `Subscription.animationFrame({ isActive, toMessage })` — emits a Message per rAF tick carrying `deltaTime` in ms. `isActive(model)` gates whether the loop is scheduled at all; when false, no callbacks fire. The docs warn that a hidden tab makes `deltaTime` spike to seconds on refocus and advise capping it (32ms is called typical).
- `Subscription.fromEvent` / `fromEventFilterMap` — build a `Stream` (not an entry) from a DOM `EventTarget`, with `Effect.acquireRelease` listener lifecycle so the listener never leaks on interruption. `fromEventFilterMap`'s mapper returns `Option<Message>` and is documented as the right choice when the keep/drop decision is paired with `preventDefault()`, because the mapper runs synchronously inside the browser's event dispatch while a downstream `Stream.filterMap` would run a turn too late. `target` accepts a thunk, read inside acquire, for targets that do not exist until the scope opens.

The docs page (https://foldkit.dev/core/subscriptions) draws one distinction worth carrying: `Stream.tick` is wall-clock time, for a discrete cadence, while `animationFrame` is display refresh, for physics. The blessed periodic pattern shown there is a plain Effect stream gated by Model state —
`Stream.when(Stream.tick(Duration.seconds(1)).pipe(Stream.map(Ticked)), Effect.sync(() => isAutoCounting))` — inside an entry's `dependenciesToStream`. The `keepAliveEquivalence` example on that page is exactly the rAF-plus-live-pointer-position case, using `Equivalence.Struct({ isDragging: Equivalence.Boolean })` so that a per-frame `clientY` in the Model does not restart the stream, with `readDependencies()` read synchronously inside the rAF callback.

**There is no built-in SSE/EventSource or interval helper in the shipped surface.** `dist/subscription/` contains exactly `subscription`, `animationFrame`, and `fromEvent`. An `EventSource` stream is written by the application as an ordinary Effect `Stream` — `Stream.callback` with `acquireRelease` around `new EventSource(...)` / `.close()` — and then either wrapped in `Subscription.persistent` or placed in an entry's `dependenciesToStream` keyed on whatever Model state should own its lifetime. Periodic work is likewise plain Effect (`Stream.repeat` / `Schedule`), gated the same way. The framework's opinion is about *where the lifetime is declared*, not about supplying the transport.

**ManagedResource** is the model-driven lifecycle for long-lived *handles*, threaded through the runtime config as `managedResources?: ManagedResources<Model, Message, ManagedResourceServices>` and contributing services to the same `Resources | ManagedResourceServices` channel that `update` and Subscriptions see. https://foldkit.dev/core/managed-resources gives the API — `ManagedResource.tag<T>()('name')`, `ManagedResource.make()`, and a `modelToMaybeRequirements` returning `Option.some(params)` / `Option.none()` — and the four transitions: none→some acquires and dispatches `onAcquired`; some→none releases and dispatches `onReleased`; some(a)→some(b) releases and re-acquires; structurally equal keeps the handle. Acquire failure dispatches `onAcquireError` without crashing. Commands reach the handle via `Tag.get`, which fails with `ResourceNotAvailable` when inactive.

The distinction the docs draw against Subscriptions is that Subscriptions are read-only effects with no exposed handle, while a ManagedResource hands you something you can operate on later. **The listed use cases include Web Worker pools** alongside WebSockets, camera/audio streams, `AudioContext`, and per-session database connections — which is the shipped, named door for offloading work to a worker under Model control.

**Commands** are the door for one-shot async work: `Command.define(name, { args, messages, execute })`, where `execute` is an Effect returning one of the declared Messages. Constructing a Command never runs it. `interrupt: true` or `{ keyFields, toKey }` registers invocations in an interrupt registry so a later Interrupt Command can stop them; the docs are firm that a key is an address, not a lock, and that `[Interrupt, Next]` in one batch is a race because Commands in a batch run concurrently with no ordering guarantee. The docs also draw the line explicitly: work whose lifetime is derived from the Model belongs in a Subscription or ManagedResource, not in an interruptible Command.

**Mount** is the seam where view code hands a real DOM element to something that owns its own DOM. `Mount.define(name, ...results)(element => Effect<Message, never, Scope>)` for one-shot work; `Mount.defineStream(name, ...results)(element => Stream<Message>)` for a continuum of events, with `ResizeObserver`/`IntersectionObserver`/listener examples given directly in the docs. Two documented constraints matter:

- **Args are captured at mount, not refreshed across renders.** `OnMount` binds only snabbdom's `insert` and `destroy`; there is no `update` hook between. The docs advise naming args accordingly (`initialScroll`, not `currentScroll`).
- **Cleanup is asynchronous with respect to `destroy`**: the runtime forks `Fiber.interrupt` and returns, so finalizers run on a separate fiber after `destroy` completed. Idempotent DOM teardown is fine; ordering-sensitive work should happen synchronously inside `acquire`.

At least one result Message schema is *required* on every Mount, and the stated reason is observability: without a declared result there is no record in `update`, and DevTools, Scene, and time-travel replay lose their reference point. Fire-and-forget Mounts are told to declare a `Completed*` Message that `update` no-ops on.

**Ports** are the embedding boundary: `Runtime.embed(program)` returns an `EmbedHandle` whose `ports.<name>.send(value)` decodes against the Port's Schema (returning `Exit<void, SchemaError>`; on failure nothing reaches the app) and whose `ports.<name>.subscribe(listener)` receives encoded outbound values in registration order. `dispose` is idempotent and tears down Subscriptions, ManagedResources, Mounts, listeners, and in-flight Commands, leaving the container empty and re-embeddable.

**What the docs site says the module is for.** https://foldkit.dev/core/canvas states the scene is a `ReadonlyArray<Shape>`, that Foldkit clears and repaints after VNode insertion and on each patch so there is no hidden state, and that identical shapes produce identical pixels — which is what lets DevTools time-travel work by re-rendering the Model. The named use cases are pixel art, board games, generative art, charts, and data visualization. The page pairs Canvas with `Subscription.animationFrame` for continuous animation and states that Foldkit batches patches to one per frame.

### 2.4 SSR, hydration, and what happens to canvas children

`Runtime.hydrate(program, { buildId })` adopts a server-rendered DOM instead of building fresh. The handoff is documented as strict, and the failure list is long: a missing server root, an empty or duplicated root stamp, more than one stamped root, a requested root outside the document body light DOM, a missing Flags payload, an undecodable payload, or **a page from another deployment** all terminate startup. `buildId` is compared against the id the server stamped *before* the Flags payload text is accessed or decoded — an anti-mismatch measure, not just a version check. `@foldkit/vite-plugin` fills `import.meta.env.FOLDKIT_BUILD_ID`.

On any of those failures the runtime *contains* the page rather than proceeding: the body is marked `inert` and a nondismissable modal shield is opened above existing top-layer content. The docs are candid that this is not a script/event/embedded-document sandbox — capture-phase handlers, timers, and stale scripts can still run.

Both `hydrate` and server rendering are marked **`@experimental`** in the shipped types: "Server rendering and hydration are experimental while their contracts settle."

The docs page (https://foldkit.dev/core/server-rendering) adds the framing that matters: `renderToString` runs the pure view over the Model returned by `init`, and it does **not** execute Commands, Subscriptions, or ManagedResources, because there is no DOM to attach to and no Message to dispatch. Data a Command would load appears as the Model's pre-Command state — usually a loading state. Elements requiring DOM measurement before rendering (the page names virtual lists) are called out as not server-renderable. Only `makeApplication` hydrates; `makeElement` and `embed` apps do not. The page's own sentence on this topic is direct: canvas, third-party mounts, and similar interactive elements must load their state through Commands or Subscriptions running after hydration. Server rendering ships from `foldkit/experimental/server` and the page says the API may change in any release, advising pinning the exact deployed version.

**Canvas under SSR.** A `<canvas>` element server-rendered by foldkit is markup only. The paint happens exclusively in the snabbdom `insert` and `postpatch` hooks, both of which are client-side DOM hooks that require a real `HTMLCanvasElement` and a `getContext('2d')` result — `view.js` returns early if `vnode.elm` is not an `HTMLCanvasElement` or the context is null. So the server emits an empty `<canvas width height>` and the first client paint happens when hydration patches that vnode. There is no server-side rasterisation path, and canvas content contributes nothing to server-rendered HTML — which also means it contributes nothing to search indexing or to the accessibility tree.

### 2.5 What the test renderers can and cannot see

Two renderers ship: `foldkit/story` (exercise `update` directly, resolving Commands inline) and `foldkit/scene` — which re-exports `../test/scene.js` — described as driving the real view the way a user does, with accessible locators, no browser required.

The decisive constraint is stated in the `MountTracker` docs: "Test renderers do not provide this service, since snabbdom hooks never fire in their VNode-only environment."

**The Scene renderer is VNode-only.** Snabbdom hooks do not fire. The canvas module is *entirely* implemented in snabbdom hooks. Therefore Scene can see that a `<canvas>` vnode exists with its `props.width`/`props.height` and class, and it can see the `shapes` array only insofar as that array is a value the test itself can reach — but **no paint ever happens, no 2D context is created, and no pixel is produced under Scene.** Pointer handlers registered in the vnode's `on` record are likewise not driven through a real `HTMLCanvasElement`, and `toCanvasPoint` requires `getBoundingClientRect` on a live element.

The docs say it outright. https://foldkit.dev/testing/scene states Scene operates on VNodes directly and needs no DOM, jsdom, or browser, and lists what it cannot verify: **canvas rendering**, DOM measurements, animation execution, and CSS computed styles beyond inline properties.

There is a second, sharper limit visible only in the types. Scene's interaction steps are `click`, `doubleClick`, `contextMenu`, `pointerDown`, `pointerUp`, `hover`, `focus`, `blur`, `focusEnter`, `focusLeave`, `type`, `change`, `changeFiles`, `dropFiles`, `submit`, `keydown`. **There is no `pointerMove` step and no `wheel` step.** So of the canvas module's three handlers, Scene could in principle reach `onPointerDown` and `onPointerUp` as vnode listeners, and cannot reach `onPointerMove` at all — and even for the two it can reach, `toCanvasPoint` needs `getBoundingClientRect` on a live `HTMLCanvasElement`, which a VNode tree does not have.

The testable surface therefore sits *above* the canvas module: `shapes` is a pure function of the Model, and `ReadonlyArray<Shape>` is schema-described data, so scene content is fully assertable as data in a `Story` test without any renderer at all. That is the module's real testing story, and it follows from the shape union being schemas rather than draw calls.

`Story.Command.resolve` / `Scene.Command.resolve` replay a Command's recorded message-mapping chain over a substitute result without running the Effect — which is why `Command.mapMessage`/`mapMessages` exist as distinct from `mapEffect`, and why the docs warn that wrapping a result Message via `mapEffect` "dispatches correctly in production but is invisible to `Story`/`Scene` `resolve`".

### 2.6 Other shipped surfaces relevant to a demanding canvas app

- **DevTools** (`devTools?: DevToolsConfig`) records a full Model snapshot per retained Message. `maxEntries` defaults to 100, clamped 20–500. `keyframeInterval` defaults to 31 — time-travel replays `update` forward from the nearest earlier keyframe. Critically for high-frequency canvas input, `excludeFromHistory` takes Message `_tag` values that should not be recorded, and the docs name the exact use case: animation frames, pointer moves, scroll events, which "would flood history without adding insight" and otherwise pay a per-Message diff cost. Note `keyframeInterval` is forced to 1 when `excludeFromHistory` is active.
- **`foldkit/render` exports `afterCommit` and `afterPaint`** — and these are the frame-synchronisation primitives a canvas app will want. `afterCommit` is an `Effect<void>` that completes after the runtime's next render commits; the docs state the reason explicitly, that the runtime batches renders to `requestAnimationFrame` so an Effect running immediately after a dirtying Message would otherwise query the DOM before the matching patch applied. `afterPaint` waits for the commit *and then one further animation frame*, so the prior state is actually on screen — the docs name CSS transition orchestration, where the from-state must be displayed before the to-state is applied or the browser collapses both into one frame. Internally these wait on a `RenderCommit` service rather than counting frames, precisely because a View Transition hands its patch to the browser's update callback at a time frame-counting would miss. Read via `Effect.serviceOption`, so outside a runtime they fall back to frame counting. The `Dom` helpers gate themselves with `afterCommit` already.
- **`freezeModel?: boolean`** — a `deepFreeze` module ships, so the Model can be frozen in development. Relevant because a canvas app is tempted to keep mutable typed arrays in the Model.
- **`Html.createLazy` / `createKeyedLazy`** are exported from `foldkit/html` — the vdom memoization primitive (README: "lazy memoization and keyed diffing, powered by Snabbdom"). This is the mechanism by which a subtree, including a canvas vnode, can be skipped during patch.
- **`preserveScroll`**, `preserveScheduler` (debounced Model encoding off the hot path, with a synchronous `flush` for `vite:beforeFullReload`), and HMR: the Vite plugin provides state-preserving hot replacement, and `foldkit/hmr-protocol` is a public export.
**The Vite plugin (`@foldkit/vite-plugin@0.19.0`) contract.** `foldkit(options?)` returns an *array* of Vite plugins (Vite flattens nested arrays, so `plugins: [foldkit()]` works). The set is: the view-identity branding transform and DevTools overlay injection in both dev and build, plus the HMR bridge with state preservation and an optional DevTools MCP relay in dev only. Options are exactly three — `devToolsMcpPort?: number` (starts a WebSocket server for an external MCP server; off by default), `ssr?: Omit<FoldkitSsrOptions, 'buildId'>` (serves SSR pages from the dev server via `renderPage` at `ssr.serverEntry`), and `buildId?: string` (compiled in as `import.meta.env.FOLDKIT_BUILD_ID`, defaulting to the env var of the same name; explicitly must not be a secret since it is published in the page). Also exported: `brandDistDirectory`, `foldkitSsr`, `foldkitViewIdentity`/`transformViewIdentity`.

The HMR state-preservation mechanism is visible in the core runtime: `foldkit/hmr-protocol` is a public export, `MakeRuntimeReturn.start` takes an optional `hmrModel?: unknown`, and `preserveScheduler` debounces `preserve(model)` encoding off the hot path — stashing the latest model and restarting a debounce timer so only one encode runs per quiet window, with a synchronous `flush` the runtime calls from `vite:beforeFullReload` via `Effect.runSync` so there is no race against Vite's `location.reload()`. **The practical consequence for a canvas app: the Model is Schema-encoded on a debounce for HMR, so Model size is a recurring dev-time cost, not just a memory one.**

Others worth knowing: `no-raw-dom-event-attributes`, `no-duplicate-onmount-per-element`, `mount-factory-must-use-element`, `keyed-required-for-mapped-rows`, `no-array-index-view-keys`, `no-disabling-dev-guardrails`, `no-hand-rolled-command-struct`, `no-spread-in-evo`, and the `Got*` submodel-envelope family.

### 2.7 Where the seams are

Reading only the types and the docs, the framework's own boundaries land in these places:

1. **Above `Canvas.view`, in the Model→shapes function.** The scene is a pure function of the Model and a schema-typed value. Everything a canvas app wants to do that the module does not do — culling, level of detail, layout, aggregation — is expressible as a function producing a smaller `ReadonlyArray<Shape>`. The module has no opinion here and no hook to interfere.
2. **`Html.createLazy` / `createKeyedLazy` around the canvas vnode** is the only shipped lever over *whether* `postpatch` fires — and the mechanism is documented precisely: on each render, if the function reference, dispatch, and all arguments are referentially equal (`===`) to the previous call, the cached VNode is returned, and "Snabbdom's `patchVnode` short-circuits when it sees the same VNode reference, so both VNode construction and subtree diffing are skipped." A short-circuited patch never reaches `postpatch`, so a memoized canvas vnode does not repaint. Since `paintScene` is unconditional *inside* `postpatch`, this is where repaint avoidance has to live. Two documented constraints: dispatch is part of the cache key (a VNode built under a different dispatch would misroute every event in the subtree), and a cached VNode must be rendered at exactly one position in the tree, because snabbdom tracks the real DOM through each VNode's mutable `.elm` field. `createKeyedLazy` entries are never evicted, so keys must be bounded.
3. **`Mount` / `Mount.defineStream` is the framework's own named door for "a third-party library owns this DOM element."** https://foldkit.dev/core/mount states the role separation as: the Model owns the input data, the library owns its rendered subtree, Foldkit owns the lifecycle — and names charts, editors, and maps as the case. A canvas that needs WebGL, `OffscreenCanvas`, a worker, a `ResizeObserver`, wheel/keyboard/pointer-capture events, or its own rAF loop is precisely that case. Four constraints from the page: `execute` must actually use the live element (if it does not, the real cause is a Message or Model condition); the work must be replay-safe because it reruns whenever the element is inserted again, so no network calls, storage writes, or analytics; **one Mount per element** — multiple mounts on the same element silently conflict and must be combined; and args are captured once at insertion.

   Decisively: **Mount is *beside* `Canvas.view`, not an extension of it.** `Canvas.view(config, h)` builds its own vnode with its own three hooks and accepts no attribute list, so there is no way to attach `OnMount` to the canvas the module creates. A Mount-owned canvas is a different element built with the ordinary `h.canvas(...)` builder.
4. **`Subscription.persistent` + a hand-written Effect `Stream`** is the door for a long-lived event source, and `keepAliveEquivalence` is the door for a stream that must survive per-frame Model churn.
5. **`Subscription.fromEventFilterMap` on `window`/`document`** is the door for every input event the canvas module does not expose — wheel, keyboard, pointer capture — with the `preventDefault()` timing guarantee that a downstream filter would lose.
6. **`excludeFromHistory`** is the door that keeps DevTools usable under pointer-move and rAF Message rates.
7. **`slow.onSlow` with `thresholdOverrides`** is the shipped frame-budget instrument, and it is per-phase, so Update, View, and Patch can be attributed separately.

8. **SVG is a fully-typed peer of the canvas module inside the same view.** `TagName` in `dist/html/index.d.ts` includes `canvas` *and* the entire SVG element vocabulary — `svg`, `g`, `path`, `rect`, `circle`, `ellipse`, `line`, `polygon`, `polyline`, `text`, `tspan`, `textPath`, `defs`, `use`, `symbol`, `marker`, `mask`, `clipPath`, `pattern`, `linearGradient`/`radialGradient`/`stop`, `foreignObject`, the whole `fe*` filter set, and the SMIL `animate`/`animateMotion`/`animateTransform` elements — plus the MathML set. Every one is an `ElementFunction<Message>` on the builder, so it gets the ordinary attribute list, the full event-handler surface, keyed diffing, and `createLazy` memoization. Anything drawn as SVG is therefore inside the vdom, hit-testable by the browser, in the accessibility tree, server-renderable, and **visible to Scene's locators** — none of which is true of the canvas module. `h.canvas(...)` is also available as a plain element for a Mount-owned canvas.

### 2.8 What foldkit's own examples do (the blessed patterns, from source)

The repo ships `canvas-art`, `charting`, `generative-art`, `map`, and `pixel-art` examples (https://github.com/foldkit/foldkit/tree/main/examples).

**`generative-art` is the canvas module's showcase** (https://raw.githubusercontent.com/foldkit/foldkit/main/examples/generative-art/src/view.ts). What it actually does, and it is instructive:

- `sceneShapes(model)` **rebuilds the entire shape array from scratch every frame**, allocating fresh `Canvas.Path` / `Canvas.Circle` / `Canvas.Rect` objects for every particle, every tick. No memoization, no `createLazy`, no caching of any kind.
- `Canvas.view` is called with fixed `CANVAS_WIDTH` / `CANVAS_HEIGHT` constants — **no DPR handling, no resize handling.**
- Frame driving is exactly `Subscription.animationFrame({ isActive: model => model.isRunning, toMessage: deltaTimeMs => TickedFrame({ deltaTimeMs }) })`, aggregated with the UI slider subscriptions via `Subscription.aggregate`.
- Pointer input is `onPointerDown` and `onPointerMove` mapping straight to `PressedCanvas({x, y})` / `MovedPointer({x, y})`.

Two workarounds in that file document the shape union's gaps better than any prose could. **The vignette is four nested rings of stacked semi-transparent `Rect` strips** (`VIGNETTE_STEPS = 4`, each at `VIGNETTE_ALPHA / 4`) because there are no gradients. **The "nebula glow" is a plain 280px-radius translucent `Circle`** because there is no blur and no radial gradient. Colour variety is achieved entirely through `hsla(...)` strings in the `fill`/`stroke` fields, which is what the `S.String` typing permits.

**`map` is the canonical "third-party renderer beside foldkit" recipe**, and it is worth reading as the template for any renderer foldkit does not own. From `main.ts` and `mapHost.ts`:

- `MountMap = Mount.define('MountMap', { args: { hostId }, messages: [SucceededMountMap, FailedMountMap], execute })`, attached in the view as `h.OnMount(MountMap({ hostId: HOST_ID }))` on a plain `div`.
- Inside, `Effect.acquireRelease` constructs the MapLibre `Map` in the acquire body and calls `removeMap(hostId)` in release.
- The live instance is stashed in a **module-level `Map<string, MapInstance>` keyed by host id**, and `mapHost.ts` states the reason in its own comment: so Subscriptions and Commands can reach it **without putting the mutable, unfreezable instance in the Model**, with cleanup paired in the Mount's release.
- Commands (`FlyTo`, `Geolocate`) then reach the instance via `getMap(hostId)` returning `Option`, and a Subscription reads it the same way.

That module-level side table keyed by an id, paired with Mount acquire/release, is foldkit's own answer to "where does a mutable renderer handle live." Note the tension worth flagging: `@foldkit/oxlint-plugin`'s `no-module-level-mutable-state` rule targets exactly this shape, and the framework's own canvas module uses a module-level `WeakMap` for its 2D contexts — so the pattern is sanctioned but the linter's scope around it is worth checking before adopting.

The honest summary of the canvas module's altitude: it is a **complete, correct, immediate-mode Canvas2D scene-description layer with a schema-typed shape union and no performance machinery whatsoever.** Its guarantees are purity and state isolation. Its silences are DPR, damage, culling, hit-testing, layering, images, text metrics, and every input event beyond three pointer callbacks.

## Part 1 — how production canvas rendering is actually done

### 1.1 Design and whiteboard tools

#### Figma — they left the browser's rendering model entirely

Figma wrote a tile-based WebGL renderer in C++, cross-compiled with Emscripten; TypeScript and React handle only the surrounding UI chrome. Evan Wallace's foundational post (https://www.figma.com/blog/building-a-professional-design-tool-on-the-web/) gives their reasons for rejecting each alternative, and they are specific:

- **HTML/SVG** — DOM access overhead makes it slower than Canvas2D; masking, blurring, and blend modes are inconsistent across browsers; text layout differs between browsers *and* between platforms on the same browser.
- **Canvas2D** — immediate mode means re-uploading geometry every frame, there is no guarantee of GPU acceleration, and features they needed were missing (angular gradients named).
- **The structural argument, which is the transferable one:** browser rendering APIs are optimized for scrolling, not zooming — geometry gets re-tessellated on every scale change. For an infinite canvas where zoom is the primary navigation gesture, that is the wrong optimization target.
- **Text** — CSS has sophisticated layout algorithms but exposes no way to customize them or read back the result. That read-back gap is why they wrote their own text engine.

**Their 60fps claim is a memory claim, not a GPU claim.** All C++ objects are reserved ranges inside a pre-allocated typed array, so the JavaScript garbage collector is never involved: no GC pauses, therefore no dropped frames. They also cite 32-bit floats over JS's 64-bit doubles, and asm.js reaching within roughly 2× of native.

**Numbers.** The WASM migration (https://www.figma.com/blog/webassembly-cut-figmas-load-time-by-3x/, June 2017) cut load time **3×** — app init plus file download plus first render, independent of document size — because WASM parses roughly **20× faster** than asm.js. Compressed download size was essentially a wash. The win was parse and compile time, not bytes. It shipped Firefox-only at publication due to Chrome caching bugs.

The renderer restructure (https://www.figma.com/blog/figma-faster/) is the best-numbered result in the whole survey: file load **29s → under 8s**; dragging **30fps → 60fps average**; and the number that actually describes the felt improvement, **worst-frame hitch 120ms → 30ms** — dropping one frame instead of six. Zooming holds 60fps average. Their method is real design files driven by simulated interactions in Electron, reporting to Datadog, and they track **both average and maximum frame time**.

Their performance discipline post (https://www.figma.com/blog/keeping-figma-fast/) adds: the perf suite must finish in **10 minutes** or it won't get used; a **20% pass margin** on cloud VMs absorbs virtualization noise while still catching complexity regressions; and they maintain a **hardware lab of real old machines** alongside cloud VMs. The cautionary tale there is an optimization that improved p50 frame rate but regressed p90 on specific machines — median-only measurement would have shipped it.

**WebGL → WebGPU (https://www.figma.com/blog/figma-rendering-powered-by-webgpu/, Sept 2025) bought them very little.** They built a shader processor to auto-translate existing WebGL 1 GLSL to WGSL rather than maintain two shader sets, and had to rebuild their API to batch and encode many draw calls before submitting, because WebGPU forces uniforms into one buffer. The published result is honest: improvement on some device classes, neutral on others, no regressions, and **no figures given**.

**Working-set reduction, which is culling at the document level rather than the pixel level:**
- Per-page dynamic loading via a read/write dependency graph (https://www.figma.com/blog/speeding-up-file-load-times-one-page-at-a-time/): **33% faster** for the slowest 5% of loads, **70% fewer nodes held in client memory**, **33% fewer OOM errors**, parallel decoding **>40% faster**, preloading saving **300–500ms** off p75. Files grew 18% year over year regardless.
- Memory layout in Rust (https://www.figma.com/blog/supporting-faster-file-load-times-with-memory-optimizations-in-rust/): replacing a `BTreeMap<u16, ptr>` with a flat sorted vector — around 60 keys on average — cut memory **25%** on large files and **20%** fleet-wide, with bit-stuffing field IDs into unused bits of 48-bit x86 pointers giving a further **5%**, and **20% faster deserialization at p99**. Their reasoning is worth carrying: linear scans over small contiguous memory beat asymptotically better tree structures at this size.
- Incremental frame loading for prototypes (https://www.figma.com/blog/incremental-frame-loading/) — no numbers published.

**The DOM-overlay lesson, which is the single most transferable trick here.** Figma's comment pins (https://www.figma.com/blog/improving-scrolling-comments-in-figma/ — verified first-hand by this lane) started at **15fps with 30 comment threads**, burning **68ms of JavaScript per frame**. Two fixes: first, pull viewport information out of the Redux store into a custom event emitter, so unrelated components — left panel, toolbar — stop re-rendering on every viewport tick, giving **50fps at 50 pins**; second, move per-pin position math from O(n) to O(1) by positioning the pins statically inside **one overlay container and repositioning that single container with a CSS translate**, giving **60fps regardless of count, tested to 150**. Their noted trade: recalculating boundary boxes when comments are added (rare) in exchange for cheap panning (constant).

Their layers panel (https://www.figma.com/blog/improving-performance-in-the-layers-panel/) uses windowing — roughly 20–30 visible rows rendered in files with tens of thousands of layers — for **30–50% faster** interactions, with a rope-like structure cutting memory by **up to 99%** versus their first prototype.

Incidental but relevant to any JS hot path: in their TypeScript migration post (https://www.figma.com/blog/figmas-journey-to-typescript-compiling-away-our-custom-programming-language/) they report that avoiding JS array destructuring gave **up to 25%** better per-frame latency, and that in 2020 TypeScript in Safari benchmarked around **2× slower** for prototype loads, which blocked the migration until WASM matured.

Attribution is confirmed at https://madebyevan.com/figma/ — Wallace co-authored the original WebGL renderer with Alec Miller, wrote a next-generation version covering curves, images, blurs, masking, blending and opacity groups, plus the initial text layout and editing, vector networks, and the `kiwi` binary serialization format. Their multiplayer post (https://www.figma.com/blog/how-figmas-multiplayer-technology-works/) is relevant only to *feel*: property changes apply locally immediately without awaiting server acknowledgement, and on conflict they show their best prediction of the eventual value rather than flickering. LiveGraph is a Postgres/GraphQL data-fetching layer and is **not** part of the rendering path.

#### tldraw — the deliberate DOM counterexample, and it is more subtle than advertised

tldraw renders shapes as DOM/HTML elements. Their README (https://raw.githubusercontent.com/tldraw/tldraw/main/README.md) states the position as a DOM canvas supporting anything the browser supports, naming embedded YouTube, Figma, and GitHub content. In Steve Ruiz's talk (https://gitnation.com/contents/whats-under-the-cursor), asked whether he regretted it, he calls it probably one of the better decisions he made with tldraw, justified by how trivial it becomes to put videos and iframes on the canvas.

**The trade is exactly inverted from Figma's.** Figma gave up the browser to get consistency and speed. tldraw keeps the browser to get live web content and React ergonomics, and pays for it with an engineered culling and indexing layer. Customers have swapped in WebGL renderers while keeping the geometry system — the renderer is a seam.

**They do not use browser hit testing.** This is the most important structural finding for anyone tempted to copy the DOM approach. They abandoned DOM hit testing — hidden SVG paths behind shapes absorbing browser hit tests — because overlapping shapes and z-order broke it. The current system sets `pointer-events: none` across the whole canvas and runs a two-phase geometric test: **broad phase** on bounding boxes, **narrow phase** distance-to-polyline/polygon. So they render in the DOM but do not *interact* through it. The selection rules encoded there are themselves a quality spec: hollow shapes let the pointer pass through, filled shapes stop it, labels beat edges, frames clip and block selection behind them, ties break on z-index.

**Techniques** (https://tldraw.dev/sdk-features/performance):
- **Culling via a spatial index**, applied as `display: none` on off-screen shapes. Their worked example: **10,000 shapes on a page, roughly 50 actually rendered.**
- **Reactive signals rather than React state**, so a shape prop change re-renders only that shape.
- **Debounced zoom**: `getEfficientZoomLevel()` returns a stable value during camera movement once the document exceeds **500 shapes**. They deliberately stop re-resolving level of detail mid-gesture.
- **Level of detail**: image resolution scales with on-screen size; built-in shapes simplify at low zoom, hiding shadows and flattening patterns to solid. Text shadow LOD threshold defaults to **0.35 zoom**.
- **Geometry caching** for bounds, hit tests, and outlines, invalidated on prop change.
- Max shapes per page defaults to **4000**, configurable.

**Source confirms the architecture** (https://raw.githubusercontent.com/tldraw/tldraw/main/packages/editor/src/lib/components/default-components/DefaultCanvas.tsx): the layer stack is a `.tl-canvas` root, an `svg.tl-svg-context` holding shared defs collected from every shape util's `getCanvasSvgDefs()`, a background, a `.tl-html-layer.tl-shapes` **carrying the camera transform**, then overlays, collaborators, and menu capture. One camera transform applied to the whole HTML layer — the same O(1) trick Figma used for comment pins. There is also a `MovingCameraHitTestBlocker` div that disables hit testing while the camera moves. Culling is centralized in a single reactor, and the source comment gives the reason: **O(1) instead of O(N) subscriptions**. Naive per-shape reactivity is O(N) subscription churn per camera tick, and they hit it.

Per-shape rendering (https://raw.githubusercontent.com/tldraw/tldraw/main/packages/editor/src/lib/components/Shape.tsx) positions each container with `Mat.toCssString()`, applies opacity and z-index in `useLayoutEffect`, floors width and height at 1px, and wraps `InnerShape`/`InnerShapeBackground` in `memo` with a custom `areShapesContentEqual()` comparator — the stated rationale being that rendering a shape's interior costs more than positioning or recoloring it.

**Published numbers, and the twist:**
- SDK 4.4 (https://tldraw.dev/blog/tldraw-sdk-4.4) added an **R-tree spatial index** so brush select, scribble select and erase stay fast in rooms with thousands of shapes; and moved **shape indicators from SVG to 2D canvas for up to 25× faster** select/hover of many shapes.
- SDK 5.0 (https://tldraw.dev/blog/tldraw-sdk-5-0) moved indicators, handles and other **ephemeral overlays out of individual React SVGs into a single HTML canvas**, with an Overlays Utils system paralleling Shape Utils, plus new spatial indexing and optimized math hot paths. No figures.
- SDK 5.2 (https://tldraw.dev/blog/tldraw-sdk-5.2) rewrote freehand ink: **roughly 2× faster to compute, up to 3× on long strokes, 57% smaller SVG path data**, with no visual change. Method: derive each point's direction from its neighbours instead of storing a vector per point, and compute radius and taper in the same pass that builds the outline.

**The twist matters more than the headline.** tldraw is not a static counterexample — they are **moving overlays to canvas while keeping shapes in the DOM**. Ephemeral, high-churn, non-interactive chrome goes to 2D canvas; persistent, interactive, arbitrary content stays in the DOM. That split is the actual finding, not "tldraw is DOM". An open issue to finish the conversion exists at https://github.com/tldraw/tldraw/issues/8314 — title surfaced in search, contents UNVERIFIED, not fetched.

**How they make it feel good** — three posts that are essentially craft specs:
- The eraser (https://tldraw.dev/blog/erasing) is tested as a **line segment, not a point**, explicitly to prevent tunneling — shapes surviving between sparse pointer samples on a fast drag. Hit margin converts from screen pixels to page space by dividing by zoom, so the eraser feels the same physical size at any zoom. Shapes render semi-transparent while marked, nothing deletes until pointer-up, and Escape mid-drag snaps everything back to full opacity.
- Hand-drawn character (https://tldraw.dev/blog/engineering-imperfection-with-draw-shapes) comes from a **seeded PRNG keyed on the shape's ID**, not `Math.random()`, so wobble is stable across re-renders instead of re-rolling every frame. Strokes are drawn twice by default with slightly different offsets for ink texture. Corners are softened with quadratic béziers, rounding scaled by corner angle — 90° gets full rounding, 180° almost none.
- Comments (https://tldraw.dev/blog/a-comment-is-not-a-shape) are a parallel record type in the sync engine rather than shapes, because shapes carry "anyone can move anything" permissions and comments need author-only edit.

#### Excalidraw — Canvas2D + roughjs, dual-canvas, aggressive bitmap caching

**Excalidraw publishes no rendering-architecture blog post.** `blog.excalidraw.com` redirects to https://plus.excalidraw.com/blog, whose index covers elbow arrows, SOC 2, year-in-review, CJK hand-drawn fonts, a component API redesign and Project Fugu — nothing on the renderer. Everything below is read from source.

**The dual-canvas split.** `interactiveScene.ts` (https://raw.githubusercontent.com/excalidraw/excalidraw/master/packages/excalidraw/renderer/interactiveScene.ts) states in a code comment that the interactive scene is the UI canvas for bounding boxes, selections and other UI. It carries selection borders, transform and rotation handles, linear-element point and midpoint handles, arrow binding focus points and dashed connectors, crop handles, text bounding boxes, binding/frame/group highlights, remote collaborator cursors, scrollbars, search match highlights, and snap guides. `staticScene.ts` carries the actual elements drawn through roughjs, with `context.scale(zoom, zoom)`, frame clipping, `visibleElements` already filtered upstream, and rAF throttling via `throttleRAF()`.

**Why the split works: the two canvases have wildly different update frequencies.** Selection and hover chrome changes on every pointer move; the drawing changes only on edit. Invalidation is keyed on two separate nonces — a **scene nonce** (element mutation invalidates static) and a **selection nonce** (selection change invalidates interactive only). `Renderer.getRenderableElements()` is memoized on a composite key of viewport parameters plus scene nonce.

**Per-element bitmap caching is the real performance story** (https://raw.githubusercontent.com/excalidraw/excalidraw/master/packages/element/src/renderElement.ts). Each element is rasterized to **its own offscreen canvas**, held in a `WeakMap<ExcalidrawElement, ExcalidrawElementWithCanvas>` so deleted elements are collected automatically. Regeneration triggers only on: zoom changed *and* `!appState.shouldCacheIgnoreZoom`; theme changed; image crop changed; containing-frame opacity changed.

That `shouldCacheIgnoreZoom` flag is the notable one: **during an active zoom gesture they deliberately reuse stale, wrong-resolution cached bitmaps**, re-rasterizing only when the gesture settles. It is the Canvas2D equivalent of tldraw's debounced zoom — smoothness bought with temporary softness.

Cache tiles get per-type padding via `getCanvasPadding()` — freedraw `strokeWidth * 12`, text `fontSize / 2`, arrow `40` with arrowheads else `20`, default `20` — bleed room so roughjs's wobble and arrowheads are not clipped. Roughjs *geometry* is cached separately from the pixels via `ShapeCache.generateElementShape()`, so there are two cache tiers: shape geometry and element bitmap. Link icons get their own cache, invalidated on zoom, sized `width * devicePixelRatio * zoom`.

**Crispness.** `StaticCanvas.tsx` does the standard split between CSS size (`style.width = appState.width + "px"`) and backing store (`canvas.width = appState.width * props.scale`), with `scale` carrying DPR. The React component is memoized with a hand-written `areEqual` keyed on `canvasNonce`, `scale`, `elementsMap` and selected appState fields. Grid crispness has a specific rule in `staticScene.ts`: **1px lines are snapped only at 100% zoom**, with the code explaining that at other zooms the offset is fractional. That is honest sub-pixel handling — they do not pretend to snap at arbitrary zoom.

**Why Canvas2D was enough is INFERRED, not stated — UNVERIFIED.** No Excalidraw statement justifying Canvas2D over WebGL was found. What the code shows is a different workload from Figma's: sketch-style strokes, no blend modes, no nested opacity groups, no blur, modest element counts — and the caching scheme absorbs it. Decisively, **roughjs is a Canvas2D/SVG library**, so Canvas2D came with the aesthetic rather than the other way round.

**Excalidraw publishes essentially no numbers.** The only figures found are in https://github.com/excalidraw/excalidraw/issues/10063, and the provenance disqualifies them as Excalidraw's position: filed by an outside contributor with no maintainer response on the page. Its claims — redundant throttled render work, O(n) `isElementInViewport` per element, contending rAF loops, a projected "30–50% improvement" at 1000+ elements — are **an outside proposal, not Excalidraw's own measurement.**

### 1.2 Documents and grids at scale

#### Google Docs' 2021 move to canvas — and the accessibility bill that came with it

**The official announcement** (https://workspaceupdates.googleblog.com/2021/05/Google-Docs-Canvas-Based-Rendering-Update.html, 2021-05-11) is remarkably thin. Google migrated Docs document rendering from HTML/DOM to `<canvas>`, rolled out over several months. **Their entire stated reason** is to improve performance and improve consistency in how content appears across different platforms. They warn that some Chrome extensions may stop working and direct integrators to the Workspace Add-ons framework. They assert that compatibility with supported assistive technologies — screen readers, braille devices, screen magnification — will not be impacted, **describing no mechanism**. And they publish **zero performance figures**.

**The only on-record Google explanation of the accessibility mechanism** comes from a Google I/O 2021 AMA, reported by Richard MacManus (https://thenewstack.io/google-docs-switches-to-canvas-rendering-sidelining-the-dom/, read via the Wayback capture at http://web.archive.org/web/20251128164511/... since the live URL is behind a signup wall). Dion Almaer, then Director of Web Developer Ecosystem, recounted Bespin — the 2009 Mozilla canvas code editor he built with Ben Galbraith — which used a **side DOM** to handle accessibility, and confirmed Docs took the same approach with a great deal of work behind it. MacManus clarified afterwards that this means **a hidden DOM the user never sees, existing purely for accessibility**. Almaer also named the W3C **Accessibility Object Model** and said screen reader support works by using **ARIA live regions as a text-to-speech engine** — explicitly not what they were invented for. Paul Kinlan's framing: choosing canvas puts pressure on browser engineers to improve the DOM.

**WebAIM tested it and disagreed with Google's reassurance** (https://webaim.org/blog/seismic-change-to-docs/, 2021-08-19): on the canvas-based demo they found only rudimentary assistive-technology support, and characterized Google's accessibility statement — which came only after community backlash — as content-free. Their broader worry is imitation: Google's example carries weight and others will copy it without the a11y plan.

**The concrete mechanism, from working extension source.** This is the most valuable primary evidence in this section, because it shows what actually shipped rather than what was promised. An extension opts into "annotated canvas" mode by injecting a page script that sets a global keyed to its own extension id — `window['_docs_annotate_canvas_by_ext'] = '<chrome.runtime.id>'` (https://raw.githubusercontent.com/melink14/rikaikun/main/extension/docs-annotate-canvas.ts, and the PR at https://github.com/melink14/rikaikun/pull/865.diff, which also *deletes* the older `_docs_force_html_by_ext` escape hatch that forced Docs back to HTML). What annotated mode produces, per the consuming code:

- Canvas tiles are detected by the class `.kix-canvas-tile-content`.
- Over each tile sits an **SVG overlay**: `<svg>` → `<g>` groups → `<rect>` elements, **one per text run**.
- Each `<rect>` carries the run's text in **`ariaLabel`**, plus a **`data-font-css`** attribute with the font shorthand. The extension reconstructs running text by walking sibling and cousin `rect` nodes and concatenating their `aria-label`s.

So the shipped "side DOM" is **an invisible, geometry-aligned SVG rect layer carrying the text as aria-labels** — not fallback content inside `<canvas>`, and not AOM. Access to it is gated behind an undocumented allowlist form; a chromium-extensions thread (https://groups.google.com/a/chromium.org/g/chromium-extensions/c/dLnxATEOcqg) has developers reporting that competitors have access and that feedback submissions went unanswered, **with no Google engineer participating**.

**The best technical rationale is ex-employee reasoning, not a Google statement.** Steve Newman, one of the three original Writely authors, who left Google in 2010 and had no involvement in the canvas project, argued on HN (https://news.ycombinator.com/item?id=27133929) that word processors need layout, rendering and incremental-update primitives the DOM does not expose — naming selection highlighting in mixed LTR/RTL text, and wanting to "cheat" reflow to update only the line containing the insertion point. His analogy: browsers are CISC, and if your use case does not fit the instruction set you drop to something lower-level. **No Google or Docs engineer commented in that thread.** Notably, VS Code's Daniel Imms did, stating the VS Code editor is DOM-based apart from the minimap and that a canvas rewrite would be a large undertaking once accessibility, backwards compatibility and Monaco extensibility are counted.

**Chrome is now building the fix for the problem Google Docs created.** https://developer.chrome.com/blog/html-in-canvas-origin-trial states the problem directly: browser features integrated into the DOM break completely when the UI is trapped inside a static canvas pixel grid — naming text selection, copy/paste, right-click context menus, find-in-page, and screen reader support — and notes that without native form controls apps rebuild UI logic and inflate bundle size. The API: a `layoutsubtree` attribute makes the browser aware of DOM content nested inside the `<canvas>`, lays it out, and **exposes it to the accessibility tree**, with drawing entry points `drawElementImage()` (2D), `texElementImage2D()` (WebGL) and `copyElementImageToTexture()` (WebGPU), returning transform values that sync the DOM location with the drawn location so hit testing lines up. **Google Docs, Miro and Figma are named by name as the motivating cases.** Status: origin trial in **Chrome 148 through 150**.

**MDN's guidance is blunter** (https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/canvas): canvas is a bitmap that exposes nothing about drawn objects, and its content is not surfaced to accessibility tools the way semantic HTML is — so you should avoid using canvas in an accessible website or app. The recommended mitigation is fallback content inside the `<canvas>` element, which also serves no-JS and legacy browsers.

The New Stack article asserts it, attributing it to a Young Coder post that is Medium-hosted and returns Cloudflare 403 to both fetch and curl — so that link in the chain is unverifiable. No published numbers, no accessibility story.

That is a product feature, not a rendering-architecture statement.

#### Glide Data Grid — the best-documented open-source canvas grid

**Their stated reason for canvas** (README FAQ, https://docs.grid.glideapps.com/faq): they originally virtualized in both axes with react-virtualized and hit a scrolling-performance wall — once you load and unload hundreds of DOM elements per frame, nothing saves you. They tried timers and a "low fidelity" mode rendering one element per cell; that broke down again at hundreds of visible cells.

**Published numbers** (https://grid.glideapps.com/, README, https://github.com/glideapps/glide-data-grid/releases/tag/v6.0.0, 2024-01-13): scales to **millions of rows** with cells rendered lazily; handles **hundreds of thousands of updates per second** (their marketing phrasing — note it says *updates*, not cells); **damage rendering is 2× faster than the 5.0 series**, achieved by reducing clipping during a damage pass; and Safari renders **2 to 5 times faster on mobile** in 6.0. No fps figures.

**Damage rendering** (`packages/core/src/internal/data-grid/render/data-grid-render.ts`): a damage pass draws **directly to the target context to avoid large blits**. `damage` is a `CellSet`, tested via `damage.hasItemInRegion([...])` against a list of rectangles — main viewport, header band, frozen columns, frozen trailing rows — and the pass is skipped entirely if nothing damaged is on screen. Header damage is handled separately via `clipHeaderDamage`, building a clip path only over damaged header columns.

**Their per-cell clipping strategy is the most interesting single detail** (`data-grid-render.cells.ts`): they clip **each cell individually rather than forming one super clip region**, with the stated reason that passing too many clip regions to the GPU at once causes a performance hit, while per-cell clipping lets them damage a large number of cells at once without issue. Then the further optimization — **not clipping at all is better still** — so they only take the `save`/`clip`/`restore` path when the cell is the leftmost column or overlaps the bottom freeze area. During damage they repurpose the cell's fill to wipe previous contents, avoiding an extra draw call.

There is a long in-source comment explaining that the obvious `damage.some(...)` closures were replaced with a reused `[number, number]` tuple and index `for` loops, because **allocation in the tightest part of the draw loop had a measurable impact** — their smoke test being to scroll to the bottom, scroll back up while profiling, and count major GC collections. That is the same GC-pressure lesson Figma states from the other end.

**Public damage API**: `dataGridRef.current.updateCells([{ cell: [10, 10] }, { cell: [11, 10] }])`. The docs state that rerendering a single cell is significantly faster than invalidating `getCellContent`, since the latter forces all cells to redraw. Internally it wraps the cells into a `CellSet` and does one synchronous draw with `damageRegion` set, then clears it. The animation queue and image loader feed the same callback.

**Scroll blitting** (`data-grid-render.blit.ts`): `blitLastFrame` copies the previous frame's canvas by the scroll delta and returns the uncovered regions to be repainted, with `imageSmoothingEnabled = false`. A `renderStrategy` of `"single-buffer" | "double-buffer" | "direct"` defaults to **double-buffer on Safari and single-buffer elsewhere**.

**DPR handling**, and this one is genuinely instructive:
```
const dpr = Math.min(maxScaleFactor, Math.ceil(window.devicePixelRatio ?? 1));
const maxDPR = enableFirefoxRescaling && scrolling ? 1 : enableSafariRescaling && scrolling ? 2 : 5;
```
Under experimental flags they **deliberately drop resolution while scrolling** — to 1× on Firefox, 2× on Safari — and restore up to 5× when idle. Same family as tldraw's debounced zoom and Excalidraw's `shouldCacheIgnoreZoom`: **transient softness bought for motion smoothness**, now applied to DPR itself.

**Text measurement caching** (`data-grid-lib.ts`): a module-level `metricsCache` keyed `` `${s}_${font}_${baseline}` ``, **flushed wholesale when it exceeds 10,000 entries**, and also cleared once `document.fonts.ready` resolves so metrics taken against fallback fonts do not stick. A separate `biasCache` memoizes middle-center baseline bias per font, measured off the magic string `"ABCi09jgqpy"`. Wrapping is delegated to `canvas-hypertxt`.

**Overlay editors are real DOM on top of canvas**: the editor is `createPortal`'d into a `#portal` element (the grid throws an explicit error telling you to add `<div id="portal" />` as the last child of `<body>`), positioned absolutely at the cell's computed rect with `min-width`/`min-height` equal to the cell, `width: max-content`, `max-width: 400px`.

**Accessibility is the same trick Google used**: a parallel hidden `<table role="grid">` with `aria-rowcount`, `aria-colcount`, `aria-multiselectable`, per-row `role="row"` and `aria-rowindex`, per-cell `aria-colindex`/`aria-selected`/`aria-readonly` — built in a **debounced memo** covering only the currently visible columns and `accessibilityHeight` rows, with focus pushed out of the grid if the selected cell scrolls out of the rendered window, and a `experimental.disableAccessibilityTree` switch. Their own honest caveat in the README FAQ is that screen readers are supported but no primary developer is an accessibility user, so there are likely unknown flaws.

### 1.3 Trace and profiler viewers — the closest domain to a growing event log

This is the most directly transferable section in the report, so it is the most detailed.

#### Perfetto UI

**The floating canvas — their virtual-scrolling mechanism** (https://raw.githubusercontent.com/google/perfetto/main/ui/src/base/virtual_canvas.ts). `VirtualCanvas` turns a potentially enormous HTML element into a virtual drawing surface by floating **one small real `<canvas>` over the scroll container's viewport**. Three rects are tracked: `_canvasRect` (where the real canvas sits), `_viewportRect`, and `_viewportLimits`. `getCanvasRect(viewport)` returns the existing canvas rect **unchanged** if `_viewportLimits.contains(viewport)` — no move, no resize, no repaint; otherwise it expands the viewport by `overdrawPx` on the scrolled axes and resets `_viewportLimits` to the viewport expanded by `overdrawPx - tolerancePx`. `updateCanvas()` then diffs: a width/height/DPR change resizes and fires a resize listener; a **position change sets `canvas.style.transform = translate(left, top)` and nothing else.** Driven by a `{passive: true}` scroll listener plus a `ResizeObserver`.

Their stated reason, from the file header: canvas maximum size is system-determined and can be as small as **4096×4096px**, and most of a large canvas is off-screen anyway — so they approximate a huge canvas using a much smaller one.

**Numbers**: `VirtualCanvas` defaults are `overdrawPx = 200`, `tolerancePx = 100`. The widget the timeline actually uses (https://raw.githubusercontent.com/google/perfetto/main/ui/src/widgets/virtual_overlay_canvas.ts) passes `CANVAS_OVERDRAW_PX = 300`, `CANVAS_TOLERANCE_PX = 100`. **So the invariant is: canvas = viewport + 300px on scrolled axes; it moves only once the viewport has drifted 200px from its last anchor, leaving 100px of drawn margin as the safety buffer against seeing blank canvas mid-scroll.** `VirtualOverlayCanvas` optionally creates a *second* canvas for WebGL, inserted **before** the 2D canvas so GL renders underneath, with `pointerEvents: none`.

**Virtual scrolling of tracks** (`ui/src/core_plugins/dev.perfetto.Timeline/track_tree_view.ts`): a track is drawn full-fat only if the **canvas rect** — viewport plus overdraw, not the viewport itself — overlaps its vertical bounds; otherwise `renderDOM({lite: true})`. The redraw callback only calls `m.redraw()` when the canvas rect has *moved*, and it passes `disableCanvasRedrawOnMithrilUpdates: true`, registering `redrawCanvas` with the global RAF scheduler instead — **deliberately decoupling DOM diffing from canvas painting to avoid double redraws.**

**Quantization and LOD live in the database, not the renderer.** `__intrinsic_slice_mipmap` (https://raw.githubusercontent.com/google/perfetto/main/src/trace_processor/plugins/slice_mipmap_operator/slice_mipmap_operator.h) is a SQLite virtual-table module whose header states the equivalent query: per `(depth, ts / $window_resolution)` bucket, keep `max(dur)`. It does not run that as SQL — it uses an `ImplicitSegmentForest<Slice, Agg>` per depth with a max-by-duration monoid that **also sums `count`**, claiming O(log n) per query. Result columns: `timestamp, dur, count, id, depth`. **The `count` is what lets the UI show "N slices collapsed here" rather than silently lying about a single slice** — the honesty mechanism in an LOD scheme.

The bucket size comes from `calculateResolution(timeSpan, widthPx)` (`ui/src/base/resolution.ts`): `timePerPixel = dur / widthPx`, returned as `BigintMath.bitFloor(...)` — **rounded down to the nearest power of two.** That is the cache-stability trick: resolution changes only at octave boundaries, so panning at fixed zoom reuses the same query key. The benchmark sweeps resolution steps of **4194304, 1048576, 262144 and 2048 ns**.

**Incremental data arriving into an already-rendered view** — the part most directly analogous to a growing log (`ui/src/components/tracks/buffered_bounds.ts`). `BufferedBounds.update(visibleSpan, resolution)` refetches only when the visible span escapes the loaded span or the resolution changed; on refetch it **pads each side by the full visible duration, so the total window is 3× the visible width**; and it quantizes bounds with `quantFloor`/`quantCeil`, with the in-source comment giving the reason: quantizing keeps the **cache key** consistent.

Rendering never blocks on the query. `render()` draws whatever data frame it has, then calls `checkerboardExcept(...)` to paint a diagonal-hatch "Loading..." region over everything outside the loaded span (`ui/src/components/checkerboard.ts`, which measures the label once into a module-level `LOADING_TEXT_WIDTH` and skips it if it does not fit). **Stale frame stays on screen, unloaded regions are honestly marked, new data swaps in on a later frame.**

**Hit testing is arithmetic, not colour picking.** `findSlice({x, y, timescale})` walks depths comparing `y` against row layout to get the depth, then scans that depth's slices in the current data frame. `onMouseMove` uses a `hoverMonitor.ifStateChanged()` guard so a redraw is scheduled only when the hovered slice actually changes. No readback, no spatial index — the mipmap already bounds the frame to roughly one slice per pixel per depth, so a linear scan is cheap **by construction**.

**Text**: `SLICE_MIN_WIDTH_FOR_TEXT_PX = 5`; narrower slices skip text entirely, as does text on collapsed rows below depth 0. Labels are **collected into a `textLabels` array during the rect pass and drawn in a second loop after the slices**, so `ctx.font` is set once per label class rather than per slice. `cropText` truncates against a precomputed character width instead of calling `measureText` per slice, and label x is centred on the *clamped* viewport-intersected rect so labels on partially-scrolled slices stay visible.

**Frame scheduling** (`ui/src/core/raf_scheduler.ts`): `RafScheduler` monkey-patches `m.redraw`/`m.mount` and maintains three ordered callback sets — `animationCallbacks` (pan/zoom at 60fps), `canvasRedrawCallbacks`, `postRedrawCallbacks` — guaranteeing redraw callbacks run after all action callbacks each frame. `perfStats` tracks `rafActions, rafCanvas, rafDom, rafTotal, domRedraw` via `performance.now()` deltas.

**The plugin contract** (`ui/src/public/track.ts`): `TrackRenderContext = {visibleWindow, size, resolution, ctx, timescale, colors, renderer}`, where `resolution` is documented as time units per pixel rounded down to the nearest power of 2, minimum 1, and a track may ignore it and compute its own. `TrackRenderer.render(ctx)` is documented as called **synchronously every render cycle**, so all async work must be memoized behind slots.

**Scale**: https://perfetto.dev/docs/visualization/large-traces gives a browser total-runtime-memory ceiling of **2GB typical**, runtime inflation of **2–4× over binary trace size** for uncompressed proto traces, and a native `trace_processor` RPC server on ports 9001/9002/9003 as the escape from WASM. The CHANGELOG **v55.0 (2026-04-29)** records two adjacent UI entries: WebGL rendering for GPU-accelerated slice and counter tracks with significant improvements on large traces, and virtual track scrolling rendering only visible tracks. (A widely-quoted "hundreds of processes, thousands of tracks, millions of slices" phrasing attributed to v55.1 release notes **could not be found in the fetched CHANGELOG — UNVERIFIED.**)

#### speedscope

**Published numbers** (https://jamie-wong.com/post/speedscope/): total compressed download **131KB**, of which **63KB** is needed before the page is usefully interactive, loading in **just under 2.5s over Fast 3G**; **60fps** interactive exploration; handles **100MB+ profiles exported from Chrome**. The post states speedscope moved *off* regl to a hand-rolled WebGL abstraction **because regl uses `eval`, which breaks under a strict Content-Security-Policy** — a deployment constraint driving a rendering-stack decision, which is a genuinely unusual and worth-knowing reason.

**The row atlas is a GPU-side LOD cache** (`src/gl/row-atlas.ts`): a single **4096×4096** `NEAREST_CLAMP` texture with a render target over it, where each texture *row* (1px tall, 4096px wide) is one cached pre-rendered strip, backed by `new LRUCache(texture.height)` — **4096 cache slots**. `writeToAtlasIfNeeded` renders missing rows inside one pass; `renderViaAtlas` blits a cached row. It registers a `gl.addContextResetHandler` that clears the CPU-side cache, because all cached data lives GPU-side with no client copy.

**Zoom-level selection is a dyadic tiling** (`src/gl/flamechart-renderer.ts`): the cache key is `{stackDepth, zoomLevel, index}`, with entry width `totalWeight / 2^zoomLevel` at offset `width * index`. The render loop starts at `zoomLevel = 0` and increments while the physical width of one atlas entry is at least the atlas resolution (4096) — the stated goal being to render the lowest resolution that still guarantees the atlas line is higher resolution than its destination rect. Frames are packed per stack depth into `RectangleBatch`es capped at `MAX_BATCH_SIZE = 10000`, wrapped in range-tree leaf nodes culled by rect intersection.

**Colour-encoded identity — and an important correction to the common assumption.** Each rect's vertex colour encodes identity: red = index within row, green = row, blue = colour bucket, each `+1` so 0 stays reserved for background. But this is consumed **by a shader for edge detection, not read back to the CPU for hit testing**: the fragment shader samples the identity texture at the fragment plus its four neighbours and declares an edge where the row differs, drawing transparent there, checking *both* sides deliberately so a 1px-wide rectangle is not rendered as pure outline and vanish. A grep of `graphics.ts`, `canvas-context.ts`, `flamechart-view.tsx` and `flamechart-color-pass-renderer.ts` for `readPixels` found **zero hits**.

**Actual hit testing is math with early exit** (`src/views/flamechart-pan-zoom-view.tsx`): transform logical → physical → config space via the inverse affine transform, then recurse the flamechart tree bailing immediately when the mouse x is outside a frame's config-space bounds.

**Text lives on a separate 2D overlay canvas above the WebGL canvas.** `minWidthToRender = cachedMeasureTextWidth(ctx, 'M' + ELLIPSIS + 'M')` — the threshold is literally one char, an ellipsis, and one char — converted to config space, below which rendering returns early. Elision is **middle**, via `trimTextMid`, with `remapRangesToTrimmedText` so search-match ranges survive the trim. `LABEL_PADDING_PX = 5 * devicePixelRatio`, and the overlay canvas is sized at `width * devicePixelRatio` with an in-source comment stating the render-high-then-scale approach exists so text renders crisply at 1:1 device pixels. Six batches accumulate per overlay pass via `BatchCanvasTextRenderer`/`BatchCanvasRectRenderer` (`src/lib/canvas-2d-batch-renderers.ts`), whose header comment gives the reason: building several batches simultaneously lets you **decide paint order at the end**, with `fillStyle` set once per batch.

**Pan/zoom smoothness has a documented interaction lock**: inertial scrolling keeps delivering wheel events after the user releases Cmd, which would flip a zoom gesture into a pan mid-flight — so an `interactionLock: 'pan' | 'zoom' | null` is held until **two consecutive frames with no wheel events**.

#### Chrome DevTools Performance panel

**The canvas model is the opposite choice from Perfetto's**, and the contrast is instructive (`front_end/ui/legacy/components/perf_ui/FlameChart.ts`, 4646 lines, and `ChartViewport.ts`). `resetCanvas()` sets the canvas to **exactly the viewport size** times DPR, every draw. Vertical scrolling is a **genuine DOM scrollbar**: `ChartViewport` owns `vScrollElement`/`vScrollContent`, and `draw()` applies `context.translate(0, -top)`. No oversized canvas, no repositioning, full repaint per frame — **the entire cost control lives in what gets submitted.**

`getDrawBatches` stacks six techniques in one loop:
1. **Row culling** — skip a level outside `[top, top + offsetHeight]`, with an in-source comment explaining why comparing the offset alone would pop the level out the instant it went 1px off the top.
2. **Binary search to the right edge** via `lowerBound(levelIndexes, windowRightTime())`, exploiting start-time ordering within a level.
3. **Iterate right-to-left with an early `break`** once the entry's right edge is left of the window.
4. **Pixel-collapse LOD, the key line**: `const barX = timeToPositionClipped(entryStartTime); if (barX >= lastDrawOffset) continue; lastDrawOffset = barX;`. Because iteration is right-to-left, this drops every entry landing in an already-occupied pixel column — **at most one event drawn per pixel column per level, regardless of how many events are there.** That is the hard ceiling making a 10M-event trace cost the same as a 10K-event one at full zoom-out.
5. **Colour batching** — entries bucket into a map keyed by `{color, outline}` with two interning maps, so `draw()` does one batch per distinct colour, minimising `fillStyle` churn.
6. **Text threshold** — `minTextWidth = 2 * textPadding + measureTextWidth(ctx, '…')`, converted to a **duration** via `pixelToTimeOffset`, so an entry only gets a title if its duration clears it. Titles are drawn in a single later pass.

Draw order: batched rects → custom symbols → markers → titles → decorations → group headers → flow events → marker lines → grid.

**Hit testing** is again arithmetic: `coordinatesToEntryIndex(x, y)` adds the scroll offset then linearly scans levels against `visibleLevelOffsets`/`visibleLevelHeights` — the in-source comment notes tracks are reorderable so the offsets are not monotonic, hence a scan rather than a division — then checks custom-drawn positions, marker positions, and regular entries.

**Frame-budget discipline** (`front_end/ui/components/render_coordinator/render_coordinator.ts`): `scheduleUpdate()` defers through `RenderCoordinator.write(...)`. The coordinator holds two queues and one `requestAnimationFrame`, draining readers together, awaiting them, then running all writers as a block — **read/write phase separation to prevent layout thrash**, with a `DEADLOCK_TIMEOUT = 1500` ms racing each phase and rejecting with a possible-deadlock message.

**A genuine gap worth recording: no published Chrome blog or doc describes the flame chart's rendering internals.** https://developer.chrome.com/blog/perf-tooling-2024 is about UX consolidation, and `docs/contributing/performance.md` is about a Crossbench benchmark of panel *load* times, not frame budgets. The source is the only primary record.

#### Firefox Profiler

**The shared chart abstraction** (`src/components/shared/chart/Canvas.tsx`): `ChartCanvas<Item>` is a generic canvas host parameterised by two injected functions — `drawCanvas(ctx, scale, hoverInfo)` and **`hitTest(x, y) => Item | null`** — with each chart (stack chart, flame graph, marker chart, js-tracer, network chart) supplying its own. Two details worth stealing: `ChartCanvasHoverInfo` carries `{hoveredItem, prevHoveredItem, isHoveredOnlyDifferent}`, so **the draw function is told that only the hover changed and can repaint just the two affected items**; and `MOUSE_CLICK_MAX_MOVEMENT_DELTA = 5` CSS pixels distinguishes a click from a viewport drag, with a comment explaining a real `click` event cannot be used because a long pan would then select an item.

**The viewport model** (`src/components/shared/chart/Viewport.tsx`) opens with a large ASCII diagram defining the coordinate system: `viewportLeft`/`viewportRight` are **unit intervals `[0,1]` of the current profile range** while `viewportTop` is in pixels. The unit-interval choice is significant — **zoom state is resolution-independent and survives container resize without recomputation.** `KEYBOARD_NAVIGATION_SPEED = 2000` px/sec, `MAX_KEYBOARD_DELTA = 500`, dual QWEASD/vim keymaps.

**Per-pixel accumulation in the activity graph** (`src/components/shared/thread/ActivityGraphFills.tsx`) is a different LOD shape from Perfetto's max-reduce: each `CategoryFill` owns two `Float32Array`s, `perPixelContribution` (0–100) and `accumulatedUpperEdge` (0–1), mutated in place. The run walks samples accumulating category contributions per pixel column, accumulates the upper edge, applies **`_applyGaussianBlur1D` with `BOX_BLUR_RADII = [3, 2, 2]`** — three successive box blurs approximating a Gaussian to smooth the graph — then accumulates the upper edge again. Picking converts y to a percentage and walks the stacked upper-edge arrays, then stacks candidate samples' contributions until it finds the one whose sub-range contains that percentage.

**The Firefox colour-picking-canvas claim is NOT supported by current source — UNVERIFIED / likely historical.** Greps of `ActivityGraphCanvas.tsx` and `ActivityGraph.tsx` for `getImageData`, `ImageData`, `pick` and `hidden` returned zero matches, and the picking path traced above is pure arithmetic over the same `Float32Array` edges used for drawing — strictly better than a readback, since it avoids a GPU sync stall and recovers the *sample* rather than just a colour. Only `main` was checked; git history was not searched.

Their architecture doc (`docs-developer/architecture.md`) covers only ingestion pathways and **contains no canvas, chart, memoization or perf content** — the useful record is in the source.

#### Tracy — the best primary source on *why* naive timeline rendering dies

https://wolf.nereid.pl/posts/how-tracy-faster/ (Tracy's author, 2023).

**The problem**: to decide what to draw, Tracy binary-searches its dataset — **for every column of a 4K screen**. Binary search hits memory at unpredictable addresses, so prefetching is useless and each step is a round trip to system memory rather than cache.

**The fix, and the surprise**: he separated the **search phase** from the **draw-submission phase** rather than interleaving them. Search now produces a draw list of minimal descriptors — **about 20 bytes per entry, typically under a thousand elements** — and submission happens afterwards. **He reports this separation was the main performance driver, largely independent of the parallelisation added alongside it**, because the two phases were competing for the same cache and memory resources.

**Numbers**: headline **30×**, individual traces **33×** and **22×**, one comparison **45×** (he notes that one used a different zoom level). Frame time **83.3ms (12 FPS) → 2.5ms (400 FPS)** on one trace; **47.6ms (21 FPS) → 2.17ms (460 FPS)** on another. `ZoneEvent` is packed to **22 bytes** where it would naturally be 32, and he states the stakes plainly: at a billion zones, one extra byte costs **1 GB**. Timestamps use **48 bits**, giving about **1.6 days** of continuous profiling; pointers are **6 bytes**, exploiting the 48-bit practical address space. Scale context: timelines with **hundreds of millions of zones**.

#### Jaeger UI — the DOM-virtualization counterexample in this domain

Worth including precisely because it is not canvas (`packages/jaeger-ui/src/components/TracePage/TraceTimelineViewer/ListView/index.tsx`). `DEFAULT_INITIAL_DRAW = 300` items. **Two separate buffer knobs, documented in-source**: `viewBuffer` (extra items rendered above and below when a new range is drawn) and `viewBufferMin` (the minimum offscreen items required before a re-render is triggered at all) — exactly Perfetto's overdraw/tolerance pair in a different medium. Items are keyed **and** indexed, with the comment stating this is to handle **addition of new rows** — the append-into-a-rendered-view case. Heights are adaptive: `_yPositions` tracks height and y by index, `_knownHeights` caches *measured* heights by key, `_scanItemHeights()` runs in `componentDidUpdate`, and the parent supplies `itemHeightGetter` as a fallback. `_onScroll` sets a flag and schedules positioning on a single `requestAnimationFrame`.

#### Datadog, Honeycomb, Grafana Tempo — mostly a dead end, with one good idea

No engineering posts on waterfall rendering internals were found for any of the three. One real number and one genuinely different idea: Datadog documents (https://docs.datadoghq.com/tracing/trace_explorer/trace_view/) that when a trace exceeds **100MB** it cannot be fully visualized, and **Trace Preview** mode engages, showing only service-entry spans, error spans, long-running spans, and linked spans. **That is a semantic LOD — pick the important events — rather than a geometric one**, and it is the only example of that approach in the survey. Honeycomb documents only "up to 6 levels of span dependency" in the trace summary, which is a display feature rather than a limit.

### 1.4 Large-scale data marks, retained scene graphs, and the GPU libraries

#### deck.gl (Uber / vis.gl) — reactive descriptors over retained GPU state

Layers are cheap descriptor objects re-created every render; deck.gl matches them by `id` against existing layers and **transfers the GPU state across**, so only changed attributes are re-uploaded. Accessors (`getPosition`, `getFillColor`) run once per data item to fill typed-array attribute buffers, and the layer draws with WebGL **instancing** — one geometry, N instances, effectively one draw call per layer. `updateTriggers` is the explicit invalidation channel for when an accessor closure changes but its outputs do not. This reactive-declarative position over retained GPU state is the interesting middle ground between immediate and retained mode.

Uber's stated motivation (https://www.uber.com/blog/visualizing-data-sets-deck-gl-framework/, https://www.uber.com/blog/deck-gl-4-0/) was web-based, shareable, interactive exploration of historical and real-time GPS and trip data, with the layer model existing so analysts can compose semantically separate datasets and toggle them. They implemented **emulated 64-bit float on the GPU** because competitors trade precision for speed.

**Numbers** (https://deck.gl/docs/developer-guide/performance): fluid **60 FPS pan/zoom up to about 1M items** for Scatterplot-class layers; **10–20 FPS approaching 10M items**; browser memory death **between 10M and 100M items**. Around 100 layers tested fine. Picking limits are **255−1 layers** and **255·255·255−1 objects per layer** simultaneously pickable, which the perf doc phrases as **16M items per layer** and **256 layers**. Uber's blog demos show **2M points plus 36,000 taxi trips** simultaneously and **860,000 instanced circles** in one render. Retina/HiDPI generates **4× the fragments**, and the doc explicitly tells you to disable it if you are fill-rate bound.

**GPU picking** (https://deck.gl/docs/developer-guide/custom-layers/picking): all pickable layers render into an **off-screen picking buffer** in a special mode toggled by a GLSL uniform. `layer.encodePickingColor()` turns an object index into a 3-byte colour; the pixel under the cursor is read back and `decodePickingColor()` inverts it. The interactivity doc states the encoding as 8-bit RGBA colours encoding object and layer index. Shader hooks are `picking_setPickingColor()` / `picking_filterPickingColor()`. Offscreen objects are not pickable.

**GPU aggregation**: `ScreenGridLayer` has `gpuAggregation` defaulting to `true` — histogram binning on the GPU. The documented caveat is that binning is in **screen space**, so it must re-aggregate on every pan and zoom, which makes it best for smaller datasets.

**TileLayer** (https://deck.gl/docs/api-reference/geo-layers/tile-layer): default `tileSize` **512px**, `maxRequests` default **6** concurrent fetches, `maxCacheSize` defaulting to **5× the tiles in the current viewport**, and `refinementStrategy: 'best-available'` filling gaps from the nearest cached zoom level during zoom.

#### regl — immediate-mode, stateless WebGL

Two primitives only: **resources** (buffers, textures, FBOs) and **commands**, where a command is a complete snapshot of the WebGL state needed for one draw. No scene graph, no math library. Commands are compiled via **dynamic code generation and partial evaluation** into specialized JS, so abstraction cost over raw WebGL is close to zero. **Scoped commands** (passing a function instead of props) let outer state persist across nested inner commands — that is the state-change-minimization mechanism. **Batch mode** (calling a command with an array of props) lets regl statically separate constant from dynamic props and re-apply only the deltas per draw.

The declared values in the README (https://github.com/regl-project/regl, https://raw.githubusercontent.com/regl-project/regl/gh-pages/API.md) are simplicity, correctness, performance, minimalism and stability, and the design thesis is that WebGL's global state machine is the source of both bugs and slowness, so you delete it. They claim over 30,000 unit tests and over 95% coverage. **Throughput benchmarks are UNVERIFIED** — benchmarks exist (`npm run bench`) but no numbers are published on the fetched pages. `regl.party` failed DNS at fetch time. **Mikola Lysenko's authorship is UNVERIFIED from the primary README**, which credits Freeman Lab / Howard Hughes Medical Institute as sponsors.

#### PixiJS — retained scene graph, batching is the whole game

v8 self-describes as the fastest 2D WebGPU/WebGL renderer. Sprites are auto-batched. **Render groups** are the v8 addition: self-contained sub-scene-graphs whose transform, tint and alpha are offloaded to the GPU, so moving a whole group costs almost no CPU. Culling is **off by default**, opt-in per object (`cullable = true`).

The stated performance model (https://pixijs.com/8.x/guides/concepts/performance-tips) is that draw-call count is driven by *ordering*. Their own example: `Screen/Normal/Screen/Normal` sprites cost **4 draw calls**; grouped by blend mode, **2**. Numbers given: **up to 16 textures batched** per draw call, hardware-dependent, which is why texture atlases matter; Graphics objects at **≤100 points** perform comparably to sprites, beyond which you bake to sprites; mask cost ranking fastest to slowest is **rectangle (scissor rect) → graphics (stencil buffer) → sprite (filters)**. Two honest warnings from their own docs: culling **hurts if you are CPU-bound**, and too many render groups degrade performance with most apps needing none. **No sprites/sec or FPS benchmarks are published — UNVERIFIED.**

Production users named on pixijs.com and its showcase — Pixi's own claim, logos on a vendor page rather than independent confirmation — include Adobe, Google, YouTube, Disney, Marvel, Lucasfilm, HBO, BBC, Cartoon Network, Spotify, Ubisoft, LEGO, Toyota, Volkswagen, Steam, Barclays, H&M, with SYBO's Subway Surfers, Google Research's Semantris, and UNICEF in the showcase.

#### Konva — retained scene graph over Canvas2D, and the clearest documented color-key picking

Stage → Layer → Group → Shape, where **each `Layer` is a real `<canvas>` element**, so layering *is* the compositing strategy.

**Hit testing is color-coded picking on a hidden canvas, confirmed from source.** Every Layer allocates two canvases: the visible scene canvas plus a hidden hit-graph canvas. In `src/Shape.ts` each shape is assigned a unique random `colorKey` via `Util.getRandomColor()` and registered in a module-global `shapes[key]` map, deleted on destroy. Shapes are drawn into the hit canvas filled with that flat colour. `Layer._getIntersection(pos)` calls `hitCanvas.context.getImageData(...)`, converts the sampled RGB back with `Util.getHitColorKey(r, g, b)` and looks up `shapes[colorKey]`. Same technique as deck.gl's GPU picking, on Canvas2D instead of a GL framebuffer. `hitFunc` lets you draw a *different* — larger or simpler — region into the hit canvas than the visual one; `hitStrokeWidth` widens thin-line hit areas; and you can un-hide `layer.hitCanvas._canvas` to debug it. (Sources: https://konvajs.org/docs/events/Custom_Hit_Region.html, https://raw.githubusercontent.com/konvajs/konva/master/src/Shape.ts, `.../src/Layer.ts`.)

**The memory numbers are the cautionary ones** (https://konvajs.org/docs/performance/All_Performance_Tips.html). The scene canvas is at device pixel ratio while the **hit canvas is always at ratio 1**. On a 1920×1080 retina screen that is roughly **41 MB per empty layer** — about 33 MB scene plus 8 MB hit. Konva **warns at 5+ layers**, since empty layers alone approach **200 MB**. And **Mobile Safari has a hard ceiling of 256–384 MB** total canvas memory, where overflow yields a *blank canvas* rather than graceful degradation. That is the single strongest published argument against unbounded multi-canvas layering.

Other documented techniques: `cache()` bakes a shape or group to a bitmap; `listening(false)` skips hit-graph drawing entirely; `Konva.hitOnDragEnabled` defaults **false** so hit testing is off during drags; `perfectDrawEnabled(false)` avoids an extra buffer pass for fill+stroke+opacity; `visible(false)` is their culling primitive with `Konva.Util.haveIntersection()` for the viewport test. Their strongest scaling advice is telling: **one custom shape drawing many items in a single `sceneFunc` beats many individual nodes** — that is Konva's own documentation advising you to escape its retained graph at scale.

#### CanvasKit / Skia-on-WASM and the Flutter Web lesson

CanvasKit (https://skia.org/docs/user/modules/canvaskit/) is a WebAssembly build of Skia; a WebGL context is wrapped as an `SkSurface` and drawn to an HTML canvas on a hardware-accelerated backend, with core canvas/paint/path/text plus Skottie for Lottie. **skia.org publishes no binary-size number — UNVERIFIED from Skia's own docs.**

**The payload cost comes from Flutter's own blog** (https://flutter.dev/blog/best-practices-for-optimizing-flutter-web-loading-speed): CanvasKit is **around 1.5 MB**, and they state its file size can be a drawback where initial load time matters. That is the vendor's own number for the Skia-in-WASM tax. The blog positions Wasm compilation as reducing size versus CanvasKit and starting faster than JS, while calling WebAssembly support experimental.

Renderer selection is a runtime option (https://docs.flutter.dev/platform-integration/web/initialization): `renderer: 'canvaskit' | 'skwasm'`, plus `canvasKitVariant: auto|full|chromium`, `canvasKitBaseUrl`, `canvasKitForceCpuOnly`, `canvasKitMaximumSurfaces`, `forceSingleThreadedSkwasm`. skwasm is the compact Skia build that can render **on a separate thread**. The commonly cited **1.1 MB skwasm figure is UNVERIFIED** — its source page now redirects and no longer contains it.

**WASM gates** (https://docs.flutter.dev/platform-integration/web/wasm): requires **WasmGC**, Chrome/Chromium **119+**; Firefox 120+ has WasmGC but a blocking bug; **all iOS browsers cannot run Flutter Wasm** because of WebKit. Multithreading needs `Cross-Origin-Embedder-Policy: credentialless|require-corp` plus `Cross-Origin-Opener-Policy: same-origin`. `--no-strip-wasm` costs roughly **47% size increase**.

**The honest cost, stated by the vendor** (https://docs.flutter.dev/platform-integration/web/faq): Flutter web prioritizes performance, fidelity and consistency, and its output does not align with what search engines need to index properly. They recommend Jaspr or plain HTML for document-like or static content, kept *separate* from the Flutter app. This is the canonical vendor statement of the canvas-rendering-loses-the-document-model trade-off. The FAQ does not cover accessibility or text selection (**UNVERIFIED**), though `debugShowSemanticsNodes` in the initialization docs implies a parallel semantics tree is synthesized for a11y rather than inherited from the DOM.

#### Mapbox GL JS / MapLibre — the canonical pan/zoom architecture

**Worker offloading is structural, not a bolt-on.** Per their ARCHITECTURE.md (https://raw.githubusercontent.com/mapbox/mapbox-gl-js/main/ARCHITECTURE.md), tiles are fetched **and parsed on WebWorker threads**, where `@mapbox/vector-tile` deserializes source layers, feature properties and geometries from PBF. Then layout: `WorkerTile#parse()` builds a **`Bucket`** per family of style layers sharing features and layout properties — their own framing is that Bucket is the single point of knowledge for turning vector tiles into WebGL buffers. Geometry is indexed into a `FeatureIndex` to serve `queryRenderedFeatures`. Rendering runs style-layer by style-layer through `Painter#renderPass()`, with `ProgramConfiguration` expanding `#pragma mapbox` into either uniforms or data-driven attributes, then `gl.drawElements()`. **The main thread only paints.**

**Why tiling** (https://docs.mapbox.com/data/tilesets/guides/vector-tiles-introduction/): their five stated reasons are efficiency at scale without fidelity loss, interactivity through fast re-render enabling smooth zoom/pan/tilt/rotate, **runtime styling** from one global dataset, small payloads, and direct property access for querying. Their stated drawback: rendering vector tiles needs more client processing than blitting pre-rendered raster.

**Glyph atlas and SDF text** (https://github.com/mapbox/mapbox-gl-native/wiki/Text-Rendering). Mapbox does **not** rasterize text per frame. Glyphs are **signed distance fields** — each pixel encodes distance from the glyph edge — enabling arbitrary scaling and halos from one texture. Per tile, all needed glyphs are packed into **a single texture atlas** uploaded to the GPU, and each glyph is drawn as **two triangles** with UVs into that atlas. Glyphs are requested in **256-glyph blocks** (`{fontstack}/{range}.pbf`, e.g. `0-255.pbf`), cached whole on first need. SDFs are generated at **24pt = 1 em**, then scaled by `text-size`.

**Label collision is the most instructive part** (https://github.com/mapbox/mapbox-gl-native/wiki/Collision-Detection). Tiles contain more labels than can be shown, so a subset is chosen **every frame**. Point labels use rectangles; line labels following curves use **chains of circles**, chosen because circles are **stable under rotation**. A **GridIndex** accelerates queries with **30px cells**, about **400 cells** for a 600×600 viewport — and the cell size came from profiling, sized so a collision circle for 16px text fits in one cell and touches at most four. **`CrossTileSymbolIndex`** assigns a shared `crossTileID` to the same symbol appearing at different zooms, so labels do not flicker across tile load/unload and can fade smoothly. Collision emits **opacities in 0–1** that the GPU interpolates, rather than binary show/hide. And the design history matters: collision was moved **off the worker back to the foreground**, because symbols originate per-tile but collide *across* tile boundaries. Their stated budget is that it must fit inside a **60 FPS loop**, so the synchronous pass has to finish in milliseconds.

**Tile numbers.** Vector Tile Spec 2.1 (https://github.com/mapbox/vector-tile-spec/blob/master/2.1/README.md): every layer **MUST** declare an integer `extent`; geometry coordinates are integers with origin top-left, encoded as command integers `(id & 0x7) | (count << 3)` with MoveTo=1, LineTo=2, ClosePath=7. **4096 appears in the spec as the worked example, not as a mandated default** — a correction worth carrying. Mapbox's text-rendering wiki states symbol geometry is normalized to an **8192 extent** regardless of source tile size. MTS limits (https://docs.mapbox.com/mapbox-tiling-service/overview/frequentlyaskedquestions/): **1250 KB per layer** default, raisable to **2500 KB**; over the limit **MTS silently drops features** and reports them in the job's `warnings` array. (An older 500 KB figure appeared only in a search summary — **UNVERIFIED**.)

**MapLibre** (https://maplibre.org/maplibre-gl-js/docs/) is the community fork after the license change, stating the same three pillars verbatim — vector tiles, WebGL, and web workers parsing tile data asynchronously so the UI does not block — and adding 3D terrain, globe and custom layers. No perf numbers on the docs landing page (**UNVERIFIED**).

#### Zed's GPUI — the cleanest primary source for glyph-atlas UI rendering

Zed (https://zed.dev/blog/videogame) rejected a general 2D graphics library and wrote **one custom shader per primitive** — rectangle, shadow, glyph, icon, image. Rounded rectangles are **SDFs evaluated in the fragment shader** (shrink by corner radius, then distance test), so there is no tessellation. Every primitive type is drawn with **instanced rendering**: rect instance data carries origin, size, background and corner radius, and the whole set goes in one draw call. Shadows use Evan Wallace's closed-form Gaussian approximation — exact 1D erf convolution on one axis, finite sampling on the other.

Their text pipeline is the model worth studying: OS shaping via CoreText with **CPU-side caching of shaped text plus font pairs**; the OS rasterizes glyphs into **the alpha channel only**, so one atlas entry tints to any colour; **up to 16 variants per glyph** for sub-pixel positioning; **bin-packing** into the atlas; then **a single instanced draw call** assembling all glyphs from atlas coordinates.

Their stated target is **120 FPS**, an **8.33 ms** budget covering state update, layout and framebuffer writes. Layout borrows Flutter's model — constraints down, sizes up — behind an `Element` trait.

#### Rive

Rive's renderer post (https://rive.app/blog/rive-renderer-now-open-source-and-available-on-all-platforms) describes a geometric reduction of antialiased vector paths into **unique triangle patches**, riding the GPU's triangle rasterizer instead of a CPU tessellator, with analytic AA from signed triangle coverage — which is why text stays crisp at any scale **without a glyph atlas**. They built it because depending on Skia and HTML Canvas meant multi-backend divergence, so any feature missing on one backend could not ship at all: a platform-consistency argument, not a raw-speed one. Claim: **120 fps** with pristine antialiasing filling the screen with vector graphics and text. Specific backend names and the circulating "57% smaller / 60% more efficient iOS runtime" figures are **UNVERIFIED** — not on the fetched page.

Two.js, Fabric.js and Paper.js were checked and dropped: no primary production-adoption evidence worth reporting.

### 1.5 Text-heavy counterexamples — the teams that stayed in the DOM

#### CodeMirror 6 — DOM plus viewport virtualization, canvas explicitly rejected

The architecture (https://codemirror.net/docs/guide/) is worth knowing precisely, because it is the discipline canvas people believe is unique to canvas, implemented in the DOM:

- **Viewport rendering.** CM6 does not render the whole document. On update it detects the part of the content not scrolled out of view and renders that plus a margin, exposed as `EditorView.viewport`. Layout queries for positions outside it fail, because there is no DOM there.
- **Height information is tracked for the entire document even outside the viewport** — initially estimated, then measured accurately once content is drawn (`EditorView.lineBlockAtHeight`). That is what makes the scrollbar honest without rendering everything.
- **`EditorView.visibleRanges`** is a second, tighter set for expensive work like syntax highlighting, further excluding content inside the viewport but not actually visible (folded ranges, long unwrapped lines).
- **Write/read phase separation.** Dispatching a transaction only *writes* to the DOM. All layout *reading* happens in a separate **measure phase scheduled with `requestAnimationFrame`**. Deliberate reflow avoidance.

**Marijn Haverbeke's own reasoning against canvas** (https://discuss.codemirror.net/t/anyone-explored-a-codemirror-6-canvas-webgl-renderer/3779) is three claims and a precedent: performance is not the win people assume, and for text layout the DOM will in most situations be faster than canvas; accessibility will be terrible if the text is only pixels; you inherit the entire text-shaping problem once you are down at `fillText`; and Bespin, Mozilla's 2009 canvas editor, is the prior art that already failed this way.

**No published numbers.** His argument is structural, not measured. His progress post (https://marijnhaverbeke.nl/blog/codemirror-6-progress.html) covers the state/view split and viewport-as-state but contains no canvas comparison and no rendering benchmarks. **Any claim that CodeMirror measured canvas and it lost is UNVERIFIED.**

#### Monaco / VS Code — they split the decision by surface, and the split held for seven years

**The editor stayed DOM.** The clearest first-party statement of why is, ironically, in the issue proposing to change it: https://github.com/microsoft/vscode/issues/221145 ("WebGPU-based renderer for the editor", July 2024). It states the current DOM renderer requires layout work every frame, capping responsiveness during scrolling and input, and traces the motivation to the long-running zero-latency-typing investigation (microsoft/vscode#27378). The planned scope: glyphs rasterized via canvas 2D and packed into texture atlas pages, with pre-allocated buffers sized for roughly **3,000 lines × 200 columns, about 7.2MB**. Prior attempts are logged — an xterm.js-based prototype in 2022 and a "game renderer" experiment in 2024, both archived.

**Status: still an opt-in experiment** (`editor.experimentalGpuAcceleration`), still generating correctness bugs through 2025 — blurred and shadowed highlighted text (microsoft/vscode#238289), overlapping lines, wrong cursor position, broken ligatures, disappearing horizontal scrollbar (#269471), and a Dec 2025 issue about formally tagging it experimental (#282893). **The editor default remains DOM.** That is the honest headline: Microsoft has been trying to leave the DOM for the editor since 2022, and after roughly two years of funded work it is an experiment with visible glitches — while the terminal made the same jump successfully in months.

Monaco's screen-reader support is documented as a strategy based on paging the text (https://github.com/Microsoft/monaco-editor/wiki/Accessibility-Guide-for-Integrators), but that page documents user-facing behaviour only; the `accessibilityPageSize` / hidden-textarea mechanics are **UNVERIFIED** from it.

#### xterm.js — the fully documented DOM → canvas → WebGL → canvas-deleted journey

This is the best-evidenced arc in the entire survey, with real numbers at every step, and its ending is the part usually left out.

**Step 1 — why DOM failed** (https://code.visualstudio.com/blogs/2017/10/03/terminal-renderer, VS Code 1.17, Oct 2017). Native DOM selection had to be overridden anyway, since you could not select across pages without reimplementing it and scrolling dropped the selection. Some Unicode characters break monospace alignment, and the fix — wrapping them in fixed-width spans — measurably increased frame time. The element count generated enough garbage that they resorted to object pooling and it was *still* a bottleneck. And the framing that generalizes: performance always has a hard cap imposed by the layout engine, and composing elements plus running layout could exceed the 16.6ms budget on its own.

What canvas bought: **four layered canvases** (text with background colours and foreground glyphs, opaque; selection; link underline; cursor) — described as a major simplification of drawing logic, not merely a speed trick. **Dirty-region tracking** via an internal model holding minimal per-cell state (character, styles, fg/bg), so only changed cells draw. A **texture atlas** as an `ImageBitmap` pre-rendering common ASCII characters in standard styles, replacing `fillText` calls. Frame-skipping was removed, enabling consistent 60 FPS. **Result: approximately 5 to 45 times faster**, depending on workload.

**Step 1.5 — canvas immediately needed a DOM fallback.** https://github.com/xtermjs/xterm.js/issues/1360 — Daniel Imms opened it to add the DOM renderer back, because certain GPU/browser combinations simply fail at drawing to canvas and the terminal then crawls; for Electron they suggested detecting via `app.getGPUFeatureStatus()`. **Worth dwelling on: the canvas renderer created a class of user for whom canvas was catastrophically slower than the DOM it replaced.**

**Step 2 — canvas → WebGL** (https://github.com/xtermjs/xterm.js/pull/1790). The stated insufficiency of canvas is **draw-call count**: canvas2d meant issuing a per-character instruction to the GPU, and those individual instructions dominate. WebGL replaces that with one `Float32Array` of all draw data uploaded per frame, plus vertex/fragment shaders, using vertex array objects and `drawElementsInstanced`. The atlas was extended to all characters including Unicode, combining characters and emoji (canvas cached ASCII only), with glyphs stored **trimmed to their minimal rect** for better packing; on atlas overflow the first implementation simply clears and restarts, chosen for simplicity.

Published frame-render-time benchmarks:

| Scenario | Canvas | WebGL | Speedup |
|---|---|---|---|
| MacBook, 87×26 | 4.80ms | 0.69ms | 596% |
| Windows, 87×26 | 7.31ms | 0.73ms | 901% |
| MacBook, 300×80 | 15.28ms | 3.69ms | 314% |

Complex text gained far less — CJK about 147%, emoji about 42%. The cost: WebGL2 cut supported desktops to roughly 68% at the time.

**Step 3 — VS Code ships it.** v1.41 (Nov 2019, https://code.visualstudio.com/updates/v1_41): experimental, opt-in, headline "up to 900%", with **frame times quoted as canvas typically 1–40ms and sometimes over 200ms, versus WebGL 0.2–2ms**. Their stated reasons: direct GPU communication instead of `CanvasRenderingContext2D`; almost everything is numbers and typed arrays; object and array creation minimized to avoid GC. Noted failure mode: WebGL either works or fails hard and falls back, unlike canvas's silent CPU fallback. v1.55 (Mar 2021, https://code.visualstudio.com/updates/v1_55) makes WebGL the **default** with a three-tier `auto` fallback — try WebGL, fall back to canvas and **measure the first 20 frames**, and if those are slow fall back to DOM. That is a real, shipped example of **runtime renderer selection by measurement**. v1.60 (Aug 2021, https://code.visualstudio.com/updates/v1_60) replaces `rendererType` with `terminal.integrated.gpuAcceleration: "auto" | "on" | "off"`, and adds pixel-perfect **custom glyphs** for box-drawing and block-element characters instead of the font, so boxes have no gaps at custom line height or letter spacing — canvas had a specific defect here, clipping rows to avoid overlap and thereby dropping underscores entirely.

**Step 4 — and this is the part that matters most.** https://code.visualstudio.com/updates/v1_90 (May 2024): the canvas renderer was deprecated in 1.89 and **removed completely** in 1.90. On the small number of machines without WebGL2, **the terminal now uses the DOM-based renderer**. The final shape is a two-renderer world — WebGL, with DOM as the fallback. **Canvas2D, the thing that delivered the original 5–45× win, no longer exists in the product.**

On the xterm.js library side the default went the other way: https://github.com/xtermjs/xterm.js/issues/3271 made the **DOM renderer the library default** and pushed canvas into an addon, the stated reason being bundle size, with canvas kept as an addon specifically because Safari and iPad were then stuck on the slower DOM renderer. Current shape: DOM default, `@xterm/addon-canvas` and `@xterm/addon-webgl` as opt-ins. (The renderer list on xtermjs.org itself is **UNVERIFIED** — the docs URL 404'd and the docs index returned only nav chrome; the GitHub issue is the solid source.)

#### Linear — their published performance story is not about rendering

This needs saying plainly, because the assumption is common. Checking https://linear.app/blog, the recent engineering posts are a StyleX migration, a delta-sync read-path rebuild (turbopuffer, over 20TB of sync actions), and how they built Linear Agent. **None is about UI rendering strategy.** Tuomas Artman's sync-engine talk page (https://linear.app/now/scaling-the-linear-sync-engine) is about the sync engine and the API shape that fell out of it — **no canvas, no DOM rendering, no virtualization content.**

The one Linear-authored post with real client-side performance numbers is about CSS: https://linear.app/now/styling-linear-for-the-future-stylex. Linear's frontend is **React**, and they migrated from styled-components to StyleX over **more than 1,000 PRs**. Their reasoning: CSS-in-JS adds work during rendering to generate styles and inject rules, and they hit regressions after upgrading to React 18's concurrent rendering, since styled-components never adopted `useInsertionEffect` and went into maintenance mode. **Numbers: on view-heavy pages, removing runtime style injection reduced main-thread CPU work by roughly 20–35%**, described as roughly 30% faster on mid-tier machines, with the client going from injecting hundreds of CSS rules during a navigation to zero. Canvas, DOM rendering, and list virtualization are not mentioned.

**Verdict: Linear is a DOM/React app whose published performance work is a local-first sync engine plus making DOM styling cheaper by moving it to build time. Their answer to "why is Linear fast" is emphatically not a rendering-strategy answer.** Claims about a MobX in-memory object pool hydrated from IndexedDB come from third-party reverse-engineering, not Linear's own posts — **UNVERIFIED**.

#### Other honest accounts

**Flipboard's react-canvas — the canonical abandoned attempt** (https://github.com/Flipboard/react-canvas). The premise was that the DOM is why mobile web feels slow versus native, so they rendered React components (`Surface`, `Layer`, `Group`, `Text`, `Image`, `Gradient`, `ListView`) to canvas. Read their own caveats as the counterexample: `ListView` required every item to be the same height; **custom fonts were not supported**; CSS-layout support was flagged experimental with unresolved performance questions; and accessibility needed further exploration with mixed results against iOS VoiceOver. The README still says work-in-progress, and the project is unmaintained (issue #168 asks maintainers to say so). **No Flipboard post-mortem saying "we went back to DOM" was found — that specific claim is UNVERIFIED.** What is documented is that the library's limitations were exactly the DOM's affordances: fonts, text layout, accessibility.

**A candid individual failure account**, low authority but honest: https://dev.to/manuartero/trying-to-replace-the-dom-with-canvas-and-failing-112i — a senior engineer at Telefónica's video platform spent three weeks on a Pixi.js product grid for a RAM-constrained embedded TV target and could not finish, concluding that graphics programming is a different discipline rather than another JS library. Cite as a staffing and expertise data point, not a performance one.

**AG Grid — a data-heavy product that stayed DOM** (https://www.ag-grid.com/javascript-data-grid/dom-virtualisation/): row *and* column virtualisation; a default row buffer of 10 rows before and 10 after the visible range; a safety cap of **500 rendered rows** (`suppressMaxRenderedRowRestriction` to lift, `suppressRowVirtualisation=true` to disable). Notably **no column buffer**, with the explicit reasoning that horizontal scrolling is not as CPU-intensive as vertical. Canvas is not mentioned anywhere on the page. (A claim that AG Grid caches and reuses rendered nodes came from search aggregation, not this page — **UNVERIFIED**.)

### 1.6 The techniques themselves, with authoritative docs and known users

#### Dirty rectangle / damage tracking
**MDN's "Optimizing canvas"** (https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas) lists rendering only screen differences as an explicit recommendation. The best-documented shipping use is the **VS Code terminal canvas renderer**: an internal model holds minimal per-cell state and only changed cells trigger a draw, replacing whole-line reconstruction. The transferable caution: **damage tracking requires a model of what is currently on screen, which means you now own a second data structure whose staleness is a new bug class.**

#### Multi-canvas layering
MDN recommends splitting complex scenes into multiple `<canvas>` elements at different z-indexes, static versus dynamic, and separately recommends plain CSS `background` on a `<div>` for large static backgrounds rather than painting them.

**Konva** (https://konvajs.org/docs/performance/Layer_Management.html) makes each layer its own canvas element, which is what lets animated content redraw without touching static content — with the cap stated in their docs that 3–5 layers is usually the maximum, and the memory arithmetic given in §1.4 above (verified first-hand by this lane: roughly 41 MB per layer at 1920×1080 retina, a warning above five layers, and a Mobile Safari ceiling of about 256 MB on some devices and 384 MB on others, where exceeding it yields `Total canvas memory use exceeds the maximum limit` and a blank canvas).

**Excalidraw** ships exactly this, confirmed from source: https://github.com/excalidraw/excalidraw/tree/master/packages/excalidraw/components/canvases contains `StaticCanvas.tsx`, `InteractiveCanvas.tsx` and `NewElementCanvas.tsx`. **VS Code's terminal** used four layers and described the win as simplified drawing logic as much as speed.

#### OffscreenCanvas + Web Workers — the docs are good and the field evidence is essentially absent

**Mechanics** (https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas, https://web.dev/articles/offscreen-canvas): `HTMLCanvasElement.transferControlToOffscreen()` returns a transferable `OffscreenCanvas`, which must be passed in the **transfer list** of `postMessage`; the original `<canvas>` can no longer be manipulated from the main thread. `requestAnimationFrame` works inside the worker (the older `commit()` is deprecated). A non-worker mode also exists: construct `new OffscreenCanvas(w, h)`, draw, then `transferToImageBitmap()` into a main-thread `bitmaprenderer` context. Known friction: `OffscreenCanvas` has no `style.width`/`style.height`, so libraries like Three.js need stubbed dimension properties.

**Browser support, with a discrepancy worth knowing.** https://caniuse.com/offscreencanvas: Chrome 69 full (58–68 flagged), Edge 79, Firefox 105 (44–104 flagged), **Safari 17.0 full with partial support from 16.2–16.6**, iOS Safari 17.0, about 95.2% global. https://web-platform-dx.github.io/web-features-explorer/features/offscreen-canvas/ instead credits **Safari 16.4 (2023-03-27)** and marks Baseline **Widely Available since 2025-09-27**; web.dev says 16.4+. **If your target includes Safari, verify per-context (2d versus webgl) rather than trusting a single "supported since" number.** Practical read: Safari-complete is roughly 2023, and Baseline-widely-available only around September 2025.

**Adoption — be skeptical.** The one hard figure is Chrome Platform Status reporting roughly **7.958%** of page loads using OffscreenCanvas (via the web-features explorer; the chromestatus timeline page itself returned no readable content, so treat as second-hand-but-cited). That number is also ambiguous, because a usage counter fires on API presence and does not tell you the canvas is driven from a worker.

**No named shipping user could be verified from a first-party source.** Search surfaced claims about Bloomberg, Hyperliquid, Figma running its WASM engine in a worker, and Datadog live tail — **all from search aggregation with no primary citation, none confirmable: UNVERIFIED.** Figma's own rendering post describes WebGL, not OffscreenCanvas-in-a-worker. The nearest first-party-ish material is a W3C Maps4HTML community post (https://www.w3.org/community/maps4html/2020/04/07/better-web-maps-with-new-browser-features/) and web.dev's own demos — which **publish no timing or FPS numbers at all**, only qualitative "the UI stays responsive" demos.

**Honest summary: OffscreenCanvas is well-specified, widely supported since 2023–2025, and essentially undocumented in the wild. There is no public case study with numbers.**

#### Device pixel ratio and crispness
https://developer.mozilla.org/en-US/docs/Web/API/Window/devicePixelRatio gives the canonical backing-store pattern: set `canvas.style.width/height` in CSS pixels for layout, set `canvas.width/height` to `Math.floor(size * devicePixelRatio)` for the backing store, then `ctx.scale(dpr, dpr)` so drawing code stays in CSS-pixel coordinates.

Two things worth internalizing: **page zoom changes `devicePixelRatio`** (pinch-zoom does not), and there is **no resize-style event for it**. MDN's monitoring recipe is a self-renewing `matchMedia("(resolution: Xdppx)")` listener that re-registers on each change — needed when a window moves between displays. Konva's counter-advice is the other side of the same coin: set `Konva.pixelRatio = 1` on retina to *reduce* scaling overhead. **On dense displays, crispness and throughput trade directly.**

#### requestAnimationFrame, frame budgets, RAIL
**RAIL** (https://web.dev/articles/rail):
- **Response** — transition within **100ms** of input; process the event in **50ms**, because roughly 50ms of the window is typically consumed by other background work.
- **Animation — produce each frame in 10ms or less.** The derivation is the load-bearing part: the frame budget is 16ms at 60Hz, but browsers need about **6ms** to render, leaving about **10ms** for your code. **Do not plan against 16.7ms — plan against 10ms.**
- **Idle** — chunk deferred work into pieces of 50ms or less so input is not blocked.
- **Load** — interactive within 5s on mid-range mobile over slow 3G; 2s on subsequent loads.

**rAF semantics** (https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame): the callback runs **before the next repaint**; frequency matches the display refresh rate, and 60/75/120/144Hz are all common; calls are **paused in background tabs and hidden iframes**; it is **one-shot**, so you must re-request. The callback receives a `DOMHighResTimeStamp` equal to the previous frame's render end time, shared across same-origin windows so animations can sync. MDN's explicit warning: **always drive progress from that timestamp, or the animation runs faster on high-refresh screens** — a real bug class now that 120Hz is ordinary.

#### MDN's "Optimizing canvas" — the full concrete list
In order, from https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas:
1. Pre-render repeated drawing to an offscreen canvas.
2. **Avoid floating-point coordinates** — `Math.floor()` coordinates passed to `drawImage` to avoid sub-pixel rendering.
3. Don't scale in `drawImage` — cache pre-scaled sizes offscreen.
4. Use **multiple layered canvases** with z-index for static versus dynamic content.
5. Use plain CSS `background` on a `<div>` for large static backgrounds.
6. Scale with **CSS transforms** rather than scaling the canvas — GPU-accelerated.
7. **Turn off transparency**: `getContext("2d", { alpha: false })` when you don't need it.
8. Scale for HiDPI via `devicePixelRatio` plus `ctx.scale(dpr, dpr)`.
9. **Batch calls** — one polyline instead of many separate lines.
10. Avoid unnecessary canvas **state changes**.
11. Render only screen differences, not the whole state.
12. **Avoid `shadowBlur`.**
13. **Avoid text rendering.**
14. Try the different clearing methods — `clearRect()` versus `fillRect()` versus resizing the canvas — and measure.
15. Use `requestAnimationFrame`, not `setInterval`.
16. Be careful with heavy physics libraries.

#### Text on canvas
**MDN's own advice is item 13 above: avoid rendering text.** That is the authoritative version of "keep text in the DOM."

`measureText` returns a `TextMetrics` (https://developer.mozilla.org/en-US/docs/Web/API/TextMetrics) with `width`, `actualBoundingBoxLeft/Right/Ascent/Descent`, `fontBoundingBoxAscent/Descent`, `emHeightAscent/Descent`, `hangingBaseline`, `alphabeticBaseline`, `ideographicBaseline` — baseline widely available since July 2015 and **available in Web Workers**. A useful gotcha MDN calls out: for italic or slanted faces, `actualBoundingBoxLeft + actualBoundingBoxRight` can exceed `width` because of overhang, and is the more accurate absolute width. **MDN states no explicit cost for `measureText` — the "measureText is expensive" folklore is UNVERIFIED from MDN.**

What *is* documented is the workaround everyone converges on: **glyph and texture atlases.** Two first-party accounts — the VS Code terminal used an `ImageBitmap` GPU-resident atlas of common ASCII characters in standard styles specifically to **replace `fillText` calls**, and xterm.js's WebGL renderer extended the atlas to all characters including Unicode, combining characters and emoji, stored trimmed to minimal rects. VS Code's editor GPU work plans the identical thing. Add Mapbox's SDF atlas and Zed's alpha-channel atlas with 16 sub-pixel variants per glyph from §1.4. **Nobody who is serious calls `fillText` per glyph per frame.**

The dissenting data point is xterm.js's own benchmark: the atlas advantage **shrinks sharply for CJK (147%) and emoji (42%)** versus ASCII (596–901%). **Atlases pay off in proportion to glyph repetition** — which is why they work superbly for a fixed-grid terminal and much less well for arbitrary multilingual prose.

#### Path2D, save/restore, will-change, imageSmoothingEnabled
- **`Path2D`** (https://developer.mozilla.org/en-US/docs/Web/API/Path2D) declares a path you can retain and replay. Constructors: empty, from another `Path2D`, or **from SVG path data**. Carries the full path vocabulary plus `addPath()`, and is used as `ctx.fill(path)`, `ctx.stroke(path)`, `ctx.isPointInPath(path, x, y)`. The documented benefit is **reuse**; MDN gives no speedup numbers.
- **`ctx.save()`/`restore()`** (https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/save) pushes the *entire* drawing state: transformation matrix, clipping region, dash list, plus `direction`, `fillStyle`, `filter`, `font`, `fontKerning`, `fontStretch`, `fontVariantCaps`, `globalAlpha`, `globalCompositeOperation`, `imageSmoothingEnabled`, `imageSmoothingQuality`, `letterSpacing`, `lineCap`, `lineDashOffset`, `lineJoin`, `lineWidth`, `miterLimit`, all four `shadow*`, `strokeStyle`, `textAlign`, `textBaseline`, `textRendering`, `wordSpacing`. **MDN documents no cost warning and no stack-depth limit — the "save/restore is expensive" claim is UNVERIFIED.** But note MDN separately warns against unnecessary *state changes* (item 10), which is the same concern from the other side: the pair is cheap; churning 25 properties through it is not.
- **Integer coordinates** — MDN item 2. (The related half-pixel offset for crisp 1px strokes is folklore not stated on that page — **UNVERIFIED from MDN**, though Excalidraw's source shows a real implementation of the idea, snapping 1px grid lines only at 100% zoom.)
- **`will-change`** (https://developer.mozilla.org/en-US/docs/Web/CSS/will-change) should be read as a warning label rather than a technique. MDN's four cautions: do not apply it to many elements, since overusing it can slow the page down instead; use it sparingly and toggle it from script around the change, because putting it in a stylesheet keeps the optimization alive far longer than the browser would; never use it as premature optimization — it is a last resort for existing problems, and excessive use costs memory and forces more complex rendering; and give the browser lead time. Also, values that create a stacking context create it **up front**, which can change visual output.
- **`imageSmoothingEnabled`** (https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled) defaults to `true`; set `false` for pixel art, sprites, and any upscaled blit you want crisp. `imageSmoothingQuality` tunes the algorithm when smoothing is on. Both are part of the saved state.

#### Hit testing — three approaches, all with real users
1. **`isPointInPath`** (https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/isPointInPath). Signatures `(x,y)`, `(x,y,fillRule)`, `(path,x,y)`, `(path,x,y,fillRule)`; `fillRule` is `"nonzero"` (default) or `"evenodd"`. **Coordinates are unaffected by the context's current transformation** — a classic source of bugs in panned and zoomed canvases. `isPointInStroke()` is the stroke counterpart. Cost is O(shapes) per query, so it belongs in small scenes or as a refinement step after a broad-phase filter.
2. **Color-buffer picking on a hidden canvas** — **Konva's** production approach, documented at https://konvajs.org/docs/overview.html: each layer has two renderers, a visible scene renderer and a hidden **hit graph** renderer used for high-performance event detection. Each shape gets a unique colour key; hit-testing reads the pixel under the pointer and maps the colour back to a shape. Konva's docs note this **breaks under canvas farbling** — privacy-hardened browsers perturbing canvas readback — emitting an error about failing to find a unique colour key. Controls: `listening(false)` skips a node; `hitFunc` lets you draw a *different, simpler or larger* region than the visible shape, which is excellent for thin lines and small handles; `hitStrokeWidth` fattens a line's clickable area; `Konva.hitOnDragEnabled` (default off) skips hit detection during drags. And the real cost, stated in their own performance page: disabling the hit graph greatly increases draw performance because it is otherwise redrawn on every layer draw. **The hidden canvas is a second full render pass.**
3. **Spatial index (R-tree)** — **rbush** by Vladimir Agafonkin of Leaflet/Mapbox (https://github.com/mourner/rbush). R-tree with bulk insertion; single insert uses non-recursive R-tree insertion with the R*-tree overlap-minimizing split; bulk loading uses OMT with Floyd–Rivest selection. Benchmarks on 1M random rectangles at maxEntries=16: insert 1M sequentially 3.18s; **1000 searches over a 0.01% area in 0.03s (30× the alternative)**; 1% area 0.35s (6.5×); 10% area 2.18s (4.4×); **remove 1000 items 0.02s (50×)**; bulk-insert 1M in 1.25s. Siblings: **kdbush** for static points (5–8× faster than rbush) and **rbush-knn** for nearest-neighbour. tldraw adopted an R-tree in SDK 4.4.

**The practical composition is broad-phase rbush → narrow-phase `isPointInPath` or geometry math**, which avoids both the O(n) scan and colour picking's second render pass. That is exactly what tldraw does (bounding-box broad phase, distance-to-polyline narrow phase).

#### Animation in canvas UIs
**FLIP** — Paul Lewis, https://aerotwist.com/blog/flip-your-animations/. First / Last / Invert / Play: record start geometry with `getBoundingClientRect()`, apply the final state, compute the delta, apply an inverting `transform` so it *looks* unmoved, then transition the inversion away. The point is that **only `transform` and `opacity` animate without forcing layout or paint**. The scheduling insight generalizes beyond CSS: there is roughly a **100ms window after user input** in which measurement work goes unnoticed, so do the expensive measuring there and leave only compositor-cheap work for the visible frames. That 100ms is the same figure as RAIL's Response budget.

**Springs versus easing.** Android's official animation docs (https://developer.android.com/develop/ui/compose/animation/customize) state that spring can handle interruptions more smoothly than duration-based animation. The structural reason: an easing animation is a function of *elapsed time along a fixed curve*, so an interruption must restart or discontinuously retarget; a spring is a function of *current position and velocity*, so it absorbs an interruption — and a hand-off from a drag or swipe — by seeding the new solve with the current velocity. Springs have no duration, which is precisely why they compose with interruption. **No source benchmarking the two was fetched; specific parameter guidance from Motion or Anime.js is UNVERIFIED.**

**Who owns transitions when the view is a pure function of state?** **No authoritative published answer was found.** This is the genuinely open design question in the brief, and no MDN, web.dev, or first-party doc settles it. The nearest evidence is architectural, from CodeMirror: CM6 keeps viewport state *inside* the editor state precisely because extensions need it, and Marijn flags this as a pain point in the pure-state design. The analogous conclusion — that transient animation state must live somewhere addressable by the state model, or every animating element becomes a special case — is **inference, not citation: UNVERIFIED.**

### 1.7 The "beautiful" half — what makes production canvas tools feel high quality

The craft evidence is thinner than the performance evidence, but it is real and it clusters into five disciplines.

**1. Measure the worst frame, not the average.** Figma's dragging headline is 30→60fps average, but the change users actually feel is **120ms → 30ms maximum frame time** — one dropped frame instead of six. They track both, and their perf post records an optimization that improved p50 while regressing p90 on specific machines, which median-only measurement would have shipped. Tracy reports the same shape from the other end: 83.3ms → 2.5ms per frame. **A stutter is a max-frame event; averages hide exactly the thing that reads as cheapness.**

**2. Budget 10ms, not 16.7ms.** RAIL's derivation is the most useful single number in the survey: the 60Hz frame is 16ms, browsers need about 6ms of it to render, so **your code gets about 10ms**. Zed targets 120Hz and therefore **8.33ms** covering state update, layout and framebuffer writes.

**3. Freeze fidelity during the gesture, restore it at rest.** This is the most consistent craft pattern found, and four independent teams converged on it: tldraw's `debouncedZoom` above 500 shapes; Excalidraw's `shouldCacheIgnoreZoom` reusing **stale, wrong-resolution bitmaps** mid-gesture; Glide Data Grid dropping DPR to 1× on Firefox and 2× on Safari **while scrolling** and restoring up to 5× when idle; and Perfetto not moving its canvas at all until the viewport drifts past tolerance. **Smoothness is bought with transient softness, deliberately, everywhere.** The corollary is that the crisp state must arrive promptly and unmistakably when motion stops, or the softness reads as a bug rather than a trade.

**4. Selection and hover are a spec, not a detail.** tldraw's published rules are the closest thing to a written standard: hollow shapes let the pointer pass through while filled shapes stop it; labels beat edges; frames clip and block selection behind them; ties break on z-index. Their eraser post is the model for gesture quality — the eraser is tested as a **line segment rather than a point** so shapes cannot survive between sparse pointer samples on a fast drag (tunneling), the hit margin is divided by zoom so it feels the same physical size at any zoom, marked shapes render semi-transparent, nothing deletes until pointer-up, and Escape mid-drag restores everything to full opacity. Konva's `hitFunc` and `hitStrokeWidth` exist for the same reason: **the clickable region should be larger and simpler than the drawn region**, especially for thin lines and small handles. Firefox Profiler's `isHoveredOnlyDifferent` flag and Perfetto's `hoverMonitor.ifStateChanged()` both exist so hover does not cost a full repaint — hover responsiveness is a budgeted feature, not a freebie.

**5. Determinism is an aesthetic requirement.** tldraw's hand-drawn wobble comes from a **seeded PRNG keyed on the shape's ID**, not `Math.random()`, so the character is stable across re-renders instead of re-rolling every frame. This is the sharpest craft finding in the survey and it generalizes past hand-drawn styling: **any procedural visual character must be a pure function of stable identity, or it shimmers.** Mapbox's `CrossTileSymbolIndex` is the same principle applied to labels — a shared `crossTileID` for the same symbol across zoom levels so labels do not flicker as tiles load and unload, with collision emitting **opacities in 0–1 that the GPU interpolates** rather than binary show/hide, so labels fade rather than pop.

**On honesty about incompleteness.** Perfetto's checkerboard is the best-designed "we don't have this data yet" affordance found: the stale frame stays on screen, and everything outside the loaded span gets a diagonal hatch with a "Loading..." label that is skipped when it does not fit. Perfetto's mipmap `count` column is the same instinct applied to LOD — when N slices collapse into one pixel, the UI can say so rather than silently showing one. **Both are cases where the quality move is admitting what the view does not know.**

**On sub-pixel correctness.** Excalidraw snaps 1px grid lines **only at 100% zoom**, with the source explaining that at other zooms the offset is fractional — honest partial handling rather than a pretence of universal snapping. MDN's `Math.floor()` guidance for `drawImage` coordinates and `imageSmoothingEnabled = false` for pixel-exact blits are the authoritative baseline. Zed keeps **up to 16 sub-pixel variants per glyph** in its atlas rather than snapping text to whole pixels; Rive avoids the question entirely with analytic AA that stays crisp at any scale without an atlas; Quadratic's MSDF atlas holds crispness from **0.01× to 10× zoom** off a single 42px atlas.

**Empty states: no evidence found.** No published source in this survey discusses canvas empty states as a craft topic. **UNVERIFIED / absent** — the closest analogue is Perfetto's checkerboard, which is a loading state rather than an empty one.

### 1.8 The convergent architecture — what nearly everyone at scale does

Stripping out what varies, the following appears in nearly every system surveyed, across 2D, WebGL, and even DOM implementations:

1. **Virtualize by viewport, with two thresholds rather than one.** Render generously, re-render lazily. Perfetto: 300px overdraw, 200px drift before moving, 100px safety margin. Jaeger: `viewBuffer` and `viewBufferMin`. AG Grid: 10 rows above and below. CodeMirror: viewport plus margin. **A single threshold thrashes at the boundary.**
2. **Reduce to at most one mark per pixel before drawing.** Chrome DevTools does it in the draw loop (right-to-left with `lastDrawOffset`); Perfetto does it in the database (mipmap max-reduce per depth per bucket); Firefox does it by accumulation into `Float32Array` columns; speedscope does it in a GPU atlas by dyadic zoom level. **The mechanism varies; the invariant does not.**
3. **Quantize the cache key, not just the data.** Power-of-two resolution plus quantized window bounds means panning at fixed zoom produces identical keys and zero refetches. Perfetto's `bitFloor` + `quantFloor`/`quantCeil`, speedscope's `2^zoomLevel` dyadic tiling.
4. **Split "decide what to draw" from "draw it."** Tracy's 30× came from precisely this and he says it dominated even parallelisation. Chrome's `getDrawBatches` → `drawBatchEvents`, Perfetto's collect-labels-then-draw, speedscope's six deferred batches with paint order decided at the end, Mapbox's Bucket. **A cheap traversal producing a small descriptor list, then a tight submission loop with minimal state changes.**
5. **Batch by state, especially colour and font.** Chrome buckets entries by `{color, outline}`; speedscope sets `fillStyle` once per batch; PixiJS's whole performance model is that ordering drives draw-call count; Mapbox's Bucket is one buffer set per style-layer family.
6. **Apply the camera transform once, to one container.** Figma's comment pins (O(n)→O(1), 15fps→60fps), tldraw's single `tl-html-layer`, Perfetto repositioning its canvas with a CSS transform. **The highest-leverage single trick in the survey.**
7. **Split surfaces by update frequency, not by object type.** Excalidraw's static/interactive canvases with independent nonces; VS Code's four terminal layers; tldraw moving ephemeral overlays to canvas while shapes stay DOM; speedscope's 2D text overlay above the WebGL canvas. **The axis is churn rate.**
8. **Hit-test with arithmetic, ideally after a broad phase.** All four trace viewers use math. tldraw uses bounding-box broad phase then distance-to-polyline narrow phase, backed by an R-tree since SDK 4.4. Colour-buffer picking is real (Konva, deck.gl) but is a **second full render pass** and breaks under canvas farbling.
9. **Cache glyphs in an atlas; never `fillText` per glyph per frame.** VS Code terminal, xterm.js, Mapbox SDF, Zed, Quadratic MSDF, and VS Code's editor GPU plan all do it. Elide text below a measured threshold (Perfetto 5px, speedscope the width of `M…M`, Chrome the width of `…` converted to a duration).
10. **Coalesce all repaints into one `requestAnimationFrame`, and separate reads from writes.** Chrome's `RenderCoordinator`, Perfetto's `RafScheduler`, Firefox's `_scheduleDraw`, CodeMirror's measure phase, Jaeger's `_positionList`.
11. **Keep allocation out of the hot loop.** Figma's pre-allocated typed arrays so the GC never runs is the strongest version; Glide replaced closures with index loops for the same reason; VS Code cites minimizing object creation to avoid GC; Tracy packs `ZoneEvent` to 22 bytes.
12. **If there is text, you will build a parallel accessibility tree.** Google Docs (SVG rects with `aria-label`), Glide Data Grid (hidden `<table role="grid">`), Monaco (text paging). Quadratic and Univer publish nothing on it. Chrome's HTML-in-Canvas origin trial exists specifically to make this unnecessary.

### 1.9 The genuine forks in the road

**Fork 1 — Canvas2D vs WebGL.** The evidence does *not* say WebGL always wins. It says WebGL wins when **draw-call count** is the bottleneck, and that is a specific condition. xterm.js's canvas→WebGL numbers are 596–901% for ASCII but **147% for CJK and 42% for emoji**, because the atlas pays off in proportion to glyph repetition. Figma's WebGL→WebGPU migration produced improvement on some device classes, neutral on others, **no published figures**. Excalidraw handles a full drawing tool on Canvas2D with caching alone. Meanwhile WebGL fails *hard*: xterm.js needed a DOM fallback within months because some GPU/browser combinations fail at canvas entirely, and VS Code ships a three-tier fallback that **measures the first 20 frames** before deciding. The honest rule: reach for GPU when you have thousands of similar marks per frame and repeated glyphs; Canvas2D plus caching is sufficient for a great deal more than people assume.

**Fork 2 — immediate vs retained.** regl's thesis is that WebGL's global state machine causes both bugs and slowness, so you delete it and make each command a complete state snapshot. Konva and PixiJS retain a scene graph — and **Konva's own performance documentation tells you to escape it at scale** by drawing many items inside one `sceneFunc`. deck.gl occupies the interesting middle: cheap descriptor objects re-created every render, diffed by `id`, with GPU buffers carried across. The trade is legibility and diffability against per-node overhead, and the systems that scale furthest all end up with a flat, batched submission at the bottom regardless of what sits above it.

**Fork 3 — canvas vs DOM at all. The honest answer about when DOM/SVG wins.**

DOM wins when any of these hold, and the evidence is direct:
- **The content is text that must be selected, found, or read by assistive technology.** CodeMirror's position (for text layout the DOM will usually be faster, and accessibility will be terrible as pixels), Monaco's seven-year hold, WebAIM's finding on Docs, MDN's own guidance to avoid canvas in an accessible app, and Flutter's own FAQ conceding its output does not align with what search engines need.
- **The content is arbitrary and open-ended.** tldraw's whole justification: embedded YouTube, Figma and GitHub content are trivial in the DOM and enormous outside it.
- **The element count is bounded by the viewport and modest.** AG Grid caps at 500 rendered rows; Jaeger draws 300 items initially. Virtualized DOM is entirely adequate at those counts, and you keep native semantics for free.
- **Your team does not have graphics expertise.** The Telefónica account and Microsoft's two-year editor experiment are both evidence that the second 80% of a canvas renderer is a different discipline.

Canvas or GPU wins when: marks per frame are in the thousands-to-millions; zoom rather than scroll is the primary navigation gesture (Figma's point that browser rendering is optimized for scrolling, so geometry re-tessellates on every scale change); cross-platform pixel consistency is a product requirement; or you need effects the DOM does not expose.

**And the most important single data point on this fork is the ending of the xterm.js story.** Canvas2D delivered a 5–45× win over DOM in 2017. WebGL then delivered another 3–9× over canvas. And in May 2024 **VS Code deleted the canvas renderer entirely** — the final shape is WebGL with **DOM as the fallback**, and the xterm.js library itself now ships **DOM as the default** with canvas and WebGL as opt-in addons. The middle rung of the ladder turned out to be the one worth removing.

### 1.10 The five most load-bearing numbers

1. **~10ms, not 16.7ms, is the per-frame code budget.** The 60Hz frame is 16ms, but browsers need roughly 6ms of it to render. (https://web.dev/articles/rail — RAIL also gives 100ms for input response and 50ms for chunked idle work.) Zed's 120Hz equivalent is 8.33ms (https://zed.dev/blog/videogame).
2. **Figma: worst frame 120ms → 30ms, alongside dragging 30 → 60fps average, and file load 29s → under 8s.** (https://www.figma.com/blog/figma-faster/ — verified first-hand.) The maximum-frame figure, not the average, is what describes the felt change.
3. **One mark per pixel column per level is the universal ceiling.** Chrome DevTools enforces it in three lines (`if (barX >= lastDrawOffset) continue`), which is why a 10M-event trace costs the same as a 10K-event one at full zoom-out; Perfetto enforces the same invariant in SQLite via `__intrinsic_slice_mipmap`, carrying a `count` so the collapse stays honest. (https://raw.githubusercontent.com/ChromeDevTools/devtools-frontend/main/front_end/ui/legacy/components/perf_ui/FlameChart.ts; https://raw.githubusercontent.com/google/perfetto/main/src/trace_processor/plugins/slice_mipmap_operator/slice_mipmap_operator.h)
4. **Konva: ~41 MB per empty layer at 1920×1080 retina, a warning above 5 layers, and a hard Mobile Safari ceiling of 256–384 MB where overflow yields a blank canvas rather than degradation.** (https://konvajs.org/docs/performance/All_Performance_Tips.html — verified first-hand.) The strongest published constraint on multi-canvas layering, and it fails catastrophically rather than gracefully.
5. **deck.gl: 60fps to ~1M marks, 10–20fps approaching 10M, browser death between 10M and 100M — and HiDPI costs 4× the fragments.** (https://deck.gl/docs/developer-guide/performance — verified first-hand; measured on 2015 MacBook Pros, with Chrome capping individual allocations at 1GB, and 10M points at 5px radius generating roughly a billion fragment shader invocations per frame.) The clearest published mark-count ceiling anywhere in the survey.

Runners-up worth keeping: xterm.js canvas→WebGL frame times of 4.80ms → 0.69ms (MacBook, 87×26) with the CJK/emoji caveat; Tracy's 83.3ms → 2.5ms from splitting search from submission; tldraw's 10,000 shapes with ~50 rendered; Flutter's CanvasKit at ~1.5 MB; Figma's 3× load win coming from WASM parsing ~20× faster with compressed size a wash.

## Unprompted observations

*Everything in this section is the agent's own synthesis across Part 1 and Part 2, not a finding from any single source.*

**The foldkit canvas module and the production consensus are not in conflict; they sit at different altitudes, and the seam between them is unusually clean.** Every system in Part 1 that scales has the same two-layer shape: a cheap traversal that decides what to draw, producing a small descriptor list, and a tight submission loop that draws it with minimal state changes. Tracy's 30× came from separating exactly those two phases; Chrome's `getDrawBatches`, Perfetto's label collection, and speedscope's six deferred batches are the same split. `Canvas.view` **is** the submission loop, and it is a competent one — the save/restore bracketing is correct, the transform composition is correct, and the runtime already coalesces repaints into a single rAF frame, which is machinery most hand-written canvas code has to build. What foldkit does not supply is the first phase. But that phase is a pure function from Model to `ReadonlyArray<Shape>`, which is precisely where the framework's discipline is strongest, and the shape union being Effect Schemas rather than draw calls means the descriptor list is diffable, hashable and testable as data. The framework has, perhaps accidentally, drawn its boundary at the same place the production systems draw theirs.

**The single most under-appreciated finding in Part 1 is that the middle rung of the ladder got removed.** Canvas2D beat DOM by 5–45× in the VS Code terminal in 2017. WebGL then beat canvas by another 3–9×. And in 2024 Microsoft deleted the canvas renderer, leaving WebGL with **DOM** as the fallback — while the xterm.js library made DOM its default. Read alongside Monaco's editor still being DOM after two funded years of trying to leave, and CodeMirror's unmeasured but consistent position, the pattern is that Canvas2D's niche is narrower than its reputation: it is fast enough to beat naive DOM but not fast enough to be worth its costs once you have either a virtualized DOM below it or a GPU path above it. The teams that stayed on Canvas2D and are happy — Excalidraw, Glide Data Grid, Univer — all did so because of **caching and damage tracking**, not because of Canvas2D's raw draw speed. That reframes the technology choice: the question is not "is canvas faster than DOM" but "does my content have a natural cache key, and can I afford to rebuild selection, hit testing, and accessibility."

**Three teams independently invented the same quality trick, and nobody has named it.** tldraw freezes the zoom level above 500 shapes, Excalidraw reuses stale wrong-resolution bitmaps during a zoom gesture, and Glide Data Grid drops device pixel ratio to 1× or 2× while scrolling and restores it to 5× at rest. Perfetto does the structural version, refusing to move its canvas until the viewport has drifted 200px. This is a coherent, transferable discipline — **trade fidelity for continuity while the user is in motion, and restore fidelity at rest** — and it appears in no guidance document, no MDN page, and no talk. It is also the thing most likely to be omitted by anyone building from first principles, because it feels like a bug rather than a feature until you have felt the alternative. The corollary matters as much: the restore must be prompt and unambiguous, or the transient softness reads as a broken renderer rather than a deliberate trade.

**For a growing event log specifically, the trace viewers have already solved the hard part, and the answer is that the log should be queried, not iterated.** Perfetto's design is the one to study: level of detail is computed in the database as a max-reduce per (depth, time-bucket) with a `count` carried alongside so a collapse can be shown honestly; the bucket size is the time-per-pixel **rounded down to a power of two** so that the cache key only changes at octave boundaries; the fetched window is padded to **3× the visible width** so panning does not refetch; and the view renders whatever frame it has while hatching the regions it has not loaded. Every one of those decisions is about making an append-only feed cheap, and none of them is about rendering at all — the renderer downstream is naive enough to do a linear scan for hit testing, and that is affordable precisely *because* the query already bounded the frame to about one mark per pixel. The lesson generalizes past Perfetto: **in an event-log timeline, the rendering strategy is mostly a data-access strategy wearing a costume.**

**The accessibility cost of canvas is not a corner case, it is the main structural cost, and it is now well enough documented to be predictable.** Google Docs promised no impact, shipped an invisible SVG rect layer carrying text as `aria-label` per run plus ARIA live regions repurposed as a text-to-speech channel, and WebAIM found only rudimentary support. Glide Data Grid builds a debounced hidden `<table role="grid">` over the visible window and states honestly in its own FAQ that no primary developer is an accessibility user. The two fastest published architectures in the survey, Quadratic and Univer, publish nothing on the subject at all. Chrome is now shipping an origin trial specifically to make this parallel tree unnecessary, naming Google Docs, Miro and Figma as the motivating cases. The practical consequence for anything text-bearing on canvas is that **a hidden parallel DOM is not an optional polish item; it is a second implementation of the view that must stay synchronized**, and it should be budgeted as such from the start rather than discovered later. Worth noting that in foldkit this is a less alien proposition than usual: the same Model that produces `ReadonlyArray<Shape>` can produce an `Html` tree beside it, and unlike the canvas surface, that tree would be visible to Scene's locators, server-renderable, and diffed by the same vdom.

**The one thing nobody has published an answer to is the question this brief happens to sit on top of.** Who owns transitions when the view is a pure function of state? The survey found no authoritative source. Springs compose with interruption because they are functions of position and velocity rather than elapsed time, which is a real structural argument, but it implies transient animation state must live somewhere the state model can address — and every pure-state system surveyed either keeps that state inside its own model (CodeMirror keeps the viewport in editor state precisely because extensions need it) or sidesteps the question by not animating. foldkit's shipped answer is unusually concrete for a framework: `viewTransition` is a per-render predicate over `{previousModel, model, message}`, and `Render.afterPaint` exists specifically so the from-state is on screen before the to-state applies. That is an opinion about transition ownership that most frameworks do not have, and it is worth noticing that it puts the decision in `update`'s vocabulary — per Message — rather than in the view's.
