# RQ synthesis — the REF-program research sweep, 2026-08-16

Status: synthesis for the operator's ratification pass. Nine research
questions (RQ-1 … RQ-9) were dispatched on 2026-08-16 against
`scratch/dispatch/19-refinement-research-questions.md`. Each produced a
dated report in `docs/research/`, each report was re-checked by a second
seat that did not write it and was instructed to refute it where
refutable, and each carries that seat's findings as an "Independent
verification" addendum. This document consolidates the nine, maps them
onto the decisions the board is waiting on, and states what a reader
should believe at what strength.

**This document recommends. It edits nothing.** No report body, no
dispatch draft, no grill record and no ledger row is modified by this
pass. Where a report needs a correction, the correction is named here
and left for the operator to order.

---

## How to read this

The REF program is an attempt to close the gap between a mathematical
model of foldlab's protocol and the two running programs that implement
it (a Go daemon and a TypeScript library), by *generating* the running
piece from the proved model rather than by testing the two against each
other forever. The vocabulary below is used throughout.

| Term | What it means here |
| --- | --- |
| the ladder | `scratch/dispatch/17-the-refinement-ladder.md`, which cuts the program into ten slices named REF-0 … REF-9 |
| seam | a place where two independently written pieces of the system must agree. S1 is model↔Go daemon; S7 is model↔TypeScript kernel |
| the kernel | the small program generated from the Lean model that both runtimes will call, so that the seam has one implementation and it is the proved one |
| D-a, D-bc, D-d, D-e | the four decisions ratified at the REF-0 grill on 2026-08-16 (`docs/design/2026-08-16-ref0-extraction-grill-record.md`): extraction mechanism, binding topology, kernel interface, and what `proved` requires |
| T1–T4 | four pre-registered thresholds. If the REF-0 spike breaches one, the program falls back from Lean's own C compiler backend to a purpose-written C generator |
| footprint-clean | a Lean proof that depends on no axioms beyond the three the estate permits, checked mechanically by `#print axioms` |
| the corpus | an exhaustively enumerated set of protocol operations with expected outcomes, generated by executing the model, used as evidence where proof cannot reach |
| divergence | a behaviour where the running daemon and the model disagree; D-e requires the count to reach zero before a seam may be called `proved` |
| gate | a command that exits nonzero when its claim is false. In this estate a claim without a gate is not evidence |

Two words about confidence. Where a report says "I ran it" and the
verifier re-ran it and got the same result, that is the strongest
grade available in this sweep. Where a report quotes a primary source
and the verifier re-fetched the source and found the string, that is
next. Where a claim was checked and did not hold, it is reported as
**refuted** below — never quietly dropped. Where nobody could settle a
claim, it is reported as **unverifiable**, with the reason.

## 1. What each report established

### RQ-1 — Lean's C compiler backend, measured

Lean 4's `@[export]` attribute really does turn a Lean function into a
C-callable symbol, and a hello-kernel built through it links and runs on
Windows in three host configurations (a plain C driver, a Bun
foreign-function host, and a Go cgo host), so threshold T1 is unbreached
on the platform tested. Sizes and speeds are far inside their
thresholds: the added artifact is a 9,584-byte static archive plus a
3,979,776-byte linked-binary delta against T2's 64 MB ceiling, and the
worst measured per-call median at the 10 KB payload is 4.87
microseconds against T3's 1-millisecond ceiling — three orders of
magnitude of margin, re-measured independently at a different
filesystem path. T4 (the runtime unsafe under one-session-at-a-time
use) is also unbreached, but the report's sharpest operational finding
is that a *naive* Go integration crashes anyway: without pinning the
calling goroutine to an operating-system thread the process faulted 4
runs out of 4, and with pinning it completed 3 out of 3 — a difference
invisible to any test that only checks output bytes. Two additions to
the REF-6 slice follow from executed evidence rather than opinion. The
first is that a small hand-written C shim is unavoidable in the native
fallback lane, because the runtime function that allocates a byte array
is a `static inline` with no linkable symbol, so neither Bun's
foreign-function interface nor Go's cgo can construct the argument type
the interface needs; that shim is hand-written C on the critical path
and should be named in the trusted base rather than absorbed silently.
The second is that D-d's totality rule assumes the failure mode is a
trap, and on this backend it is not: a Lean `panic!` returns the type's
default value to the caller, writes one line to standard error, and the
process exits 0 — so "no trap" as written cannot catch the failure the
chosen backend actually produces. Two smaller mechanical findings: an
`@[export]` on a theorem emits no symbol and no diagnostic at all, so
REF-6 must gate on symbol *existence*; and building the native shared
library the obvious way (`lake build :shared`) produces a 66,560-byte
stub standing on 178 MB of Lean runtime libraries, which would breach
T2 by roughly three times, while explicit static archives plus
dead-code elimination give a self-contained 4 MB library importing only
Windows system libraries.

*Refuted in verification:* three sub-claims. The stated reason why
`lean_initialize_runtime_module` is missing from the library's export
table is wrong (the symbol is present and linked; it is absent from the
Windows export table because the shim marks its own entry points for
export, which suppresses automatic export of everything else). The
reference transcript claims every block is pasted verbatim from the run
that produced it, and two blocks are stale or edited. And the report
says the Lean spike file declares five exports where it declares seven.
None of these touches the threshold verdicts, which were re-measured
and hold.

*Unverifiable:* nothing was left unverifiable, but nothing was measured
on Linux and nothing was measured in the WebAssembly lane — the report
says so in two places, and both remain open for the REF-0 spike.

### RQ-2 — Is extraction proved, or trusted?

Across every surveyed project that ships extracted code into
production, the extraction step is **trusted, not proved**, and the
field words that boundary in a strikingly uniform way that we should
borrow. seL4 publishes an exhaustive assumptions page and removes the
compiler and linker from its trusted base only on the architectures
where a separate binary-level proof exists. CompCert's own manual says
roughly 90% of the compiler is proved and the remaining 10% —
elaboration, assembling, linking — is not, with a commercial tool
providing after-the-fact validation instead. Fiat-Crypto names a
pretty-printer and the C toolchain in its trusted base while shipping
into BoringSSL. The camp that genuinely *proves* the step exists —
CakeML, and the CertiCoq/CertiRocq family including a verified
WebAssembly backend — but both live in other proof assistants and
neither is reachable from Lean without abandoning the estate's existing
proofs. Lean 4 sits squarely in the trusted camp on its own evidence:
the shipped source of `Init/Core.lean` says in as many words that using
Lean as a programming language means already trusting the compiler, the
interpreter, and every `@[implemented_by]` and `@[extern]` annotation.
Two findings sharpen this beyond "as expected". First, the hole is
bigger than "the compiler": the generated kernel calls hand-written
runtime C for every primitive over the very types the kernel interface
uses — an ordinary, unannotated byte-array fold emits calls to
`lean_byte_array_uget`, `lean_byte_array_size` and `lean_nat_add` —
and Lean 4.33.0's sources carry 931 `@[extern]` annotations, 626 of
them under `Init/`. Second, and demonstrated by running it, the
estate's existing axiom-footprint gate is blind to this channel by
construction: a theorem that "does not depend on any axioms" coexists
happily with an exported C symbol computing a different function, via
`@[implemented_by]`. The recommended fix is one cheap source-level
check forbidding `@[implemented_by]` and non-allowlisted `@[extern]` in
the sources we own; it adds nothing to the trusted base and reversing
it means deleting the check.

*Refuted in verification:* none. All ten load-bearing claims confirmed,
several by independent re-fetch of the primary text, and the executed
demonstration reproduced here.

*Recorded caution:* the report's summary sentence "REF-7 enlarges the
exposure, not the kind" is true of the *component* but understates the
change in *consequence*. Today the Lean compiler's output is a fixture
a human ratified and a diff would expose; after REF-7 it is the
production seam with no oracle above it. The report's own body says
this plainly; the summary should not be read as softer.

### RQ-3 — WebAssembly as a target for verified code

WebAssembly's core semantics are a defensible foundation for a
bytes-in/bytes-out kernel, and the report measured bit-identical
results for a zero-import module across three engines (wazero's
compiler, wazero's interpreter, and Bun's JavaScriptCore). But the
specification places host imports **outside** that determinism
guarantee explicitly, and the consequence was demonstrated
mechanically: the same WebAssembly bytes that wazero runs to completion
make Bun 1.3.14 throw an out-of-bounds memory error, and a system call
that wazero answers with errno 0 (and errno 21 when it should fault)
Bun answers with 32 in both cases — Bun is returning a byte count where
the specification says errno, confirmed by two further probes at
lengths 16 and 7 which returned 16 and 7. So D-bc's
"one digest everywhere" property is real, but it is a property of
**modules with no declared imports**, not of WebAssembly files in
general, and REF-6 should gain a mechanical "zero declared imports"
gate. Feature acceptance also diverges, and Lean's own build sits on the
wrong side of it: wazero at its default configuration rejects shared
memory and tail calls, while Bun accepts both unconfigured, and Lean
4.33.0's in-tree Emscripten target is configured with `-pthread` and
`-fwasm-exceptions`. The Lean-to-WebAssembly path is thinner than the
dispatch's leads suggested: the target exists in Lean's build system,
but its continuous-integration job has been commented out since v4.16.0
(2025-02-03), no release ships a WebAssembly asset, and the browser-based
Lean editor named as a lead turns out to run Lean server-side, refuting
that lead. Two consequences for ratified text: D-a's T4 must not be
scored against a shared-function-handle call pattern, because that
faults the Go process by misusing the host interface rather than by any
Lean-runtime unsafety — the safe pattern for a Lean-runtime module is
one instance per session, which makes the per-instance memory and
instantiation evidence the grill record already requires the deciding
data; and D-d's totality rule needs a clarification, because the
specification licenses memory growth to fail for embedder-resource
reasons even under its strictest profile, so an allocation failure must
be a typed refusal rather than a trap.

*Refuted in verification:* one sampled sub-claim. The report's
description of what a search of wazero's rationale document returned is
false — the same search returns roughly eighteen hits across at least
five topics, including a whole section on goroutine safety of generated
machine code. The *conclusion* drawn from that search survives (none of
those passages states a goroutine-safety contract for the objects in
question), but the description of the evidence does not.

*Calibration corrections carried forward:* three, all in the report's
decision-impact paragraph. Appealing to the grill record's D-bc
amendment 3 is an over-read — that amendment governs toolchain
nondeterminism, not host divergence, and the conclusion stands without
it. T4's ratified wording already excludes the shared-handle pattern,
so the urgency is overstated. And the grill record's amendment 6
already makes per-instance instantiation and memory *required*
evidence, so calling it "decisive rather than optional" misstates the
record.

### RQ-4 — The road not taken: verifying the code we already have

The alternative to generating the kernel — proving the existing Go and
TypeScript implementations correspond to the model — was assessed
against its strongest available form and **loses on our seam, for
stated reasons rather than by default**. On the Go side the state of
the art is Gobra, a Viper-based deductive verifier that its own README
calls a prototype; it is live in production use on VerifiedSCION, whose
gate runs on every push and pull request with per-step timeouts up to
six hours, but it is standalone and SMT-backed with no connection to
Lean, and the one published Isabelle-to-Gobra link says in its own words
that the linking step is unverified. Goose/Perennial targets Rocq, not
Lean, and declares its translator trusted. On the TypeScript side the
coordinator's expectation of thinness is confirmed with sources: there
is no TypeScript deductive verifier, TypeScript's own design goals
disclaim soundness as a non-goal, its language specification was
archived in 2020 and the directory holding it is now gone, and the
nearest live tool (Gillian-JS) works on roughly 200 lines of ES5
JavaScript with types elided and no higher-order reasoning. The
alternative would also have to be paid twice in two unrelated
toolchains, and would leave two implementations where D-e demands one.
The concentration achieved by DEV-674/675 cuts *for* extraction rather
than against it: it shrinks the verify-existing target to roughly 780
lines of Go and 1,040 lines of TypeScript — genuinely tractable, and the
report says so — but the same concentration is exactly what makes the
seam replaceable by one generated function. The one finding that should
change something is a gate-design gap: s2n-tls's negative-control
technique (patch the C with planted defects, assert the prover *fails*,
and grep for the specific error) is directly adoptable, and REF-6's
planted-mutant requirement as drafted asserts only a nonzero exit rather
than a specific named refusal.

*Refuted in verification:* none. All ten load-bearing claims confirmed,
including a byte-identical re-run of the source census and three
re-executed GitHub API measurements.

*Unverifiable:* whether s2n's prover batch is a *required* merge check.
The repository shows only that it is launched on push and on
pull-request events; whether its result blocks a merge lives in AWS
configuration outside the repository. The report's "the blocking-ness is
structural" claim is properly read as "no per-commit path visible in the
repository reaches the negative controls", which is what was verified.

*Narrowed by verification:* the gap the report names against REF-6 is
partly already closed. The ladder's REF-6 gate list already reads
"mutants die", so "the mutant roster must sit inside the per-commit
gate" is satisfied as drafted. What is genuinely new is only (a)
asserting a *named refusal* rather than a bare failure, and (b) drawing
mutants from real defect history.

### RQ-5 — Continuous-integration patterns for conformance as a build invariant

The field's blocking proof gate sits at fifteen to twenty-five minutes,
and three independent projects converge there: s2n-tls's bounded
model-checking gate has a measured median of 18 minutes 14 seconds over
its thirty most recent successful runs, and Cedar's Lean job is 15
minutes 10 seconds. Above roughly half an hour, every project surveyed
moves the work off the pull-request path. Caching is not an optimisation
for proof gates but the thing that makes them pull-request gates at all,
and every serious project pairs the cache with a cache-free tier so
that a green tick cannot be an artifact of the cache. The most
decision-bearing finding is an anti-pattern that is documented
behaviour rather than anyone's mistake: GitHub states that a job skipped
by a conditional reports "Success", and that `success`, `skipped` and
`neutral` all count as successful check statuses — so a required check
carried on an `if:`-guarded job is satisfied by a job that never ran.
This estate already has two jobs of exactly that shape
(`negative-controls.yml`'s `bridge` and `windows-r4`, both gated on the
event being a schedule or a manual dispatch); they are correct as a
scheduled tier and would become silently vacuous the day either name
were added to the required-checks list. Hence the constraint on D-e's
status-as-gate obligation: the command that re-verifies the ledger's
claims must run in an unconditional job, in a workflow with no path
filter and no `continue-on-error`. A second executed finding sharpens
Lean gate design generally: `lake build` exits 0 on a `sorry`, so "the
project builds" is not a proof gate — the axiom footprint carries the
load, and `#print axioms` itself exits 0, so a gate must parse output
rather than check a status. The estate's own `verify/moves/run.sh`
already does all of this correctly; the finding is a warning against
future gates written more casually. Wall-clock context for our own
gates: the estate's Lean gate battery runs in 27 to 35 seconds cold.

*Refuted in verification — three claims, two of them material.* First,
the report's central absence claim is false: it asserts that no
blocking gate anywhere in its surveyed set re-derives a documented
status claim and fails the build when the document is false, and
mathlib4 — one of the five repositories whose complete workflow set the
report counted — runs exactly such a gate (`lake exe check-yaml`
re-derives, against the environment at HEAD, every claim of the form
"this theorem is formalised as declaration N" made by four
documentation files, and exits 1 when any is false). Second, the report
asserts that REF-6's byte-identical regeneration gate has no surveyed
prior art and that HACL*'s weekly bot pull request is the only way
anyone reconciles a committed generated artifact; s2n-tls regenerates a
manifest and its compliance data on the pull-request path and **fails
the build** on any difference, which is the strict form D-bc ratified,
running in production. Third, the claimed four-to-fifteen-fold
cache effect at seL4 conflates cache with scope: the pull-request tier
excludes the project's largest proof session and the weekly tier does
not, so the tiers do not run the same proofs. A background measurement
of this repository's own gate battery also failed to reproduce.

*Consequence, and it favours the recommendation:* the recommendation to
keep D-bc's strict regeneration gate is *strengthened* by its own
refutation — the precedent the report said did not exist does exist, and
it is strict. The absence paragraphs must be withdrawn and rewritten
against the counterexamples.

*Unverifiable:* this repository's actual branch-protection settings.
The token available to the research seat cannot read them (HTTP 403),
so every claim about required checks is stated against GitHub's
documented behaviour rather than against our configuration. Someone
with administrator access should confirm which checks are required
before D-e's status command is written.

*Operational note, confirmed:* `model-gate.yml`, `windows-induction.yml`
and `negative-controls.yml`'s scheduled jobs have zero recorded runs as
of 2026-08-16. This is expected — all landed on 2026-08-13 and the first
Monday fire is 2026-08-17 — but a scheduled gate's green is not
evidence until it has fired once, and one manual dispatch would settle
it.

### RQ-6 — Byte-identical artifact generation

The promotion question put to this seat was whether cross-platform
(Windows-to-Linux) *build* byte-identity is achievable for our chosen
WebAssembly toolchain, such that the grill record's datum should become
a gate. **The answer is no: do not promote it**, which means the D-bc
amendment of 2026-08-16 stands exactly as written and the datum stays a
datum. The grounds are, in descending strength: no vendor in our chain
publishes a cross-operating-system byte-identity guarantee, and the only
statement on record from the Emscripten project draws the boundary
explicitly at one machine while reporting the opposite result across
machines; the one place Emscripten *does* engineer cross-platform
reproducibility covers its own system libraries rather than user code;
the nearest production precedent for reproducible WebAssembly
(CosmWasm) solves it by pinning a Docker image and declares even a
different processor architecture's output non-interchangeable for
release; the one toolchain that did achieve host independence (Go) got
there by its own authors removing every host input from the compiler
over a release cycle, which is not an option available to us for LLVM;
and operationally a cross-operating-system gate is a gate we could not
fix, because a red result would be an upstream difference with no lawful
local remedy. Two executed findings change how the gate must be
*written*. Two rebuilds in the same directory prove almost nothing — on
this machine same-directory rebuilds were byte-identical while a
rebuild from a differently-named directory was not, and the standard
path-trimming flag fixed it — so REF-6's "two clean checkouts" must mean
two *different filesystem paths* or the gate passes while blind to the
commonest failure. And Lean's emitted C can absorb the build
directory's name, because the module name is derived from the source
path relative to the package root and is baked into the emitted C as
both a string literal and a symbol name; driving emission through
`lake` or an explicit root flag fixes it, and the verifier executed both
mitigations rather than inferring them.

*Refuted in verification:* no claim. All eleven load-bearing claims and
roughly fifteen sampled beyond them confirmed, both probes re-run, and
two mitigations the body asserted without executing were executed by the
verifier and hold.

*One sub-clause does not survive:* the report's line-ending finding is
real and correctly sourced (Emscripten's generated *text* output
defaults to the host's line endings), but its stated consequence is
overstated. Under the amended D-bc the deployed artifact is built once
on a designated platform, which the estate's own continuous integration
fixes at Ubuntu, so a host-line-ending default cannot falsify the
single-digest claim — it can only perturb the cross-platform datum this
report already recommends never gating. The recommendation to deploy a
standalone WebAssembly file with no generated-JavaScript half is still
right, but on the ground D-bc already states: a JavaScript half is a
second file carrying a second digest, and "one artifact, one digest"
excludes it by construction.

### RQ-7 — What a per-run certificate buys

A certificate and a proof differ in their quantifier and the difference
is not one of degree: a universal proof says "for all inputs", a
certificate says "for this one input, here is why". A verified checker
does not remove trust, it relocates it — and the relocation is worth
having because the checker is small, fixed and published in advance
while the producer is large and changes. The checker's guarantee is
one-directional and this is visible in the theorem rather than only in
the prose: Lean 4.33.0 ships a verified checker whose soundness theorem
reads "if the check returns true then the formula is unsatisfiable", so
success implies the claim and **failure implies nothing** — a refused
certificate is evidence that the session was not certified, not evidence
that it was wrong. Using such a checker costs exactly one visible axiom,
attributable per declaration, which is the direct analogue of D-e's
footprint obligation for this route. "Checking is cheap" is false as a
general claim and the field says so; the fix is a richer certificate
rather than a faster checker, and the cost of REF-8 will be set by what
the certificate contains. Certificates grow with *search effort*, not
statement size, and the growth is brutal — measured here, a one-line
statement about 8-bit multiplication produced a 5,831,357-byte
certificate and the same statement at 12 bits produced 733,925,046
bytes, after which the checker itself failed under Lean's default
limits. Our certificates are in the benign regime for a structural
reason: a foldlab session certificate encodes a *replay*, not a search,
so its size is linear in the operation count — provided it stays a
commitment-plus-replay artifact and never starts carrying intermediate
state. The item requiring an operator ruling is REF-8's gate wording.
The ladder says the certificate is "verified by an independently built
kernel binary"; D-bc as amended pins the *deployed* artifact's digest,
built once and embedded everywhere. Reading 1 (rebuild from the same
source on a clean checkout, byte-identical) is already REF-6's
regeneration gate and adds no semantic independence. Reading 2 (the
same artifact under both hosts re-deriving the same verdict) is cheap,
useful, catches host-embedding bugs, and cannot catch a wrong kernel.
Reading 3 (a differently authored checker) is the only reading giving
semantic independence and is exactly the hand-written OCaml
certificate-checker niche the REF-0 record deliberately preserved.
Finally, a certificate never makes a seam `proved` — D-e admits no
proved-with-asterisks status, and a certificate over a kernel that is
wrong on both sides stays green, which the report demonstrates in code
rather than asserting.

*Refuted in verification — six items, four of them from re-running the
report's own reference material.* The claim that no prior art exists for
a per-session runtime conformance certificate is false: two on-point
precedents were found on the first two widened searches — a TACAS 2023
runtime-monitoring paper whose verdicts serve as certificates in a
formally verified Isabelle checker, and a 2020 "verifiable state
machines" line that certifies state transitions of a stateful,
concurrent service. The honest sentence is "no template for our exact
combination", not "no template". A pre-registered guard the report
states it implemented does not work: the reproduction's driver does not
exit 2 when a tampering control turns out to be a no-op, and a neutered
control reports success because the refusal it triggers comes from a
missing file rather than a detected tamper. One obligation's stated
strength exceeds its demonstration in two places — the journal
obligation refuses any edit that survives canonicalisation, not "any
byte edit anywhere" (demonstrated by re-serialising with different
whitespace and getting a pass), and the build-identity obligation is
written into the certificate but never read on the checking side and
fired by none of the six controls. The enumeration of "exactly three
coherent readings" of independence is not exhaustive — there is a
fourth, *builder* independence, where a different party on different
infrastructure rebuilds from the same source and reproduces the digest,
which is semantically distinct from all three and unnamed. And a
configuration-key list is attributed to a file that does not contain
them (the keys and defaults are genuine; the citation is wrong).

*Downgraded by verification:* "collides with D-bc" is stronger than the
evidence. D-bc pins the digest of the *deployed* artifact and nothing in
it forbids a verifier from rebuilding that artifact and comparing
digests. What exists is an ambiguity in the ladder's wording, which one
editing pass resolves.

*Unverifiable:* the claim that "session certificate" already means an
X.509 artifact to most of the industry. Re-issuing the report's own
search returned database-recovery patents and a process-mining tool and
no TLS results at all. The naming caution is reasonable; the evidence
offered for it is not.

### RQ-8 — What a living model costs

The only large evolving verified codebase with published change costs is
seL4, and its figures give an *ordering* rather than a budget: a local
change costs about a quarter of a person-month; an independent feature
costs one to two person-years and about a third of the proof; a change
touching under five percent of the code still cost a person-year and
seventeen percent — and the authors say plainly that they cannot
quantify the cost of the classes above that. The mechanism behind the
cost is measurable: across 15,018 lemmas and roughly 215,000 lines of
proof, proof size is *quadratic in statement size*, and the outliers are
caused by over-specified lemma statements. This makes what the
refinement equation quantifies over a proof-cost driver, not only a
per-call performance one, which is a second and independent support for
REF-1's candidate split (journal host-owned, outside the state blob).
The structural practices that reduce propagation cost are published and
quotable — the Raft-in-Coq team's five recommendations, of which
"separate theorem statements from their proofs using interfaces" is the
load-bearing one, with a measured build-time effect of over one hundred
times. Cedar is the closest living peer: a Lean model shipped and
maintained at AWS, pinning the same Lean version this estate pins, with
definitions and proofs in mirrored trees and a lint that fails the build
if a proof file is orphaned from the gate. Nobody has built REF-9's loop
— Cedar gates but does not generate, HACL* generates but does not gate,
seL4 gates proofs per pull request with its largest session excluded —
so the estate should expect to publish that number rather than cite one.
Executed on this machine, three results shape REF-1: editing only a
proof body does force a downstream rebuild under Lean 4.33.0 (so
build-isolation arguments for splitting packages buy nothing here); a
proof-body edit leaves the generated C and the 2000-row corpus
byte-identical, which is the load-bearing stability result for REF-6;
and the build is fast enough that build isolation is not a reason to
split — a full cold build of `verify/moves` measured 11.4 and 11.7
seconds and a model-file edit 4.06 seconds. Hence the recommendation for
the open wire-model-home question: one Lake package with a `Moves.Wire`
namespace, justified by measured build cost and by gate topology, since
D-e's first obligation requires the refinement equation to be
footprint-clean inside the same axiom sweep as the abstract laws and
splitting packages splits that sweep.

*Refuted in verification — three claims, two of them consequential.*
The report's arithmetic on the Cedar dissent is wrong: it says three of
AWS's four objections to "develop entirely in Lean, compile to C, deploy
the generated C" dissolve under our narrower scope, and at most one
does. Two of the four are debugging costs, and one of those —
"particularly difficult if the failure is due to an interaction between
handwritten code and Lean-generated C code" — is *sharpened* rather than
dissolved by foldlab's design, since hand-written Go and TypeScript
hosts calling generated kernel code across a bytes interface is
precisely that interaction. The fourth (C is memory-unsafe, so a
compiler bug becomes a security bug) is mitigated in the ratified
WebAssembly lane but live in its pre-registered native fallback. So the
addition recommended to D-bc's stated costs should name **two** costs,
not one. Second, the report's absence finding on Lean proof-repair
tooling is overstated: its own search terms return primary research
rather than the marketing pages it describes (a 260,000-example repair
dataset published in February 2026, and a 127-problem Lean repair
benchmark). The narrow claim — that no established tool repairs proof
terms in response to a *definition* change — survives, and the manual

### RQ-9 — RFC 8785 in a proof assistant: the number problem

The coordinator's concern is **confirmed on the inheritance, sharpened
on the difficulty, and refuted on "no prior art"**. RFC 8785 makes the
ECMAScript number-to-string algorithm normative by reference and by
MUST, and additionally promotes ECMAScript's own *non-normative* Note 2
to a requirement, so the canonicalisation scheme's number rule is
strictly stronger than what ECMAScript itself normatively demands. The
requirement is not one hard problem but one hard step and nine easy
ones, and the seam runs exactly between them: step 5 — find the
shortest digit string, with Note 2's closest, ties-to-even selection —
is the Ryu/Grisu problem, while steps 1–4 and 6–10 are pure
integer-and-string rendering with no floating point in them at all. The
rendering half was transcribed into Lean 4.33.0 during the research
session in roughly forty lines with zero imports and no
`native_decide`, and it reproduces all 26 rows of the specification's
own sample table; the hard half is 1,865 of the 3,296 lines in the only
existing formalisation. That formalisation exists and is in Lean 4 and
is MIT-licensed — refuting the expectation that nothing had been done —
but it is a single-author, zero-star, unreviewed March-2026 project
that pins a different Lean version plus all of Mathlib, uses
`native_decide` (which the estate's footprint gate forbids) in six
places including inside its main lemma, and proves *round-trip and
scale-minimality* rather than ECMAScript conformance, emitting a string
shape that is not the RFC's. Hence: **REF-2 splits before dispatch**,
at step 5 rather than at "structure versus numbers". A ratified-decision
collision surfaces with it. REF-2's charter says the canonical-value law
must hold over the entire value grammar rather than the corpus alphabet,
and the protocol specification already declares a mintable float leaf
that the Go value checker admits for any 64-bit float with no guard. So
the structural slice alone cannot satisfy REF-2's own charter unless the
operator ratifies narrowing the wire grammar — and left unratified this
collides with D-e's requirement that the divergence count be zero, since
the float leaf would be a standing divergence. The recommendation is to
land the structural slice now with the number slice pre-registered, and
to prefer building our own step 5 over importing, because importing puts
Mathlib and an unreviewed third-party project under a `proved` seam to
obtain a theorem that still is not the conformance theorem we need.

*Strengthened beyond the report's own claim:* the verifier drove the
transcribed branch table over the 200,000-value differential corpus
rather than only the 26 specification rows, and got zero mismatches
against a production implementation — so the split point is where the
report says it is, and the lower box really is the easy box.

*Refuted in verification — two claims, both in the inferential layer.*
The report asserts that Lean's `Float` is an opaque external primitive
and therefore that a number law can never be stated about it; on Lean
4.33.0 this is false — `Float` is a Lean-defined, kernel-visible binary64
bit model, and the verifier proved two small facts about it by `rfl` and
`decide` with the estate's permitted axiom footprint. What survives is
narrower and still real: `Float.toString` genuinely is opaque, so no
theorem about *that function* can be proved. The constraint on REF-1's
state representation as the report words it does not follow. Second, the
report calls the proposed 100-million-row nightly wall "a third,
independent, V8-authored oracle"; regenerating it with the repository's
Go generator produces the expected column from Go's own shortest-float
engine — the same engine behind the Go canonicaliser the estate already
differentials — so that gate would be close to a self-test unless the
gate specification names which generator and which runtime.

*Also flagged:* the driver line reading "26 rows" is 22 rendered plus 4
asserted by two constant checks, and the report's own section decomposes
this honestly, so it is a presentation defect rather than a false claim.
And treating the daemon's float leaf as inside REF-2's declared scope is
defensible but unstated — the question the operator should be asked is
"which wire does REF-2 mean", not "here is an established collision".

## 4. Consolidated gaps roster

What no surveyed source answers for our seam. These are not
deficiencies in the reports; they are the shape of the unknown that the
program will have to close itself, and several of them are the REF-0
spike's actual job.

**A. The Lean runtime on WebAssembly — the single question that decides
D-bc.** Whether the Lean runtime can be built to a module with no
declared imports at all is unaddressed by anything located, and Lean's
own Emscripten target deliberately goes the other way. Whether it builds
without exceptions and without threads is unknown — both are supported
build options in one case and unconditional in the other. What the
target's current state actually is, is unknown: its continuous-integration
job has not run since v4.15.0, and "present in the build system" is not
"works". Whether the runtime compiles *reproducibly* to WebAssembly is
entirely unmeasured, and it is the larger half of the artifact by
volume. (RQ-3 §7.1–7.3, RQ-6 §7.4, RQ-1 §8.2.)

**B. Linux, and everything cross-platform.** Every executed result in
the native-lane report is Windows. Whether today's toolchain produces
byte-identical output from Windows and Linux is unknown in *both*
directions — the recommendation not to promote rests on the absence of a
guarantee, which is the right basis for a gate decision but is not
evidence of divergence. One experiment settles it and it is already
inside REF-0's scope. (RQ-1 §8.1, RQ-6 §7.1–7.2.)

**C. What a trap looks like, and how a gate sees one.** D-d makes a trap
a gate failure, but nobody probed out-of-bounds loads, division by zero,
`unreachable`, or stack exhaustion across the two hosts, so the *shape*
of a trap on each host is unknown. And no surveyed project has an
analogue of the totality gate at all: how to make "no trap on 2000 rows"
fast and non-flaky, and how to distinguish a trap from a harness crash,
is ours to design. (RQ-3 §7.4, RQ-5 §7.3.)

**D. Wording precedents that do not exist.** Nobody itemises their
language runtime's primitives in a trusted-base statement — every
surveyed statement says "the compiler" or "the extractor" — so the
completed list recommended for the ladder goes beyond the field's norm
and no source says where to stop. Nobody ships one artifact into two
independent host runtimes, so there is no model for "we assume these two
engines agree". Nobody words an assumption about a canonical-bytes
interface being injective enough for theorems to transfer. And nobody
re-verifies their own trusted-base statement in continuous integration —
though mathlib4's declaration check is the nearest published relative and
should be studied. (RQ-2 §10.2–10.5, RQ-5 §4.1 as corrected.)

**E. Cost data for a living model.** No published cost exists for a
chain that regenerates a deployed artifact under a proof gate — Cedar
gates without generating, HACL* generates without gating, seL4 gates
proofs with its largest session excluded. The best published maintenance
number in the field counts proof updates forced by *code* change, which
is the opposite direction from ours. Nothing measures the cost of
maintaining a frozen, hash-pinned statement discipline. Nothing bounds
how often the operator will actually change the model, so the annual
bill has a known per-change factor and an unknown frequency factor.
And nothing documents what happens between "the gate went red" and "the
gate is green again" — a gap that matters more for a one-operator estate
than for a team. (RQ-8 §8.1–8.8, RQ-5 §7.4 and §7.8, RQ-2 §10.6,
RQ-4 §7.7.)

**F. Numbers.** Nothing anywhere proves ECMAScript-conformant
*rendering*: no proof assistant contains a theorem of the form "this
string equals the specification's algorithm applied to this double". The
single existing formalisation proves round-trip and scale-minimality and
then formats to a different string shape. Nothing covers the *reading*
direction — correctly-rounded decimal to binary64 — which is on the
critical path the moment the kernel must classify a non-canonical
number. No published wall exists for driving a Lean or WebAssembly
canonicaliser through a hundred million rows within a CI budget.
Nothing formalises JSON canonicalisation at all, as opposed to JSON
round-trip. And the model-to-machine link — our binary64 *model* proved,
the host's actual doubles not — is untouched by every surveyed project,
with no calibrated language to borrow. (RQ-9 §6.1–6.8.)

**G. Certificates.** There is a template for the *architecture* — an
untrusted producer, a verified checker, a per-run witness — and now two
on-point precedents over execution traces and stateful services. There
is no template for our exact combination: journal replay through a named
kernel artifact, kernel-digest binding, tamper-evidence over a protocol
daemon's own log. Certificate *authenticity* is out of scope of
everything surveyed — every checker answers "does this verdict follow
from this evidence", none answers "who produced this and were they
entitled to", and our seats and close authority make that live. Nothing
addresses schema evolution, which REF-9 guarantees we will need: a model
extension changes the kernel digest and thereby invalidates every prior
certificate, and whether a certificate is a permanent record valid
against the artifact it names or a transient check valid only at HEAD is
undecided and REF-8 must decide it. And no measurement of *our* checking
cost exists, including by the seat that argued it is linear. (RQ-7
§8.3–8.8, as amended by its verification.)

**H. The verify-existing road, if it is ever revisited.** Nobody has
verified a JSON canonicaliser; every surveyed case study verifies
cryptographic primitives, fixed-width binary parsers, or protocol state
machines over enumerated alphabets. No published cost figure exists for
verifying a TypeScript program of our size, because nobody has done it.
Neither candidate verifier was executed on this machine, so every claim
about what they would accept is documentary. (RQ-4 §7.1–7.4.)

**I. Facts about our own repository that the research seats could not
read.** This repository's branch-protection settings are unreadable from
the research seat (HTTP 403), so every anti-pattern about required
checks is stated against documented behaviour rather than our
configuration; someone with administrator access should confirm which
checks are required before D-e's status command is written. Separately,
no proof gate in the entire survey runs on Windows, and there is no
published wall-clock for a Lean proof gate on Windows to budget REF-6's
Windows lane against. (RQ-5 §7.6, §7.2.)

## 5. Dispatch consequences

Coordinator's voice. Findings before fixes: each item names what the
evidence showed before naming what should change, and nothing below is
an instruction to any seat — these are recommendations for the
operator's ratification pass.

**5.1 Two decisions should be taken before their slices dispatch, not
inside them.**

The first is REF-2's wire grammar. The protocol specification declares a
mintable float leaf that the Go value checker admits with no guard, and
REF-2's charter demands the canonical-value law hold over the entire
value grammar. Landing the structural slice without ratifying whether
that leaf stays mintable leaves a standing divergence, which D-e's
zero-divergence rule does not tolerate. The question to put is not "does
this collide" but "which wire does REF-2 mean" — the abstract wire value
grammar, or the daemon's authoring types. Either answer is workable;
discovering the question mid-slice is the hidden rigor demand the estate
refuses.

The second is REF-8's independence wording. "Verified by an
independently built kernel binary" has four coherent readings and they
are four different slices with four different costs, one of which
(rebuild from the same source) adds no semantic independence at all and
is already REF-6's job. The recommendation is to gate REF-8 on host
independence, record build independence as discharged by REF-6, name
implementation independence as an optional later slice with its stated
cost — a second hand-authored implementation of the wire semantics that
must be maintained through every REF-9 model change — and name builder
independence as the fourth option so it is chosen rather than
overlooked.

**5.2 One ratified obligation is currently unenforceable and should be
reworded before REF-6 writes its gates.**

D-d's totality rule says a trap on any input is a gate failure. On the
selected backend the failure mode is not a trap: a Lean `panic!` returns
the type's default value, writes one line to standard error, and exits
0. In the WebAssembly lane there is a second case the wording misses —
the specification licenses memory growth to fail for embedder-resource
reasons, so an allocation failure must be a typed refusal or totality
holds only below the tightest host's limit. The recommended wording is
"no trap, no defaulted return, and no kernel-produced output on standard
error", enforced by a source gate forbidding `panic!`, partiality and
`sorry` in kernel code plus an artifact gate asserting the panic
routine's count in the emitted C is zero. Both halves were demonstrated
mechanically. The residue the operator should see: a typed refusal
preserves totality but not cross-host determinism, because the same
input can refuse on the tighter host and succeed on the looser one, and
the artifact digest cannot see that difference.

**5.3 REF-6's gate list should grow by six mechanical checks, each of
which exists because something was executed rather than argued.**

Symbol existence, because an `@[export]` on a theorem emits no symbol
and no diagnostic. Absence of `@[implemented_by]` and non-allowlisted
`@[extern]` in our own sources, because the axiom-footprint gate
provably cannot see that channel. Zero declared imports on the deployed
module, because that is the condition the one-digest behavioural claim
actually rests on. Two clean checkouts *at different filesystem paths*,
because a same-path double build passes while the property fails.
Emission through `lake` or an explicit root flag, because the checkout
directory name otherwise enters the kernel as a string literal and a
symbol. And planted mutants that die by a *named refusal* rather than by
a nonzero exit. Costs are small and stated in the source reports; none
adds anything to the trusted base; each reverses by deleting a check.

**5.4 Two things named in the ladder's trusted-base paragraph are
missing, and one thing not named is on the critical path.**

Missing: the Lean runtime's hand-written C for the byte-array,
natural-number, string and array primitives the emitted kernel calls on
every step; and the assumption that our own kernel sources carry no
`@[implemented_by]` or non-core `@[extern]`. On the critical path and
unnamed: the plain-C shim the native fallback lane requires, which is
hand-written C sitting exactly where the 2026-08-15 no-hand-authoring
ruling bites. It may be moot in the WebAssembly lane, and the spike will
say. It should be named in the trusted base rather than absorbed
silently, and REF-6 should not read the demonstrated shim as a complete
template — it implements one output where the ratified interface has
two.

**5.5 D-bc's stated costs should grow by two, and its central claim
should gain its two conditions.**

The costs: debugging a failure means stepping through generated code and
mapping it back to Lean — sharpened rather than dissolved by our
hand-written-host/generated-kernel boundary — and the memory-unsafety of
generated C, mitigated by the WebAssembly sandbox and live in the native
fallback. Both are AWS's own stated reasons for rejecting this road for
Cedar, and documented dissent belongs in the cost paragraph rather than
in a footnote. The claim: "one digest everywhere" is measured true for a
module with no declared imports and is not a property of WebAssembly
files in general, so the ratified text should state the two conditions
behavioural identity rests on — zero declared imports, and a single
artifact with no generated-JavaScript half. This is a rewording of a
claim, not a reopening of a lane, and it should be grounded on the
measurement rather than on the grill record's amendment 3, which governs
toolchain nondeterminism and was over-read.

**5.6 Two open inputs are now answerable on evidence, and the answers
point the same way.**

The wire model's home: one Lake package with a `Moves.Wire` namespace.
Build isolation buys nothing at our size — a cold build is under twelve
seconds and a model-file edit is four — and gate topology decides it,
because D-e's first obligation requires the refinement equation to be
footprint-clean inside the same axiom sweep as the abstract laws.
`stateBytes`: the journal stays host-owned and outside the blob, now
supported twice over — once by the per-call cost argument the ladder
already makes, and once by the published quadratic relation between what
a statement quantifies over and the proof it costs. A third constraint
arrives from the certificate seat and belongs in the same spec: the
journal must record each operation as the canonical operation bytes the
kernel saw, because a friendlier rendering makes third-party replay
impossible and that is not reversible later.

**5.7 Before ratification, five report bodies need corrections that
this synthesis has recorded but not made.**

RQ-5 must withdraw two absence claims refuted from inside its own
declared search scope, and rewrite its regeneration-gate recommendation
to cite the precedent it said did not exist. RQ-7 must narrow "no prior
art" to "no template for our exact combination", fix a pre-registered
guard that does not work, and correct two obligations whose stated
strength exceeds their demonstration. RQ-8 must correct the Cedar-dissent
arithmetic from three-of-four to at-most-one-of-four (so the operator is
told two costs, not one), narrow its proof-repair absence finding, and
publish the measured cold-build number rather than the estimated range.
RQ-9 must strike the "never over Lean `Float`" constraint, keeping the
narrower and correct "never over `Float.toString`", and rewrite the
nightly-wall rationale to name which generator and which runtime. RQ-1
must regenerate its transcript mechanically rather than weaken its
provenance sentence, and fix the stale counts and the contradicting
comments in its reference files. The operator may reasonably ratify on
this synthesis rather than on the uncorrected bodies; what should not
happen is a later reader citing a body paragraph that its own verifier
refuted.

**5.8 One operational item, cheap and worth doing this week.**

Three workflows carrying scheduled-only jobs have zero recorded runs.
This is expected — they landed on 2026-08-13 and the first scheduled
fire is 2026-08-17 — but a scheduled gate's green is not evidence until
it has fired once, and a single manual dispatch settles it. Separately,
someone with administrator access should read this repository's
branch-protection settings and record which checks are required, because
D-e's status-as-gate obligation is written against that answer and the
research seat could not read it.

## 6. What this synthesis does not settle

The lane is not selected. Every threshold measured is native-lane and
Windows-only; the WebAssembly lane — the ratified one — has been
surveyed but not built, and the single question that decides it (can the
Lean runtime become a module with no declared imports?) has no answer in
any source located. That is the REF-0 spike's job and nothing here
substitutes for it. Nothing here changes the ladder's shape, its slice
order, or the standing law it exists to install. And nothing here is a
ratification: every disposition in §2 is a recommendation to the
operator, and the three marked **re-grill** are questions to be asked,
not answers to be adopted.
