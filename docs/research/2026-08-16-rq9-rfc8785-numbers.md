# RQ-9 — RFC 8785 in a proof assistant: how bad is the number problem?

Research seat for the REF program, 2026-08-16. Serves REF-2 and REF-2's scope
honesty (`scratch/dispatch/17-the-refinement-ladder.md`), under the dispatch
discipline in `scratch/dispatch/19-refinement-research-questions.md`.

Reference area: `docs/research/reference/rq9-rfc8785-numbers/` — own-authored
runnable artifacts, external items linked with licence and retrieval date, and
the recorded transcript of every run cited below.

Every external retrieval in this report is dated **2026-08-16**.

## 0. Verdict up front

The coordinator's concern was: *RFC 8785's number formatting inherits
ECMAScript's shortest-round-trip algorithm, and formally specifying that is a
substantially harder problem than the rest of the canonicalization combined.*

**Confirmed on the inheritance. Sharpened on the difficulty. Refuted on
"no prior art".**

1. **Confirmed.** RFC 8785 §3.2.2.3 makes ECMA-262 §7.1.12.1 normative *by
   reference and by MUST*, and additionally promotes ECMAScript's own
   **non-normative** "Note 2" to a requirement. JCS's number rule is therefore
   strictly stronger than what ECMAScript itself normatively demands (§1).
2. **Sharpened.** The requirement is not one hard problem. It is one hard step
   and nine easy ones, and the seam runs exactly between them. ES step 5 — find
   `(n, k, s)`, shortest, ties-to-even-closest — is the Ryu/Grisu/Schubfach
   problem. Steps 1–4 and 6–10 are pure integer-and-string rendering with no
   floating point in them at all. I transcribed the rendering half into Lean
   4.33.0 in this session, and it reproduces **all 26 rows of RFC 8785
   Appendix B** byte-exactly (§4, transcript in the reference README). The hard
   part is ~1,900 lines of Lean in the only existing formalization; the easy
   part is ~40.
3. **Refuted, with caveats that matter.** Shortest-round-trip printing **has**
   been formalized in a proof assistant — in **Lean 4**, MIT-licensed
   (`lexicone42/ryu-lean4`, §2). But it is a single-author, zero-star, unreviewed
   March-2026 project; it pins Lean `v4.29.0-rc4` and all of Mathlib; it uses
   `native_decide`, which our footprint gate forbids; it proves *round-trip and
   scale-minimality*, **not** ES conformance; and its `format` always emits
   `[-]<digit>[.<digits>]e<int>`, which is **not** the RFC 8785 string. Its
   sibling `nickelean` — verified JSON serialization in Lean 4 — names precisely
   this gap as its own known limitation.

Consequence for the ladder: **REF-2 must split before dispatch**, and the split
point is ES step 5, not "structure vs numbers". Two scoped options with honest
cost and residual are in §5.

## 1. What RFC 8785 actually requires of numbers

### The requirement, quoted

RFC 8785 §3.2.2.3, verbatim
(<https://www.rfc-editor.org/rfc/rfc8785.txt>, retrieved 2026-08-16):

> ECMAScript builds on the IEEE 754 [IEEE754] double-precision standard for
> representing JSON number data. Such data MUST be serialized according to
> Section 7.1.12.1 of [ECMA-262], including the "Note 2" enhancement.
>
> Due to the relative complexity of this part, the algorithm itself is not
> included in this document. For implementers of JCS-compliant number
> serialization, Google's implementation in V8 [V8] may serve as a reference.
> Another compatible number serialization reference implementation is Ryu [RYU],
> which is used by the JCS open-source Java implementation mentioned in
> Appendix G. Appendix B holds a set of IEEE 754 sample values and their
> corresponding JSON serialization.
>
> Note: Since Not a Number (NaN) and Infinity are not permitted in JSON,
> occurrences of NaN or Infinity MUST cause a compliant JCS implementation to
> terminate with an appropriate error.

The normative reference resolves to a **pinned edition**:

> [ECMA-262] ECMA International, "ECMAScript 2019 Language Specification",
> Standard ECMA-262 10th Edition, June 2019,
> <https://www.ecma-international.org/ecma-262/10.0/index.html>.

And §3.2.2 states the standing hazard plainly:

> In the (unlikely) event that a future version of ECMAScript would invalidate
> any of the following serialization methods, it will be up to the developer
> community to either stick to this specification or create a new specification.

### What is inherited

ES2019 §7.1.12.1 `NumberToString ( m )`, verbatim
(<https://262.ecma-international.org/10.0/#sec-tostring-applied-to-the-number-type>,
retrieved 2026-08-16; superscripts restored from the source HTML's `<sup>` tags):

> 1. If m is NaN, return the String "NaN".
> 2. If m is +0 or -0, return the String "0".
> 3. If m is less than zero, return the string-concatenation of "-" and !
>    NumberToString(-m).
> 4. If m is +∞, return the String "Infinity".
> 5. Otherwise, let n, k, and s be integers such that k ≥ 1, 10^(k-1) ≤ s < 10^k,
>    the Number value for s × 10^(n-k) is m, and k is as small as possible. Note
>    that k is the number of digits in the decimal representation of s, that s is
>    not divisible by 10, and that the least significant digit of s is not
>    necessarily uniquely determined by these criteria.
> 6. If k ≤ n ≤ 21, return the string-concatenation of: the code units of the k
>    digits of the decimal representation of s (in order, with no leading
>    zeroes); n - k occurrences of the code unit 0x0030 (DIGIT ZERO)
> 7. If 0 < n ≤ 21, return the string-concatenation of: the code units of the
>    most significant n digits …; the code unit 0x002E (FULL STOP); the code
>    units of the remaining k - n digits …
> 8. If -6 < n ≤ 0, return the string-concatenation of: the code unit 0x0030
>    (DIGIT ZERO); the code unit 0x002E (FULL STOP); -n occurrences of the code
>    unit 0x0030 (DIGIT ZERO); the code units of the k digits …
> 9. Otherwise, if k = 1, return the string-concatenation of: the code unit of
>    the single digit of s; the code unit 0x0065 (LATIN SMALL LETTER E); the code
>    unit 0x002B (PLUS SIGN) or the code unit 0x002D (HYPHEN-MINUS) according to
>    whether n - 1 is positive or negative; the code units of the decimal
>    representation of the integer abs(n - 1) (with no leading zeroes)
> 10. Return the string-concatenation of: … the most significant digit …; FULL
>     STOP; the remaining k - 1 digits …; LATIN SMALL LETTER E; PLUS SIGN or
>     HYPHEN-MINUS …; abs(n - 1) …

And the "Note 2 enhancement" that RFC 8785 turns into a MUST, verbatim from the
same source:

> **Note 2**
> For implementations that provide more accurate conversions than required by
> the rules above, it is recommended that the following alternative version of
> step 5 be used as a guideline:
>
> Otherwise, let n, k, and s be integers such that k ≥ 1, 10^(k-1) ≤ s < 10^k,
> the Number value for s × 10^(n-k) is m, and k is as small as possible. If there
> are multiple possibilities for s, choose the value of s for which s × 10^(n-k)
> is closest in value to m. If there are two such possible values of s, choose
> the one that is even. Note that k is the number of digits in the decimal
> representation of s and that s is not divisible by 10.

### Three consequences the estate should record

**(a) JCS's number rule is stronger than ECMAScript's own normative rule.**
Note 2 is, in ECMAScript, a *recommendation* for implementations that "provide
more accurate conversions than required". RFC 8785 makes it mandatory. I checked
the current draft as well — ECMA-262 draft dated **August 14, 2026**
(<https://tc39.es/ecma262/>, §6.1.6.1.20 `Number::toString ( x, radix )`,
retrieved 2026-08-16) — and Note 2 is *still* worded as a recommendation there.
So an implementation can be ECMAScript-conformant and JCS-non-conformant. REF-2's
spec statement must therefore cite RFC 8785's stronger rule, not "what
`JSON.stringify` does".

**(b) The pinned edition has since been restructured, but not changed
behaviourally.** In the August 2026 draft the branch guard reads "n is in the
inclusive interval from -5 to 21" where ES2019 wrote `-6 < n ≤ 0` /
`0 < n ≤ 21` / `k ≤ n ≤ 21`; `-6 < n` and `n ≥ -5` denote the same integers. The
exponent-sign rule moved from "according to whether n - 1 is positive or
negative" to "If n < 0 … HYPHEN-MINUS, else PLUS SIGN"; on the only `n` values
that reach that branch (`n < -5` or `n > 21`) these agree. I found no
behavioural divergence between the pinned ES2019 text and the current draft for
radix 10. That is a *datum*, not a guarantee — see §6.

**(c) Refusal is part of the specification, not an implementation choice.**
NaN and Infinity MUST terminate with an error. This lines up exactly with D-d's
"total by refusal": the kernel returns a typed refusal payload, never a trap and
never a string.

### The shape of the requirement

Read as a program, ES §7.1.12.1 is:

```
        ┌──────────────────── step 5 ────────────────────┐
  m  ──▶│ find (n, k, s): shortest, Note-2 tie-break     │──▶ (sign, s, k, n)
        │ Ryu / Grisu / Schubfach / Dragonbox territory  │            │
        └───────────────────────────────────────────────┘            │
                                                                     ▼
        ┌────────── steps 1-4, 6-10 ──────────┐
        │ branch on n; concatenate digits,    │──▶ the RFC 8785 byte string
        │ zeros, '.', 'e', '+'/'-'.           │
        │ integers and strings only           │
        └─────────────────────────────────────┘
```

The seam between those two boxes is the natural split for REF-2, and §4 shows
that the lower box is genuinely small.

## 2. Formalized floating point, and whether shortest-round-trip printing exists
   in any proof assistant

### 2.1 What Lean gives us today — measured, not recalled

Run on this machine, Lean 4.33.0 (`x86_64-w64-windows-gnu`, commit
`d8b18978322de05a8f3dba51ef03cf5461676c17`). Full probe files and transcripts are
in the reference area; the load-bearing outputs:

| Expression | Lean 4.33.0 result |
| --- | --- |
| `(1e-7 : Float).toString` | `"0.000000"` |
| `(5e-324 : Float).toString` | `"0.000000"` |
| `(1e21 : Float).toString` | `"1000000000000000000000.000000"` |
| `(1e23 : Float).toString` | `"99999999999999991611392.000000"` |
| `(333333333.3333333 : Float).toString` | `"333333333.333333"` |
| `(-0.0 : Float).toString` | `"-0.000000"` |
| `(1.7976931348623157e308 : Float).toString` | a 309-digit expansion ending `.000000` |
| `Lean.JsonNumber.fromFloat? 1e-7` | `Sum.inr ⟨0, 6⟩` — **the value becomes 0** |
| `Lean.JsonNumber.fromFloat? 0.1` | `Sum.inr ⟨100000, 6⟩` — i.e. `0.100000` |
| `#print Float.toString` | `opaque Float.toString : Float → String` |
| `#print Lean.JsonNumber` | `structure … mantissa : Int, exponent : Nat` |
| `(Json.num (9007199254740993 : Int)).compress` | `"9007199254740993"` |

Four findings, each load-bearing:

1. **Lean's native float printer is a fixed-six-decimal printer and does not
   even round-trip.** `333333333.3333333` prints as `333333333.333333`, losing a
   digit. There is nothing in Lean core to build RFC 8785 numbers on. This
   confirms and sharpens the note already recorded in
   `docs/research/2026-08-15-lean-oracle-spike.md` ("`1e-7` → `0` … never
   Float").
2. **`Float.toString` is `opaque`.** It is an `@[extern]` constant with no
   definitional content. *No theorem about it can ever be proved.* Any REF-2
   number law must be stated about a Lean-*defined* binary64 model (a
   `sign/exponent/mantissa` structure), never about Lean's primitive `Float`.
   This is a structural constraint on REF-2's statement, not a preference.
3. **`Lean.JsonNumber` is an exact decimal `(mantissa : Int, exponent : Nat)`,
   not a binary64** — and `fromFloat?` routes through the six-decimal printer, so
   `1e-7` silently becomes `0`. Lean's JSON stack is unusable for this seam, in
   both directions.
4. **Lean's `Json` preserves integers beyond 2^53** (`9007199254740993` survives
   verbatim) where RFC 8785 must round to binary64 (`…992`). Already recorded as
   a divergence class in the oracle spike; re-confirmed here.

Searched and not found: any shortest-round-trip printing in Lean core, Batteries,
or Std. Mathlib was not searched exhaustively; the ecosystem result below stands
in for it.

### 2.2 The one formalization that exists

**`lexicone42/ryu-lean4`** — <https://github.com/lexicone42/ryu-lean4>, HEAD
`5dd60fd7a0f08822a6efa0f97e585ce8efa270d4`, MIT ("Copyright (c) 2026
lexicone42"), retrieved 2026-08-16. Created 2026-03-06, last pushed 2026-03-21;
0 stars, 0 forks, 0 watchers; a single author (`bryan.egan@gmail.com`, 24
commits).

Its main theorem, verbatim from `RyuLean4/Roundtrip/FullRoundtrip.lean` at that
SHA:

```lean
theorem full_roundtrip (x : F64) (hfin : x.isFinite) :
    (Decimal.parse (Decimal.format (ryu x hfin))).map Decimal.toF64 = some x
```

I read every `.lean` file at that SHA rather than building the project (see the
honesty note below). Measured: **3,296 lines** across 15 files; the shortest-digit
machinery alone (`Ryu/Interval.lean` 1,154 + `Ryu/ShortestRep.lean` 711) is
**1,865 lines**.

What it does and does not establish, for our purposes:

- **It is a round-trip theorem, not an ES-conformance theorem.** It proves
  `parse(format(ryu x)) = x`. It does not prove `format(ryu x)` equals what
  ECMA-262 §7.1.12.1 requires.
- **Its output format is not RFC 8785's.** `Decimal.format`, verbatim from
  `RyuLean4/Decimal/Format.lean`, is documented `Format: [-]<digit>[.<digits>]e<int>`
  and emits `0e0` for zero. RFC 8785 requires `0`, `295147905179352830000`,
  `0.000001`, `1e+21` — the four-branch ES table. The prior art stops exactly
  where our requirement begins.
- **Shortest-ness is proved only up to scale.** Its own README: "**Scale-minimal,
  not digit-minimal** — `ryu_shortest` proves the output uses the coarsest grid
  resolution … the center-closest tie-breaking heuristic means the post-strip
  digit count may not be globally minimal." ES step 5 with Note 2 pins a
  *specific* `s`. That selection is not proved here.
- **`F64` is a model, disconnected from any machine float.** Its README: "The
  `F64` structure is a pure Lean type, not connected to Lean's native `Float` or
  any hardware implementation." Given §2.1's finding that `Float.toString` is
  opaque, this is the *only* possible design — but it means the model↔machine
  connection is assumed, exactly as it would be for us.
- **`native_decide` is present and matters.** The README advertises "Zero
  axioms. Zero sorrys." My textual audit at the pinned SHA found **no `sorry`
  and no `axiom` declaration**, and **six syntactic `native_decide` occurrences**,
  all in `RyuLean4/Roundtrip/FormatParse.lean` (lines 18, 20, 21, 22, 28, 326).
  Line 326 is *inside* `format_parse_roundtrip` itself (line 318), and
  `full_roundtrip` proves itself by `rw [Decimal.format_parse_roundtrip …]`.

  What `native_decide` costs, **measured here** rather than reasoned about
  (`NativeDecideFootprint.lean`, Lean 4.33.0):

  ```
  'RQ9.control' does not depend on any axioms
  'RQ9.viaNative' depends on axioms: [RQ9.viaNative._native.native_decide.ax_1_1]
  'RQ9.charCompare' depends on axioms: [RQ9.charCompare._native.native_decide.ax_1_1]
  'RQ9.downstream' depends on axioms: [RQ9.charCompare._native.native_decide.ax_1_1,
   RQ9.viaNative._native.native_decide.ax_1_1]
  ```

  `decide` has an empty footprint; `native_decide` mints a per-theorem axiom that
  every downstream theorem inherits. "Zero axioms" is true only in the narrow
  sense of "no user-written `axiom` command". Under `#print axioms` — the thing
  `verify/moves`' footprint gate measures — `full_roundtrip` cannot be clean.
  The project does disclose this separately, in its own "Known limitations":
  "All are on small finite ground terms and are sound, but trust the Lean
  compiler for evaluation."

  **Honesty note.** I did **not** build the project. Building it would mean
  executing 3,296 lines of unreviewed third-party Lean (elaboration runs
  arbitrary code) and fetching all of Mathlib. The axiom-footprint consequence
  above is established by (i) reading the source at a pinned SHA and (ii)
  measuring `native_decide`'s footprint behaviour on our own toolchain. Running
  `#print axioms Ryu.full_roundtrip` in a sandbox is listed as a verifier check.

- **Integration cost is real.** `lean-toolchain` pins
  `leanprover/lean4:v4.29.0-rc4`; the estate is on 4.33.0. `lakefile.toml`
  requires Mathlib at tag `v4.28.0`; the manifest pulls Mathlib, Batteries,
  Aesop, Qq, ProofWidgets, Plausible, LeanSearchClient, importGraph, Cli. Its CI
  is `leanprover/lean-action@v1` with `use-mathlib-cache: true` and
  `lean4checker: true` (an external kernel re-check — good practice, and one we
  should note for RQ-5, though it does not remove `native_decide` axioms).

Two siblings by the same author, both MIT, both retrieved 2026-08-16:

- **`lexicone42/shortest-decimal`** — "Generic verified float-to-decimal
  roundtrip theorem in Lean 4 — covers Ryu, Dragonbox, Schubfach, and all
  shortest-decimal algorithms". ryu-lean4's README calls itself "a concrete
  instantiation" of it.
- **`lexicone42/nickelean`** — "Formally verified JSON roundtrip for Nickel
  values in Lean 4". This is the closest existing analogue of REF-2 in
  existence, and **it names our exact gap as its own limitation**, verbatim:

  > **Float string format differs from serde_json** — Our `Decimal.format`
  > always produces scientific notation (`1e-1`, `3.14159e0`). serde_json
  > post-processes Ryu's output into "nicer" forms: `0.1` instead of `1e-1`,
  > `10000000000.0` for integers-as-floats, `e+308` with explicit `+`. The
  > DIGITS are identical (both come from Ryu), so the roundtrip is correct, but
  > the character-level output format differs.

  That is the two-box picture of §1 confirmed by the only project that has
  actually built the upper box: digits proved, rendering unproved.

### 2.3 Searched and not found

Recorded so that the absence is a finding. Searched for a mechanized proof of
Ryu, Grisu, Grisu-Exact, Dragon4, Schubfach, Dragonbox, `dtoa`, or any
shortest-round-trip *printing* algorithm, in Coq/Rocq (incl. Flocq),
Isabelle/HOL (incl. AFP), HOL4, CakeML, PVS, and ACL2. **Nothing found.** What
exists in those systems is adjacent, not on-point:

- **Flocq** (Coq) formalizes floating-point *arithmetic* (Boldo & Melquiond,
  "Enabling Floating-Point Arithmetic in the Coq Proof Assistant", JAR).
- **AFP `IEEE_Floating_Point`** (Lei Yu et al., submitted 2013-07-27,
  <https://www.isa-afp.org/entries/IEEE_Floating_Point.html>): its abstract
  covers "formal specification of the standard and proofs of important
  properties of floating-point arithmetic" plus "a code generation setup". No
  decimal-string printing.
- **CompCert / CakeML** verify floating-point *compilation and optimization*,
  not printing.
- **FloVer / Dandelion** lineage verifies *error bounds*, not printing.

And the algorithms' own status: Ryu's correctness proof is a **paper proof**.
`ulfjack/ryu`'s README, verbatim: "My PLDI'18 paper includes a complete
correctness proof of the algorithm". Not machine-checked.

Two contemporary data points on how subtle "shortest" is:

- Champagne Gareau & Lemire, "Converting Binary Floating-Point Numbers to
  Shortest Decimal Strings: An Experimental Review", arXiv:2603.06581 (arXiv
  `citation_date` 2026/01/15), abstract verbatim: "Often per their
  specification, none of the implementations we surveyed consistently produced
  the shortest possible strings-some generate outputs up to 30% longer than
  optimal."
- `ulfjack/ryu`'s README notes the Java output differs from `Double.toString`
  and that "other specifications, such as for JavaScript, always require the
  shortest output" — and that its low-level API "returns the decimal
  floating-point representation as a struct, allowing clients to implement their
  own formatting". The reference implementation the RFC cites *itself* separates
  digits from rendering.
- `boa-dev/ryu-js` exists at all: "a fork of the ryu crate **adjusted to comply
  to the ECMAScript number-to-string algorithm**" (Apache-2.0, 29 stars).
  Independent evidence that plain Ryu output is not ES output.

## 3. Prior art in verified serialization and parsing

The strongest and most directly calibrating precedent is **EverParse /
EverCBOR** (Project Everest, F\*). From its own manual
(<https://project-everest.github.io/everparse/>, source `doc/index.rst`, last
changed at commit `b7dfc53f07f6ca755250566f9327d44966541a89`), verbatim:

> **EverCBOR**: A verified C and Rust library for CBOR parsing and
> serialization. Currently, EverCBOR supports the deterministic encoding
> (RFC 8949 Section 4.2) **without floating-point numbers**; supporting the full
> CBOR is work in progress.

That sentence is the field's calibrated answer to RQ-9. The most rigorous
verified-parser group in existence ships a *verified deterministic encoding of a
canonical wire format* into production **and excludes the floats**, and says so
in the first paragraph of its manual rather than in a footnote. Our REF-2a option
is not a compromise invented to dodge work; it is the same line the state of the
art draws.

EverParse's core property is also the right name for what REF-2 wants. From
Microsoft Research's own publication page for "EverParse: Verified Secure
Zero-Copy Parsers for Authenticated Message Formats" (Ramananandro,
Delignat-Lavaud, Fournet, Swamy, Chajed, Kobeissi, Protzenko; USENIX Security,
August 2019 — <https://www.microsoft.com/en-us/research/publication/everparse/>,
retrieved 2026-08-16), verbatim:

> The resulting code is verified to be safe (no overflow, no use after free),
> correct (parsing is the inverse of serialization) and non-malleable (each
> message has a unique binary representation).

Non-malleability *is* REF-2's "canonical equality iff semantic equality", stated
in the field's vocabulary. REF-2's theorem statement should borrow that word.

Bounds on the analogy, stated: EverParse targets **binary** tag-length-value
formats (TLS, QUIC, CBOR/COSE via CDDL). It does not address JSON text, decimal
number rendering, or Unicode string escaping. It is a precedent for the *shape*
of the claim and for the *scope discipline*, not a component we can use.

Searched and not found: any formalization of RFC 8785 / JCS itself in any proof
assistant. `nickelean` (§2.2) is the closest — a verified JSON printer/parser
round-trip in Lean 4 — and it is round-trip, not canonicalization, and it
explicitly does not match its target's number rendering.

## 4. The rendering half, transcribed and run

To keep the recommendation grounded rather than argued, I built the lower box of
§1's diagram and ran it.

`docs/research/reference/rq9-rfc8785-numbers/EsNumberToString.lean` is an
own-authored Lean 4 transcription of ES2019 §7.1.12.1 steps 1–4 and 6–10,
core-only (no Mathlib), taking step 5's `(sign, s, k, n)` as an input.
`make_triples.py` derives those triples for the RFC 8785 Appendix B rows from
CPython 3.13.14's `repr` — a source **independent of the fixture's expected
strings** — and emits the Lean vector list. `Driver.lean` runs the renderer over
them.

Recorded run (transcript in the reference README):

```
$ python make_triples.py
rows=26 failures=0
$ LEAN_PATH=. lean --run Driver.lean
appendix-b rendered rows: 22, mismatches: 0
zero rows: 2, refusal rows: 2
integer sub-grammar samples: 13, mismatches: 0
(exit 0)
```

22 rendered + 2 zero rows (ES step 2) + 2 refusal rows (NaN, Infinity) = the 26
rows of Appendix B, which I confirmed is the exact row count of RFC 8785
Appendix B Table 1.

What this establishes, and what it does not:

- **Establishes:** the rendering half is small and elementary. `render` and its
  three helpers occupy ~35 lines inside a 117-line file (the rest is the quoted
  specification and the stated REF-2a obligation), over `Nat`, `Int` and
  `String`, with **zero `import` lines** — no floating point, no Mathlib, no
  `native_decide`. And it is faithful enough to reproduce the RFC's own published
  table exactly from independently-derived digits: two independent
  implementations of the same branch table (mine in Python, mine in Lean) agree
  with the RFC on all 26 rows.
- **Does not establish:** that the renderer is *proved* correct. `Driver.lean`
  runs 26 vectors; it is a test, not a theorem. The file also carries
  `Ref2aIntegerLaw` — the REF-2a obligation **stated, unproved**, and marked as
  such in the source so it cannot be mistaken for a result.

```
ok  	foldlab/canonical	0.977s
```

**Where the number behaviour actually lives.** Both canonicalizers delegate the
whole of ES §7.1.12.1 to their host runtime:

- `go/canonical/canonical.go` `appendCanonical`, `float64` case: refuse
  non-finite, special-case `value == 0` to `"0"`, otherwise `json.Marshal(value)`.
- `packages/core/src/jcs.ts` `encodeValue`, number case: refuse non-finite,
  otherwise `JSON.stringify(value)`.

So today's RFC 8785 number conformance rests entirely on Go's `encoding/json`
and the JS engine's `Number::toString`. Neither is the specification, and
neither is under our control. That is worth naming: **the seam's most
specification-heavy requirement is currently discharged by two third-party
implementations agreeing.**

**The differential.** `go/canonical/differential_fuzz_test.go` runs a 26-entry
sharp corpus (2^53 neighbours, `-0`, `1e21`, `999999999999999900000`, `1e-7`,
`0.000001`, `333333333.33333329`, a 39-digit literal, surrogates, duplicate
keys, invalid UTF-8, depth 128/257) plus 160 deterministic PCG cases at pinned
seeds against a persistent Bun probe; `packages/core/test/jcs.differential.test.ts`
runs the mirror. VERIFICATION.md rates the row **Claimed** "for the stated
corpus and its generated sample".

**Number-only scale, measured today.** The existing differential mixes numbers
into the whole JSON grammar at 160 runs. I built a number-only probe
(`reference/rq9-rfc8785-numbers/number-differential/`) and ran it:

```
$ go run emit.go -n 200000 > emitted.txt      # Go encoding/json
$ bun check.ts emitted.txt                     # Bun / JavaScriptCore JSON.stringify
rows=200000 divergences=0 runtime=bun 1.3.14
```

191,216 rows rendered in exponential form, 8,784 in plain form. **Zero
divergences.** Bound, stated: this measures two implementations agreeing, not
conformance to ES §7.1.12.1; and 2×10^5 of 2^64 bit patterns is ~10^-14 of the
space.

**What the wire actually carries.** Two different grammars, and the gap between
them is the whole scope question:

- `packages/moves/src/wire.ts` line 26: `export type Val = number`, and its
  decoder admits a value only when `typeof j === "number" && Number.isSafeInteger(j) && j >= 0`
  (line 159). The 2,000-vector conformance corpus uses values `0..3`.
- `proto/SPEC.md` line 71 declares the daemon's leaf types:
  `T ::= {"k":"string"|"bool"|"int"|"float"|"null"}`. `proto/go/protod/value_check.go`
  admits `case "int"` only for `math.Trunc(number) == number && math.Abs(number) <= 9007199254740991`,
  but `case "float"` admits **any** `float64`. `proto/ts/src/author.ts` line 165
  mints `{k: "float"}` from a non-integer schema.

So: **binary64 floats are already inside the daemon's declared value grammar.**
REF-2's "entire value grammar, not the corpus alphabet" is therefore not
satisfiable by REF-2a alone unless the wire grammar is narrowed by decision. That
is the fact that forces the split to be made deliberately rather than by
omission.

**What the Lean side has.** `verify/moves/Oracle/Codec.lean`'s header says it
plainly: "The corpus grammar is deliberately narrow: objects with fixed ASCII
keys, non-negative integers below 2^53, and ASCII-identifier strings. Inside that
grammar Lean's own printer already agrees with RFC 8785". VERIFICATION.md pins
the matching bound: "outside it Lean's printer and RFC 8785 diverge". §2.1
measures how far outside: catastrophically, from `1e-7` onward.

### 5.2 The options

Both options assume REF-2's structural work is done either way: object member
sort by UTF-16 code unit, string escaping per §3.2.2.2, I-JSON constraints,
idempotence, and injectivity ("non-malleability") of canonical form. The options
differ only on numbers.

---

#### Option A — **REF-2a alone**: prove the structural laws over a narrowed number grammar; REF-2b deferred

**Scope.** Model RFC 8785 canonical form in Lean over a value grammar whose
numbers are the **integers exactly representable in binary64**, i.e.
`|v| ≤ 9007199254740991`. Prove idempotence, injectivity, and the number law
`render (step5OfNat m) = toString m` (the `Ref2aIntegerLaw` stub in the reference
area). Prove the ES rendering branch table (steps 1–4, 6–10) in full, since it is
cheap and it is what REF-2b will later need anyway. **Ratify a wire-grammar
decision in the same commit**: the daemon's `{"k":"float"}` leaf is either
removed from the mintable type grammar, or explicitly named as outside the proved
seam and left `walled`.

**Cost.**
- Requires a *decision* about `{"k":"float"}`, which is a product decision, not a
  proof decision. If floats stay mintable, S1/S7 cannot reach D-e's
  "divergence constant = 0" on the strength of REF-2a — the float leaf *is* a
  divergence, and D-e admits no proved-with-asterisks status.
- Makes a future alphabet widening (REF-9's own candidate extension is "widen the
  value alphabet") a *proof-obligation* event rather than a schema event.
- Number formatting for whatever remains outside stays a differential wall, so
  the DEV-670/672 instruments must keep carrying it.

**What it adds to the trusted base.** Nothing new. Steps 6–10 are core-Lean
`Nat`/`Int`/`String`; no Mathlib, no `native_decide`, no external library. The
footprint gate should stay at `{propext, Classical.choice, Quot.sound}`.

**Residual, honestly.** RFC 8785's number requirement is proved for a strict
subset of binary64. Every non-integer number that reaches the wire is outside the
theorem, policed by the differential wall alone. The es6testfile wall (below)
would bound that residual empirically at 10^8 values, which is ~5×10^-12 of the
binary64 space.

**Reversal.** Cheap. The rendering theorems are reusable verbatim by REF-2b; the
narrowed grammar is one predicate. Reversing means widening a definition and
proving more, not deleting work.

---

#### Option B — **REF-2a + REF-2b as separate slices**: full binary64, digits imported or built, rendering proved

**Scope.** REF-2a exactly as in Option A, landing first and standing alone. Then
REF-2b: model binary64 as data (`sign`, `biasedExp`, `mantissa` — mandatory,
since `Float.toString` is opaque), obtain ES step 5, prove the composition, and
discharge the S7 printer bound in full.

Two sub-options for step 5, with different costs:

**B1 — import.** Take `lexicone42/shortest-decimal` or `ryu-lean4` (MIT).
- *Cost:* all of Mathlib enters `verify/`'s build; a toolchain reconciliation
  from `v4.29.0-rc4` to 4.33.0; and the `native_decide` occurrences must be
  discharged into `decide` or ordinary proofs before the footprint gate can pass
  — six syntactic occurrences, but line 326 sits inside the main
  `format_parse_roundtrip`, so it is not a mechanical substitution. Then the
  *ES-conformance* gap remains: `ryu_shortest` is scale-minimal, ES Note 2 pins a
  specific `s`, and closing that is new proof work nobody has done.
- *Trusted base added:* a third-party, unreviewed, zero-star Lean project plus
  Mathlib, both of which then sit under a `proved` seam. This is a material
  widening and must be stated in VERIFICATION.md by name.
- *Reversal:* expensive once REF-3/REF-6 depend on it; the extracted kernel would
  carry whatever those definitions compile to.

**B2 — build.** Write our own step 5 against our own binary64 model.
- *Cost:* the honest comparable is 1,865 lines of Lean for the interval and
  search machinery in the only existing attempt, by an author who had already
  built the generic framework. Assume worse for a first attempt.
- *Trusted base added:* nothing beyond Lean itself, if built core-only.
- *Reversal:* it is our code; reversal is deletion.

**Common cost of Option B.** REF-2b is not a slice that fits beside REF-3; it is
comparable in size to the rest of the ladder's proof work put together. It also
imports an external-standard dependency: our `proved` claim would become
conditional on ECMA-262 not changing, and RFC 8785 itself says the community
would then have to "stick to this specification or create a new specification".

**Residual, honestly.** Even with B done, three things remain unproved: (i) the
model↔machine link — our binary64 *model* is proved, the host's actual doubles
are not; (ii) decimal *reading* (text → nearest binary64), which is Clinger's
problem and which nothing in the surveyed material formalizes either, and which
is needed the moment a non-canonical number must be canonicalized rather than
merely recognized; (iii) the ES/JCS Note-2 selection, unless proved rather than
imported.

---

#### Recommendation

**Option A now; Option B pre-registered as REF-2b with B2 preferred over B1.**

Reasons, in order of weight:

1. **The field's own line.** EverCBOR ships a verified deterministic encoding
   "without floating-point numbers". Drawing the same line, openly, is the
   calibrated move — and the estate has a standing rule that the bound be
   centered, not hidden.
2. **The rendering half is cheap and is needed either way.** §4 shows it runs
   today. Landing it in REF-2a means REF-2b, whenever it comes, is *only* step 5.
3. **The wire decision is the real blocker, and it is the operator's.** Whether
   `{"k":"float"}` stays mintable is a product question. RQ-9 cannot answer it;
   it can only make sure it is answered before REF-2 dispatches instead of
   discovered inside it.
4. **B1's trusted-base cost is out of proportion to its benefit.** It would put
   Mathlib and an unreviewed third-party project under a `proved` seam to obtain
   a theorem that still is not the theorem we need (round-trip ≠ ES conformance).

**Two concrete additions to REF-2a's gate, both cheap:**

- **Add the es6testfile wall.** `cyberphone/json-canonicalization` (Apache-2.0)
  publishes `es6testfile100m.txt.gz` — 100 million `hex-ieee,expected` rows,
  2,081,240,993 bytes, referenced by RFC 8785 Appendix B itself and by Appendix I
  as the development portal. Its generator (`testdata/numgen.js`, `numgen.go`) is
  in-repo and deterministic, so the corpus is **regenerable rather than
  vendored** — which is what the 2026-08-15 generated-vectors ruling wants. This
  is a third, independent, V8-authored oracle. Our current differential is Go
  against JavaScriptCore; neither has ever been checked against a V8-authored
  reference. Nightly tier, not per-PR, given the size.
- **Pin the specification edition.** REF-2's spec file should record that the
  target is ES2019 §7.1.12.1 *including Note 2*, that Note 2 is non-normative in
  ECMAScript itself and normative in JCS, and that the August 2026 draft was
  checked for behavioural divergence and none was found for radix 10. That is a
  one-paragraph provenance record which makes a future ECMAScript change a
  *visible* gate failure rather than a silent drift.

---

## 6. What the surveyed material does NOT answer for our seam

Named, not glossed.

1. **Nothing proves ES-conformant *rendering*.** The single existing
   formalization proves round-trip and scale-minimality and then formats to
   `[-]<digit>[.<digits>]e<int>`. No proof assistant anywhere contains a theorem
   of the form "this string equals ECMA-262 §7.1.12.1 applied to this double".
   §4's transcription is a *test-passing* artifact, not a proof; proving it is
   unclaimed ground.
2. **Nothing proves ES step 5 *with Note 2's selection*.** `ryu_shortest` is
   scale-minimal by its own README's admission. JCS's MUST is on the closest,
   ties-to-even `s`. That is the specific obligation, and it is open.
3. **Nothing covers the reading direction.** Canonicalizing a *non-canonical*
   number requires correctly-rounded decimal → binary64 (Clinger's problem). The
   surveyed material formalizes neither direction of decimal conversion outside
   ryu-lean4's own `Decimal.parse`, which parses only its own scientific-notation
   output. If REF-2's kernel must accept non-canonical input — and D-d's "total
   by refusal … malformed and non-canonical included" suggests it must at least
   *classify* it — this gap is on the critical path and nobody has published a
   formalization of it.
4. **No published wall exists for a Lean canonicalizer.** The es6testfile wall
   tests a serializer against V8; it does not tell us how to drive a Lean or
   WASM-kernel canonicalizer through 10^8 rows within a CI budget, nor what that
   costs. RQ-5's wall-clock question and this one meet here, unanswered.
5. **The model↔machine link is untouched everywhere.** ryu-lean4's `F64` is "not
   connected to Lean's native `Float` or any hardware implementation", and §2.1
   shows why it cannot be: `Float.toString` is opaque and `Float` itself is an
   `@[extern]` primitive. Every surveyed project has this gap, and none words a
   statement about it that we could copy — unlike RQ-2's extraction question,
   where calibrated language exists.
6. **No prior art for REF-2's actual theorem.** REF-2 wants "canonical equality
   iff semantic equality per the declared spec". EverParse's non-malleability is
   the closest published property and it is for binary TLV formats. Nothing
   formalizes RFC 8785, and nothing formalizes JSON *canonicalization* (as
   opposed to JSON round-trip) in any proof assistant.
7. **The daemon's `{"k":"float"}` leaf.** No external source can tell us whether
   it should exist. Its existence is what makes REF-2b mandatory rather than
   optional, and its removal is what makes Option A honest rather than
   evasive. That decision is the operator's and it gates REF-2's dispatch.
8. **Cross-runtime number agreement beyond two implementations.** 200,000
   samples of Go against JavaScriptCore diverged zero times, but Go and JSC are
   not the specification, Bun is not V8, and the number of samples is ~10^-14 of
   the space. Whether *any* mainstream pair diverges anywhere in binary64 is not
   answered by anything I found — the RFC's own advice is to run V8 live and
   generate randomly, which is an admission that no closed-form answer exists.

### Defects

1. **D1 (material) — false attribution on the proposed nightly wall.** §5.2 calls
   es6testfile "a third, independent, V8-authored oracle" and recommends
   regenerating rather than vendoring it. Regenerating with `numgen.go` produces
   `expected` from Go's `strconv.AppendFloat(…, -1, 64)` — the same engine behind
   `encoding/json`, one of the two implementations §5.1 already differentials.
   That gate would be close to a self-test of the Go path. The V8-authored oracle
   exists only via `numgen.js` under Node, or possibly via the published asset,
   whose provenance is undocumented. REF-2's gate spec must name **which
   generator** and **which runtime**, or the wall proves less than the report
   says it proves.
2. **D2 (material) — the "opaque `Float`" over-generalization.** §2.1 finding 2,
   §6 item 5, and decisionImpact (5) all assert that Lean's `Float` is an
   `@[extern]` primitive and that a number law can never be stated about it.
   Lean 4.33.0's own source contradicts this (row 22). The constraint on REF-1's
   `stateBytes` representation as the report words it does not follow.
   `Float.toString` remains opaque and that half of the finding stands.
3. **D3 (minor) — "all 26 rows" is 22 rendered plus 4 asserted.** `Driver.lean`
   renders and compares 22 rows. The other four are covered by two constant
   checks (`numberToString .zero == some "0"`, `numberToString .refuse == none`);
   `zeroRows`/`refuseRows` are hand-written string literals whose only use is

   asserted in `make_triples.py` and never checked in Lean. §4 does decompose the
   count honestly, so this is a presentation defect, not a false claim — but the
   driver line reads like a result and is not one.
4. **D4 (minor) — scope conflation between two wires.** §5.1 and decisionImpact
   (2) treat `proto/SPEC.md`'s `{"k":"float"}` leaf as inside REF-2's declared

   The decision the report wants ratified is still worth ratifying; it should be
   presented as "which wire does REF-2 mean", not as an established collision.
